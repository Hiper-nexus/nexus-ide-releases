# Auditoria Overclock 1.0.0 - Benchmark para NexusIDE

Data: 2026-07-05

Objetivo: usar o Overclock 1.0.0 instalado localmente como benchmark competitivo e decidir, com critério de engenharia senior, o que manter do Nexus, o que copiar como ideia e onde superar.

- Nenhum token, email, session id, bearer token ou chave local foi copiado para este relatório.

- A captura visual do app Overclock não foi confiável por limitação de foco/permissão do macOS; a auditoria foi feita por bundle, sidecar, estado local, processos e contratos expostos.

## Veredito executivo

O Overclock 1.0.0 está mais forte que o Nexus em quatro frentes:

1. Voz live/full-duplex com memória persistente e contexto de tela.
2. Restauração durável de panes/sessões com autosave e estado por workspace.
3. Telemetria real de tokens via transcript watchers, não estimativa por stream.
4. Ponte remota/browser/preview e mecanismos operacionais de recuperação.

O Nexus não deve trocar sua base. Nossa base é melhor ou mais promissora em:

1. Experiência terminal real com xterm persistente, DOM reparenting, canvas infinito e split grid.
2. Orquestração MCP local-first com 25 tools, handoff obrigatório, squads, todo visível e roteamento econômico por modelo.
3. Segurança de processo/env melhor estruturada: allowlist de env, zod IPC, secrets fora do renderer, keychain/armazenamento seguro e gates MCP.
4. Voz fallback robusta: wake local, STT Groq/OpenAI/local, TTS OpenAI/Piper/macOS e modo Jarvis que não depende de uma única stack live.

Direção: manter a espinha do Nexus e absorver os padrões vencedores do Overclock como camadas novas: `Jarvis Live`, `session durability`, `real usage telemetry`, `remote bridge`, `browser/preview pane` e `playbooks/harness`.

## Overclock 1.0.0 - mapa técnico

### Empacotamento e app nativo

- App macOS Tauri com bundle id `sh.overclock.app`, versão `1.0.0`.
- DMG assinado/notarizado, com Developer ID e stapled notarization.
- Sidecar Node empacotado em `Contents/Resources/sidecar`.
- Deep link `overclock://`.
- Document handlers para `md`, `txt`, `json`, `ts`, `js`, `yaml`.
- Declara uso de microfone e captura de áudio para ClockVoice/Jarvis.
- Usa plugins Tauri para updater, deep-link, notification, websocket, clipboard, menu/tray/window/webview.

Impacto para Nexus: precisamos de updater, deep link, document open e notarização como acabamento competitivo, mas isso é P2. Não muda o core.

### Sidecar e IPC

O Overclock roda um sidecar Node `@overclock-app/sidecar`, com módulos para:

- `WsHost`
- transcript watchers Claude/Codex
- `GeminiLiveSession`
- `JarvisService`
- `JarvisMemory`
- catálogo/harness/agent spec writer
- MCP CLI injection
- preview server
- remote bridge e remote spawn
- onboarding
- Discord Rich Presence
- handoff/navigate/clarify helpers

Handlers relevantes observados:

- app/config/auth: `app:version`, `appConfig:*`, `workspaceConfig:*`, `serviceKeys:*`, `providers:*`, `auth:*`
- áudio/voz: `audio:*`, `jarvis:*`
- workspace/files: `workspace:*`, `files:*`, `diagnostics:snapshot`
- token/log: `tokens:*`, `log:list`
- catálogo/harness: `catalog:*`, `overclock-catalog:*`, `harness:*`, `recipes:*`, `squads:*`
- missão/sessão/PTY: `mission:*`, `session:*`, `pty:*`, `remote:*`, `perf:snapshot`
- MCP/bridge: browser pane, marketplace, workers, inventory, overlay, stacks, chef invoke

Impacto para Nexus: o Overclock usa uma superfície de sidecar ampla. O Nexus tem IPC mais tipado e estreito, mas falta cobrir alguns domínios estratégicos.

### Sessões e panes

Pontos fortes do Overclock:

- `panes.json` por workspace com panes vivos, provider, modelo, missão, env controlado e argumentos.
- `session.json` por workspace com snapshot de sessão.
- autosave periódico e save on create/close/quit.
- high-water de pane id em `pane-seq.json`, evitando reuso de id e herança errada de telemetria.
- `pty:readSerialized`, `pty:readRaw`, `pty:readRawText`, `pty:hibernate`, `pty:wake`.
- provider session catalog: Claude/Codex sessions e summaries.
- recovery de tmux/SSH/orphan sessions.

Nexus hoje:

- Persiste layout por workspace.
- Reabre missão recriando panes e usando resume flags.
- Mantém xterm vivo durante reparenting e reshape de layout.
- Não persiste buffer serializado/sessão real de PTY entre boots.
- Não tem hibernate/wake nem high-water persistente equivalente.

Gap: crítico. Sessões duráveis são um dos maiores saltos de UX.

### Orquestração

Pontos fortes do Overclock:

- Delegação visível: `Task` invisível bloqueado em agentes delegadores.
- Handoff enforcement por hooks.
- Worker throwaway pode auto-fechar após handoff.
- Watchdog cria handoff sintético em caso de silêncio/stall prolongado.
- Instruções de workspace access e gates de recurso/comando.
- Handoff acorda o orquestrador e entrega quando ele está apto.

Nexus hoje:

- 25 tools MCP em namespace `nexus_*`.
- `nexus_pane_spawn/read/write/wait/close`, `nexus_handoff_submit/list`, missions, squads, task/todo, `nexus_route_task`.
- Handoff obrigatório com Stop-gate.
- Allowlists por agente e bearer token por sessão.
- Entrega ao orquestrador quando idle.
- Roteamento econômico por tarefa/modelo.

Gap: médio-alto. O Nexus já é forte, mas deve adicionar bloqueio explícito de agentes invisíveis por CLI, resource gate, dangerous command gate e watchdog de stall.

### Tokens, custo e atividade

Pontos fortes do Overclock:

- `ClaudeTranscriptWatcher` e `CodexTranscriptWatcher`.
- `token_usage` com dedupe por `message_id`.
- `activity_log_v2`.
- cache split 5m/1h para agregados.
- estatísticas por task/pane/workspace/global/breakdown.
- leaderboard opt-in.

Nexus hoje:

- `cost-tracker` estima tokens a partir de bytes PTY.
- `inputTokens = outputTokens * 3`, custo por tabela de pricing.
- Bom para tendência, ruim para auditoria, billing e confiança do usuário.

Gap: crítico. Precisamos trocar estimativa por leitura real de transcript quando o CLI disponibilizar, com fallback heurístico.

### Catálogo, squads e playbooks

Pontos fortes do Overclock:

- Catálogo SQLite com itens, categorias, overlays, disabled/tombstones e stacks.
- Integração com `davila7/claude-code-templates`.
- Harness com tiers `scout|builder|reviewer`.
- Recipes lintadas contra catálogo, com gaps explícitos permitidos.
- Escrita/cópia de specs de agentes para CLIs.
- Factory squads removidos do seed do usuário para não poluir workspace.

Nexus hoje:

- Catálogo `aitmpl` com cache e instalação de agents/skills em `~/.claude`.
- Squads salvos e orquestrador capaz de desenhar squads.
- Roteador de tarefa já distribui entre modelos instalados.

Gap: médio. O Nexus tem a base, mas precisa de overlay, stacks, recipe/playbook lintado e editor de agent spec. Não copiar a poluição de templates: manter nosso catálogo enxuto e operacional.

### Voz/Jarvis

Pontos fortes do Overclock:

- `JarvisService` com Agent SDK e tools internas.
- `GeminiLiveSession` full-duplex via WebSocket.
- Voz live com `delegar`, `consultar`, `ler`, `navegar`.
- Memória persistente (`JarvisMemory`) com fatos, supersede chain e soft-delete.
- Contexto de tela: panes visíveis, pane focado, missão, home, workspaces.
- ACKs renderer -> sidecar para ações como wizard/restore.
- Echo detection para evitar que TTS vire novo comando.
- `voiceSafeText` remove blocos de código, inline code, JSON e nomes de tools antes de falar.
- Soft stop/grace reuse/dormant mode para manter prosódia e reduzir latência.
- Buffer de mic pendente para não perder a primeira frase enquanto conecta.
- Tool confirmation opcional antes de ações.

Nexus hoje:

- Wake local `Hey Jarvis` com modelo ONNX, custom model opcional.
- PTT/hotkey e mic quente via WakeMic.
- STT com fallback Groq -> OpenAI -> whisper local.
- TTS com fallback OpenAI -> Piper -> macOS say.
- Barge-in, ACKs locais, think fillers, filtros de alucinação do Whisper.
- Jarvis em PT-BR que executa ações: abrir squad/workspace, missão, enviar pane, comando.
- Contexto básico de workspace, panes, squads, missões e recents.

Veredito de voz:

- Overclock provavelmente está melhor em conversa contínua, latência percebida, memória e contexto live.
- Nexus está melhor em resiliência/offline/fallback e wake local.
- A solução correta é adicionar `Jarvis Live` opcional por cima do pipeline atual, não substituir o nosso pipeline.

### Remote, browser e preview

Pontos fortes do Overclock:

- RemoteBridge WSS com self-signed TLS, código de pareamento de 6 dígitos e tokens com expiração.
- Controle remoto/phone/thin client.
- `remoteSpawn` com SSH/tmux e adoção de sessões órfãs.
- Browser webview nativo, navegação/histórico/bounds/popup interception.
- Preview server.

Nexus hoje:

- Não encontrei remote bridge, phone client, browser pane ou preview server.
- Temos file explorer/editor e panes shell/agent.

Gap: alto para percepção de produto. Browser/preview pane aumenta muito o valor para desenvolvimento web. Remote bridge diferencia em uso real.

## O que o Nexus deve manter porque é melhor

1. Electron/xterm como superfície primária de trabalho.
   - O terminal do Nexus reparenta DOM sem resetar sessão durante split/canvas.
   - WebGL tem limite controlado e fallback DOM.
   - Overclock parece forte em pane/processo, mas não vi evidência de canvas/terminal mais rico que o nosso.

2. Canvas infinito + grid.
   - O Nexus já tem `PaneGrid` e `CanvasView` com `xyflow`.
   - Isso é uma vantagem de produto. Não abandonar por layout mais simples.

3. Orquestração MCP local-first.
   - `nexus_route_task` + handoff obrigatório + todos visíveis + squads é uma base superior.
   - Overclock tem bons hooks; devemos absorver esses hooks, não reescrever a orquestração.

4. Segurança de env/secrets.
   - Nexus usa allowlist de env para shell e injeta credenciais só no PTY alvo.
   - Bloqueia variáveis de linker injection (`DYLD_`, `LD_`) em adapters.
   - Voice keys não vão para renderer.
   - Manter essa postura. O Overclock ainda mostra sinais de provider store com fallback/pendência de criptografia.

5. Voz fallback e wake local.
   - O Overclock ganha no live, mas depender de live-only é frágil.
   - Manter STT/TTS recursivo, Piper/say e wake ONNX local.

6. Roteamento econômico multi-modelo.
   - Nexus já trata custo como parte da decisão de delegação.
   - Overclock mede melhor tokens; Nexus roteia melhor por custo/capacidade.

## Roadmap para superar o Overclock

### P0 - Fazer primeiro

1. Telemetria real de uso.
   - Adicionar watchers por CLI: Claude, Codex e Gemini quando possível.
   - Criar tabelas `token_usage`, `activity_log`, `usage_cache`.
   - Usar `message_id`/session id para dedupe.
   - Cost UI deve mostrar `real`, `estimated` ou `mixed`.
   - Manter fallback heurístico do `cost-tracker`.

2. Sessões duráveis.
   - Criar store por workspace: `sessions`, `panes`, `pane_seq`, `serialized_buffers`.
   - Autosave a cada 30s e em create/close/before-quit.
   - Persistir adapter, modelo, effort, cwd, role, missionId, agentName, provider session id e confidence.
   - Usar `SerializeAddon` para buffer real.
   - Expor `pty:readSerialized`/restore.
   - Garantir pane id monotônico por workspace.

3. Jarvis Live v1.
   - Manter PTT/wake atual como fallback.
   - Adicionar `voice:live:start`, `voice:live:stop`, `voice:live:mic`, `voice:live:endTurn`.
   - Adicionar eventos `live_state`, `live_transcript`, `tool_call`, `tool_result`, `interrupted`.
   - Criar `JarvisMemory` local.
   - Criar `voiceSafeText`.
   - Incluir contexto de tela/panes/missão em stream silencioso.
   - Adicionar tool confirmation antes de `run_command`, escrita em pane e ações destrutivas.

4. Gates operacionais.
   - Bloquear `Task`/agentes invisíveis em CLIs que suportem essa flag.
   - Dangerous command gate para comandos vindos de voz/orquestração.
   - Resource gate para impedir exfiltração de chaves/arquivos sensíveis por workers.
   - Workflow deny gate para impedir delegação invisível.
   - Workspace access instruction padronizada por agente.

### P1 - Próxima camada competitiva

5. Browser/preview pane.
   - Pane tipo browser com navegação, histórico, reload, bounds e popup interception.
   - Preview server local para apps web.
   - MCP tools: `nexus_browser_open`, `nexus_browser_navigate`, `nexus_preview_start`, `nexus_browser_screenshot`.

6. Mission worktrees.
   - `nexus_mission_git_status`.
   - `nexus_mission_create_worktree`.
   - UI para status/branch/dirty files por missão.

7. Harness/Playbooks.
   - Renomear para linguagem Nexus: Playbooks.
   - Recipe lint contra catálogo/squads.
   - Overlay por workspace, disabled/tombstone, stacks.
   - Editor/exportador de agent spec.

8. Diagnostics/app observe.
   - `diagnostics:snapshot` no Nexus.
   - MCP tools de self-observe: panes, workspace, app status, screenshots, recent logs.
   - Isso acelera QA e auto-correção por agentes.

9. Hibernate/perf.
   - `pty:hibernate`, `pty:wake`, `perf:snapshot`.
   - UI para congelar workers antigos e liberar memória sem perder contexto salvo.

### P2 - Acabamento de produto

10. Remote bridge.
    - Pareamento local com código curto.
    - Tokens hash+expiração.
    - Phone/thin client para acompanhar missão, ler panes, aprovar comandos e falar com Jarvis.

11. Updater/deep link/document open.
    - `nexus://`.
    - Abrir arquivos `.md/.json/.ts/.js/.yaml`.
    - Atualização assinada.

12. Onboarding com vitórias.
    - Checklist persistente: CLI detectada, login feito, primeira missão, primeiro handoff, voz ativada, catálogo instalado.
    - Sem poluir HomeDeck com tutorial permanente.

13. Discord Rich Presence.
    - Só como opt-in. Não é core.

## Especificação recomendada para voz

O Nexus deve ter dois modos:

1. `Jarvis Classic`
   - O pipeline atual.
   - Melhor para fallback, baixo custo, offline parcial, wake local e ditado.

2. `Jarvis Live`
   - Sessão full-duplex opcional.
   - Memória local.
   - Contexto contínuo da tela.
   - Barge-in real.
   - Echo suppression.
   - Tool confirmation.
   - Dormant mode e grace reuse.
   - Tools rápidas: ler pane, navegar UI, consultar estado, delegar para orquestrador.

Critério de aceite para superar Overclock:

- Primeira resposta audível em menos de 800ms quando a sessão live já estiver quente.
- Não perder a primeira frase durante conexão.
- Interrupção por voz corta TTS em menos de 200ms.
- Código/JSON/tools nunca são lidos integralmente em voz por padrão.
- Jarvis lembra preferências simples entre sessões, com UI para apagar memória.
- Toda ação destrutiva ou comando shell gerado por LLM exige confirmação.
- Quando live falhar, cai para Classic sem perder a intenção do usuário.

## Decisões de não copiar

1. Não migrar o Nexus para Tauri agora.
   - Não há ganho suficiente para justificar trocar Electron/xterm/canvas neste estágio.

2. Não tornar live voice o único caminho.
   - O nosso diferencial deve ser live quando possível e fallback robusto sempre.

3. Não ativar leaderboard/telemetria compartilhada por padrão.
   - Se existir, precisa ser opt-in claro.

4. Não poluir workspace com squads originais/factory.
   - Manter HomeDeck limpo; usar catálogo/playbooks instaláveis.

5. Não aceitar plaintext fallback para secrets.
   - Se o keychain falhar, o modo deve ser sessão-only ou bloqueado, não plaintext persistente.

## Conclusão

O Overclock 1.0.0 prova que o próximo salto competitivo não é mais “ter muitos agentes”. Isso o Nexus já tem. O salto é confiança operacional:

- saber exatamente quanto cada agente gastou;
- voltar a uma missão sem perder contexto;
- falar com o sistema em modo contínuo;
- aprovar ações perigosas com segurança;
- ver preview/browser dentro do fluxo;
- controlar e recuperar sessões remotamente.

Se implementarmos P0 + P1 mantendo canvas, terminal persistente, fallback voice e orquestração MCP local-first, o Nexus fica acima do Overclock no uso real, não apenas pareado.
