# Relatório de Auditoria de Bugs/Correção - NexusIDE

Missão: `mission-mr7vgjyz-1`

Escopo auditado por leitura:

- Race conditions no lifecycle de `BrowserWindow`, mount do renderer e boot watchdog.
- Lifecycle de panes `spawn -> write -> wait_idle -> read -> close`.
- Promises não tratadas, async sem await e catches vazios relevantes.
- Cleanup de listeners IPC/eventos, PTYs e subprocessos.
- Edge cases: pane que morre, CLI travada, timeouts e parsing frágil.

Observação: não gastei tempo no typecheck já conhecido de `src/main/adapters/auth-probe.ts`.

## Achados

### 1. Alta - `kill/close` suprime `exit`, vazando cleanup de sessão

Arquivo: `src/main/pty/pty-manager.ts:246`, `src/main/pty/pty-manager.ts:401`, `src/main/orch/mcp-server.ts:298`

Código relevante:

- `attachProc()` registra `proc.onExit`, mas começa com `if (!sessions.has(sessionId)) return`.
- `destroySession()` limpa timer, remove a sessão de `sessions` e só então chama `session.proc.kill()`.
- Limpezas críticas de MCP/gate/artifacts acontecem por `tapSessionExit()` em `mcp-server.ts`.

#### Cenário de repro

1. Abrir uma missão com worker `cli-agent`.
2. Fechar o pane pela UI ou por `nexus_pane_close`, ou acionar failover que chama `respawnWithResume()`.
3. O renderer chama `window.nexus.pty.kill(sessionId)`.
4. O main entra em `destroySession()`, remove `sessionId` do `Map` e mata o PTY.
5. Quando `node-pty` emite `onExit`, o handler vê que a sessão não existe mais e retorna cedo.

Resultado:

- O renderer não recebe `pty:exit`.
- `tapSessionExit` não roda.
- `waitForIdle()` pendente não resolve como `exited`; tende a esperar até timeout.
- Token MCP e contexto do skill-gate não são liberados.
- `cleanupSessionArtifacts()` não remove `~/.nexus/ephemeral/<token>` nem `~/.nexus/mcp-configs/<token>.json`.
- Parser de handoff legado, pipe guard, failover watch e métricas de custo não recebem o evento de saída.

#### Fix recomendado

Criar um finalizador idempotente de sessão, por exemplo `finalizeSession(sessionId, exitInfo)`, que:

- limpa idle timer;
- remove a sessão do `Map`;
- envia `PTY_CHANNELS.exit` se o `WebContents` ainda puder receber;
- dispara `fireTaps(exitTaps, sessionId)`;
- tolera chamada duplicada quando o `onExit` real chegar depois.

`destroySession()` deve chamar esse finalizador antes/depois do kill de forma idempotente, sem depender do `onExit` posterior para cleanup lógico.

### 2. Alta - `nexus_pane_spawn` fica pendurado quando renderer fecha ou crasha

Arquivo: `src/main/orch/pane-registry.ts:72`, `src/main/orch/pane-registry.ts:249`, `src/main/orch/pane-registry.ts:265`

Código relevante:

- `rendererAvailable()` só testa `orchRenderer !== null && !orchRenderer.isDestroyed()`.
- Não testa `isCrashed()`.
- `requestPaneSpawn()` envia `orchRenderer!.send(...)` sem `try/catch`.
- `unregisterOrchRenderer()` apenas zera `orchRenderer`; não resolve `pendingSpawns`.

#### Cenário de repro

1. Orquestrador chama `nexus_pane_spawn`.
2. Durante o round-trip main -> renderer -> main, a janela fecha, recarrega ou o renderer crasha.
3. `pendingSpawns` continua esperando `paneSpawnResult`.
4. O MCP tool só retorna depois de `SPAWN_TIMEOUT_MS` ou, se `send()` lançar em condição de frame destruído/crashado, pode falhar por exceção fora do caminho normal.

Resultado:

- Orquestração fica parada por até 30s por spawn.
- Em spawn paralelo, vários workers podem timeoutar juntos.
- O erro apresentado ao agente não distingue renderer indisponível de adapter ausente.

#### Fix recomendado

- Atualizar `rendererAvailable()` para também testar `!orchRenderer.isCrashed()`.
- Envolver `orchRenderer.send(...)` em `try/catch`, removendo o pending spawn e resolvendo com erro claro.
- Em `unregisterOrchRenderer()` ou evento de crash, iterar todos os `pendingSpawns`, limpar timers e resolver com `{ ok: false, error: 'renderer unavailable' }`.

### 3. Alta - A causa raiz da "janela preta" foi mitigada, mas não está comprovadamente resolvida

Arquivo: `src/main/window.ts:113`, `src/main/window.ts:159`, `src/main/window.ts:172`, `src/renderer/main.tsx:10`

Código relevante:

- `window.ts` faz retry de `did-fail-load`.
- Há watchdog de load em dev.
- Há watchdog de mount baseado no console `[diag] app montado`.
- `main.tsx` imprime `[diag] app montado` logo após `createRoot(container).render(<App />)`.

#### Cenário de repro

1. Bundle carrega e `createRoot().render()` é chamado.
2. O log `[diag] app montado` é emitido.
3. Um erro ocorre durante render/effects iniciais do React ou antes de a UI realmente commitar conteúdo útil.
4. `mounted = true` impede o reload de mount.
5. Em produção, o watchdog de mount não roda porque está condicionado a `devServerUrl`.
6. Se o renderer crashar após `did-finish-load`, `render-process-gone` só loga em dev e não tenta recuperar.

Resultado:

- A janela preta de Vite frio foi endereçada em parte, mas o sinal de mount é fraco.
- O app ainda pode ficar numa tela escura sem recuperação automática, especialmente em packaged build.

#### Fix recomendado

- Trocar o console-log por um IPC explícito `renderer:mounted`, emitido dentro de `useEffect(() => ..., [])` no `App`, após o primeiro commit.
- Manter watchdog de mount também em produção, com limite de reloads e mensagem de erro visível após exceder limite.
- Tratar `render-process-gone` e `unresponsive` com reload controlado ou tela de recovery.
- Adicionar ErrorBoundary no topo do renderer para renderizar erro em vez de tela preta.

### 4. Média - `loadURL/loadFile` rejeitado vira Promise não tratada

Arquivo: `src/main/window.ts:122`

Código relevante:

```ts
const load = () => {
  if (devServerUrl) {
    void win.loadURL(devServerUrl);
  } else {
    void win.loadFile(...);
  }
};
```

#### Cenário de repro

1. App abre em dev antes do Vite aceitar conexão.
2. `loadURL()` rejeita por conexão recusada, navegação abortada ou frame destruído durante reload.
3. O retorno é descartado com `void`.
4. Mesmo existindo `did-fail-load`, a Promise rejeitada pode aparecer como unhandled rejection no main.

Resultado:

- Ruído/erro global no main process.
- Em versões/configurações mais estritas, unhandled rejection pode encerrar o processo.

#### Fix recomendado

Transformar `load()` em função que captura a Promise:

```ts
void win.loadURL(devServerUrl).catch((err) => {
  if (win.isDestroyed()) return;
  console.warn('[window] loadURL rejected:', err);
});
```

Ignorar explicitamente aborts esperados e manter o retry/backoff para falhas reais.

### 5. Média - `write` em PTY morto pode explodir main/IPC e responder falso positivo

Arquivo: `src/main/pty/pty-manager.ts:411`, `src/main/pty/pty-manager.ts:461`, `src/main/orch/tools-panes.ts:174`, `src/main/orch/tool-util.ts:67`

Código relevante:

- `writeSession()` chama `session.proc.write(data)` sem `try/catch`.
- `orchWriteSession()` também chama `session.proc.write(data)` sem `try/catch`.
- `injectPrompt()` valida o primeiro write, mas não valida o write do Enter.
- `nexus_pane_write` com `submit: false` ignora o retorno de `orchWriteSession()` e responde `{ ok: true }`.

#### Cenário de repro

1. Pane morre entre `sessionIdOf()` e `orchWriteSession()`.
2. Ou um `setTimeout` tenta mandar Enter após pane fechado.
3. `proc.write()` lança ou falha porque o PTY já morreu.

Resultado:

- Possível exceção no main.
- Tool MCP pode retornar `{ ok: true }` sem ter escrito nada.
- Orquestrador acredita que delegou input, mas worker nunca recebeu.

#### Fix recomendado

- Envolver `proc.write()` em `try/catch`.
- Se write falhar, finalizar a sessão como stale usando o mesmo finalizador do Achado 1.
- Fazer `orchWriteSession()` retornar `false` também para exceção de write.
- Em `injectPrompt()`, validar o Enter:

```ts
if (!orchWriteSession(sessionId, '\r')) throw new Error('session is gone');
```

- Em `pane_write` e `pane_write_many`, retornar erro quando qualquer write falhar.

### 6. Média - Pipes ficam órfãos quando pane some

Arquivo: `src/main/orch/pane-pipe.ts:52`, `src/main/orch/pane-pipe.ts:240`, `src/main/orch/pane-registry.ts:117`

Código relevante:

- Pipes ficam em `const pipes = new Map<string, Pipe>()`.
- `syncPanes()` remove apenas `orchMetaByPane` de panes não vivos.
- Não há pruning de pipes cujo `sourcePaneId` ou `targetPaneId` saiu do layout.

#### Cenário de repro

1. No canvas, criar pipe A -> B.
2. Fechar B.
3. `syncPanes()` atualiza lista de panes, mas o pipe continua no registry.
4. `CanvasView` recebe `pipes` e tenta renderizar edge com target ausente, ou o runtime descarta entregas por target indisponível.

Resultado:

- Pipe órfão permanece na UI/store.
- Pode consumir limite `MAX_PIPES`.
- O usuário vê estado inconsistente ou edge quebrado.
- Entregas são descartadas silenciosamente.

#### Fix recomendado

- Expor função `prunePipesForLivePanes(livePaneIds)` em `pane-pipe.ts`.
- Chamar essa função em `syncPanes()` após calcular `liveIds`.
- Emitir mudança de pipes quando houver remoção.
- Limpar `streamStates`, `outQueues`, `idleDirty`, `lastIdleDelivery*` para pipes removidos.

### 7. Média - Subprocessos de voz podem travar o main e não são mortos no quit

Arquivo: `src/main/voice/tts-service.ts:46`, `src/main/voice/tts-service.ts:57`, `src/main/voice/stt-service.ts:38`, `src/main/voice/voice-ipc.ts:187`

Código relevante:

- `speakViaSay()` usa `spawn('/usr/bin/say', ...)`, mas não registra o processo em lugar nenhum.
- `runPiperLocal()` usa `execFileSync(...)` sem timeout.
- `stt-service` usa `execFileSync(...)` para whisper local sem timeout.
- `closeVoiceIpc()` só chama `disposeVoiceHotkey()`.

#### Cenário de repro

1. TTS inicia `say` com texto longo.
2. Usuário fecha o app.
3. `before-quit` chama `closeVoiceIpc()`, mas não mata `say`.

Outro cenário:

1. Configurar Piper ou whisper.cpp para um binário local que trava.
2. Chamar speak/transcribe.
3. `execFileSync` bloqueia o main process indefinidamente.

Resultado:

- Processo filho pode ficar vivo após quit.
- Main process pode congelar.
- UI e IPC param enquanto o binário local não retorna.

#### Fix recomendado

- Trocar `execFileSync` por `execFile`/`spawn` assíncrono com timeout/AbortController.
- Rastrear subprocessos ativos em um `Set<ChildProcess>`.
- Em `closeVoiceIpc()` matar subprocessos ativos.
- Considerar mover STT/TTS local para worker/utility process para não bloquear o main.

### 8. Média - `node-pty` roda no main apesar da arquitetura exigir isolamento

Arquivo: `src/main/pty/pty-manager.ts:4`, `docs/ARCHITECTURE.md:91`

Código relevante:

- `pty-manager.ts` importa `@lydell/node-pty` diretamente no main process.
- A arquitetura documentada diz que `node-pty` deve ficar em `utilityProcess` para isolar crash/FD leak.

#### Cenário de repro

1. Uma CLI ou o addon nativo `node-pty` dispara crash nativo, leak de FD ou comportamento indefinido.
2. Como o addon está carregado no main process, o app inteiro cai.

Resultado:

- Um problema de PTY/CLI pode derrubar main, janelas e orquestração.
- Contraria a própria mitigação arquitetural documentada.

#### Fix recomendado

- Mover o host PTY para `utilityProcess`.
- Main deve virar supervisor e falar com o host por MessagePort/IPC.
- Protocolo mínimo: spawn, write, resize, kill, data, state, exit.
- Em crash do host, main deve marcar sessões como exited/stale, limpar recursos e, quando possível, permitir respawn recuperável.

## Notas adicionais

- O fluxo `PaneGrid` e `CanvasView` chamam `reconcileHosts(liveIds)`, então o cleanup de hosts no renderer existe para grid e canvas.
- O bootstrap principal de stores (`workspace`, `settings`, `providers`, `accounts`, `orch`, `cost`, `pipes`) tem catches de hydrate suficientes; não encontrei bug crítico ali além dos fire-and-forget já cobertos acima.
- O parser legado de handoff tem limite de bloco e tratamento de braces dentro de string, então não entrou como achado principal.

## Conclusão

A correção da janela preta está parcial: melhora o caso de dev server frio, mas ainda não garante mount real nem recovery em produção. O bug mais crítico da auditoria está no lifecycle de PTY: kills iniciados pelo próprio app removem a sessão antes do `onExit`, suprimindo o evento que alimenta cleanup, waiters e stores. Esse ponto também amplifica vazamentos de MCP/gate/artifacts e estados inconsistentes em panes, pipes e failover.
