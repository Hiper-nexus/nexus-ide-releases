# F-1479 — macOS/Linux: na volta do horário de verão a vaga pesada era liberada com o filho do comando ainda rodando

## F-1479 | categoria: funcional | severidade: alta | status: corrigido
- Tela/fluxo: (1) admissão de comando pesado no macOS/Linux → `OwnedCommandProcesses.claim/probe` (`src/main/pty/owned-command-process.ts`) → `captureDescendantSnapshot` (`ps -o lstart`) → `collectDescendantRows` (`src/main/pty/pty-descendant-termination.ts`) → `NativeHeavyCommands.#observe` (`src/main/orch/native-heavy-command.ts:133`) libera a vaga quando o probe diz `gone`. (2) `resources/heavy-command/request.cjs`, resposta HTTP do Main.
- Arquivo:linha (antes):
  - `src/main/pty/pty-descendant-termination.ts:237` — o filtro do F-1435 (filho nascido antes do pai é órfão de PID reciclado) comparava `Date.parse(startedAt)` em todas as plataformas.
  - `resources/heavy-command/request.cjs:33` — `accepted` lia `result.allow` sem conferir o objeto; `:101` (F-1434) tirou o catch do callback HTTP.
- Passos: 1) macOS com TZ America/New_York, 1º/11/2026. 2) Um comando pesado nasce 05:50Z e abre um filho às 06:10Z. 3) O comando sai antes do filho.
- Esperado: a vaga da raiz continua presa enquanto o filho estiver vivo.
- Observado: `ps lstart` dá hora local sem offset. O pai aparece "01:50" (EDT) e o filho "01:10" (EST); `Date.parse` lê o filho como anterior ao pai e o exclui dos descendentes. Com o pai saído, o probe diz `gone` e a vaga é liberada com o filho rodando. A outra metade: HTTP 200 com corpo `null` fazia o `request.cjs` sair com exit 1 e `TypeError: Cannot read properties of null (reading 'allow')`, sem a linha `nexus-heavy: <motivo>`.
- Causa raiz: o filtro do F-1435 só é válido com horários absolutos. Só o inventário do Windows tem esse horário (CIM `CreationDate`, convertido para UTC ISO `o`). O `lstart` do POSIX é ambíguo na hora repetida do horário de verão. O F-1435 dizia que "no POSIX nenhum filho real é excluído", e isso era falso.
- Correcao:
  - `ProcessTableRow.startedAtUtcMs` (opcional): instante absoluto da criação. Só `parseWindowsCommandProcesses` o preenche; o `parseProcessTable` do `ps` nunca preenche.
  - `collectDescendantRows` só exclui o filho quando pai e filho têm `startedAtUtcMs` e o filho é anterior. No Windows o comportamento do F-1435 fica igual; no POSIX o filtro deixa de rodar. Lá ele nunca foi necessário, porque o kernel re-parenta o órfão para o init/subreaper e nenhum PPID aponta para um pai morto.
  - Escolha: restringir o filtro ao horário absoluto em vez de mudar o `ps` para tempo absoluto (`etimes`). Trocar as colunas mudaria a string `startedAt`, que é a identidade de claim, probe e prova de encerramento, e o diff seria maior para um filtro que o POSIX não usa.
  - `request.cjs`: resposta que não é objeto (`null`, número, string, array) sai 78 com `nexus-heavy: Nexus admission sent an unreadable reply (HTTP <status>)`; o callback HTTP volta a ter catch com o mesmo diagnóstico.
