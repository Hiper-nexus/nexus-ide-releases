# F-814 — Portão de integração barra `git merge --abort`, `merge-base`, `merge-tree` e `merge-file` no main, inclusive no meio de um conflito

## F-814 | categoria: seguranca | severidade: alta | status: corrigido
- Tela/fluxo: PreToolUse/Bash hook em `/hook/integration` (portão de integração F-234), pane de missão com o checkout em `main`/`master`.
- Arquivo:linha: `src/main/orch/hook-integration-endpoint.ts` (`INTEGRATION_SEGMENT` e o teste de direção em `integrationCommandHit`, regex `git\s+merge\b`); `src/main/orch/integration-review-gate.ts` (recusa "árvore suja — commite e peça o veredito do HEAD").
- Passos: 1) Checkout em `main`; `git merge feature` para em conflito (`UU a.txt`, `MERGE_HEAD` presente). 2) O agente tenta se recuperar: `git merge --abort`. 3) Ou usa o plumbing de leitura: `git merge-base HEAD feature`, `git merge-base --is-ancestor HEAD feature`, `git merge-tree --write-tree HEAD feature`, `git merge-file a b c`.
- Esperado: nenhum desses comandos é integração. Encerrar um merge já iniciado (`--abort`, `--quit`, `--continue`) e consultar o histórico passam. `git merge feature` no `main` continua exigindo o veredito de modelo de ponta. Com merge em andamento, o push recebe uma recusa que manda resolver ou abortar.
- Observado (F-778, `ec8524a8`): os seis comandos davam `{"decision":"block","reason":"review_required: árvore suja — commite e peça o veredito do HEAD"}`. O agente ficava sem o comando de recuperação no meio do conflito, e a mensagem o mandava commitar a árvore suja, que nesse estado são os marcadores de conflito. `git merge-base --is-ancestor`, o comando que as missões de sincronização do F-785 usam para checar estado, também era barrado.
- Evidencia: revisão adversarial de `ec8524a8` (item A2 de `review-ec8524a8.md`). Reproduzido com repositório git real temporário: 33 dos 56 testes do arquivo falharam contra o código de `ec8524a8` (todos os casos novos de `merge-*`, de `--abort`/`--quit`/`--continue` e a mensagem de merge em andamento); `integration-review-gate.test.ts` falhou em 2 testes novos contra a versão anterior do gate. A causa raiz de `merge-base … main` já existia antes do F-778: o `\b` de `git\s+merge\b` casa antes do hífen.
- Causa: (1) `git\s+merge\b` trata `merge-base`/`merge-tree`/`merge-file` como `git merge`. (2) A detecção de direção do F-778 tratava QUALQUER `git merge` no checkout main como integração, incluindo o rollback. (3) O portão não distinguia árvore suja comum de merge parado em conflito.
- (resolvedor) Correcao:
  - `git merge` só casa seguido de espaço ou fim (`(?=\s|$)`), nas três regexes (`INTEGRATION_SEGMENT`, direção e a isenção `--ff-only`). Isso também fecha o falso positivo antigo `git merge-base … main`.
  - `isMergeControlSegment`: o segmento cujo ÚNICO argumento é `--abort`, `--quit` ou `--continue` (redirecionamentos de saída como `2>&1` e `>/dev/null` à parte) não é integração. `git merge -m '--abort' feature`, `git merge --abort feature` e `git merge --continue --no-ff feature` seguem sendo merge. Um `git push` no mesmo comando segue barrado.
  - `integration-review-gate.ts`: com árvore suja e `MERGE_HEAD` presente (`git rev-parse -q --verify MERGE_HEAD`, só no caminho de recusa), a mensagem é "merge em andamento — resolva os conflitos e conclua com `git merge --continue`, ou desfaça com `git merge --abort`; só depois peça o veredito do HEAD". Vale para o hook e para `nexus_git_push`/push do `nexus_mission_set_status`, que usam a mesma função.
  - Segurança preservada: o `--continue` cria um commit de merge no main sem veredito, mas o veredito é por HEAD exato e o push (hook, `nexus_git_push`, `set_status`) continua exigindo `approve` de ponta para o HEAD resultante (F-234 fail-closed). Quem inicia o merge no main continua passando pelo portão.
- Testes (repositório git real temporário, `init -b main`, ambiente hermético do F-816):
  - `merge-base` (3 formas), `merge-base --is-ancestor`, `merge-tree --write-tree`, `merge-file` e composições com `cd`/pipe passam no main limpo e no meio de um conflito.
  - `--abort`, `--quit`, `--continue`, com espaços, aspas, `2>&1`, `>/dev/null 2>&1 || true` e `&& git status`, passam com conflito real; o `--abort` liberado de fato desfaz o merge (`status` limpo, `a.txt` volta).
  - `git merge feature`, `--no-ff`, `--squash`, `-m "msg"`, `merge-base … && git merge feature` e `git merge --abort || git merge feature` seguem exigindo o veredito.
  - Merge em andamento: `git push origin main` e `git merge feature` recebem a mensagem própria, sem "commit" nem "árvore suja"; árvore suja sem `MERGE_HEAD` mantém a mensagem antiga. Em `integration-review-gate.test.ts`: o mesmo no checkout principal e num checkout vinculado (`git worktree add`), onde `MERGE_HEAD` é por worktree.
  - Varredura linear com 11 entradas adversariais de 16 KB (espaços, milhares de segmentos, aspas desbalanceadas, redirecionamentos em série) e teto de 50 ms, no padrão do bloco "F-764" de `limit-detector.test.ts`.
- Limite conhecido (não tratado aqui): o hook só reconhece `git` no início do segmento. `git -C dir merge x`, `git -c k=v merge x` e `command git merge x` não são reconhecidos como merge, nem como push (já era assim antes do F-778). O portão autoritativo no push continua valendo.
