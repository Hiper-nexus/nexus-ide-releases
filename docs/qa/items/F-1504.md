# F-1504 — nexus_mission_create aceitava qualquer squadId (inclusive o nome do squad)

## F-1504 | categoria: funcional | severidade: media | status: corrigido
- Renumerado na integração com a origin (0.76.252): este achado era o F-1450 da frente de squads (nunca publicado) e virou F-1504 para não colidir com a numeração que a origin publicou (F-1436..F-1451).
- Tela/fluxo: MCP `nexus_mission_create` com `squadId` → depois `nexus_pane_spawn` com `agentName` ou direção a um agente da missão.
- Arquivo:linha: `src/main/orch/tools-domain.ts:368` (leitura de `squadId`) e `:420` (`squadId: rawSquadId || defaultSquadId`), antes da correção.
- Passos: 1) Um agente cria a missão passando o NOME do squad ("Equipe Web") ou um id que não existe em `squadId`. 2) Abre um integrante do squad pela missão.
- Esperado: id inexistente é recusado na criação, com a lista dos squads (id e nome).
- Observado: a missão era gravada com o valor cru. O erro só aparecia depois, longe da causa: `unknown squad agent: X — confira o nome em Configurações › Squads…` (`tools-panes.ts:1544`, porque `findAgentInSquad` não acha o squad) ou `mission direct target requires sealed squad authority` (`mission-engine-production.ts:536`).
- Causa raiz: o handler gravava `str(args, 'squadId')` sem conferir no catálogo.
- Correcao: `resolveMissionCreateSquadId` roda antes de qualquer efeito (antes da baseline de código e da gravação) e recusa com `PreEffectRefusalError` + dica:
  - id que existe passa como antes, inclusive a cópia runtime selada (o fluxo F-1118 cria missão com `mission-runtime-*`);
  - o nome exato de um único squad salvo resolve para o id dele — mesma regra de `requireCatalogAgent` para agentes (decisão técnica: o valor é inequívoco e a missão grava o id; cópias runtime e o Pet Studio ficam fora dessa busca, pois as cópias repetem o nome do squad de origem);
  - nome repetido: `squadId ambíguo: mais de um squad se chama "Revisão"; passe o id: squad-b2 ("Revisão"), squad-b3 ("Revisão")`;
  - desconhecido: `squadId desconhecido: X. Squads disponíveis (id e nome): nexus-fullstack ("Nexus Fullstack"), …`.
  - O `inputSchema` do `squadId` passou a dizer que é o id de um squad salvo (o nome exato único também resolve).
- Fora do escopo (registrado): a criação MCP continua sem selar o squad (`squadRevisionHash`/cópia runtime); o selo nasce na aprovação/preparação. Direcionar um agente nomeado numa missão Autopilot criada pelo MCP com `squadId` ainda exige esse selo (`mission-engine-production.ts:536`). Selar na criação muda a autoridade da missão da mão do operador (F-649) e fica para decisão própria.
- Evidencia:
  - RED (código antigo): `npx vitest run src/main/orch/tools-domain-mission-authority.test.ts -t "F-1504"` → 3 falhas: id inexistente criava a missão (`expected { id: 'mission-new', … } to be an instance of PreEffectRefusalError`), o nome não resolvia (`expected 'Equipe Web' to be 'squad-a1'`) e o nome repetido criava a missão com `squadId: "Revisão"`.
  - GREEN: `npx vitest run src/main/orch/tools-domain-mission-authority.test.ts src/main/orch/tools-domain-mcp-parity.test.ts` → 86/86.
