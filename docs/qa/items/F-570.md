# F-570 — `provider-state/<adapter>/<checkoutId>` nunca era removido, nem com o checkout apagado

## F-570 | categoria: seguranca | severidade: media | status: corrigido

- Tela/fluxo: `<userData>/provider-state/<adapter>/<checkoutId>/…`
  (`linkProviderSessionState` em `cli-mcp-session-artifacts.ts`) guarda
  auth link + histórico de conversa por checkout, para Grok/Kimi/OpenCode/
  Claude family. Não existe nenhum limpador para essa árvore.
- Arquivo:linha (ausência de código): checado em
  `src/main/runtime/worktree-manager.ts` e
  `src/main/orch/ephemeral-artifact-purge.ts` — nenhum hit para
  `provider-state` em nenhum dos dois. `ephemeral-artifact-purge.ts` só
  cuida da árvore efêmera `.nexus/ephemeral/mcp-clients/<hash>`, um conceito
  diferente (e já limpo por `purgeStaleCliMcpSessions`).
- Esperado: quando um checkout/workspace sai do registro, o
  `provider-state/<adapter>/<checkoutId>` correspondente também sai — em
  todos os adapters, não só no que estava ativo no momento.
- Observado: o diretório persiste para sempre, mesmo depois do checkout ser
  apagado/esquecido. Nenhuma idade, nenhum evento de remoção o alcança.
- Investigação de onde "checkout/workspace é removido do registro" realmente
  vive (não é óbvio no código atual):
  - `worktree-manager.ts` (`WorktreeManager`) só tem `purgeRecordsWithoutTask`,
    que derruba registros de **tarefa** órfã dentro de um checkout — nunca o
    checkout inteiro, e um checkout ainda em uso pode ter uma tarefa órfã.
    Não é o gancho certo.
  - `mission-worktree-orchestrator.ts`/`worktree-lifecycle.ts`
    (`teardownTaskWorktree`/`archiveWorktree`) estão marcados no próprio
    cabeçalho como **"NOT WIRED... zero production call sites"** — não é um
    evento real.
  - `persistence/project-identity.ts` mantém um `CheckoutRegistry`
    (`readCheckoutRegistry`/`writeCheckoutRegistry`) mas ele é só-cresce: não
    há função de remoção de entrada.
  - O único evento real de "sai do registro" encontrado é
    `WORKSPACE_CHANNELS.remove` em `persistence/workspace-store.ts` — o
    handler que tira uma pasta da lista de recentes (`~/.nexus/workspaces.json`).
- Correção: novo módulo `persistence/provider-state-purge.ts`
  (`purgeProviderStateForCheckout(userDataPath, checkoutId)`), modelado na
  mesma disciplina de segurança de `ephemeral-artifact-purge.ts`: `checkoutId`
  validado como identificador puro (`^[a-zA-Z0-9][a-zA-Z0-9_-]{0,127}$`, sem
  separador de caminho — rejeita `../`, `/etc`, etc.), nunca segue symlink,
  best-effort por adapter (uma falha não trava as outras). **Nunca apaga por
  idade** — só quando chamado explicitamente. `workspace-store.ts` chama essa
  função dentro do handler `workspace:remove`, resolvendo o `checkoutId` do
  path removido via `resolveProjectExecutionScopeCached` (já usado em todo o
  resto do main para essa mesma tradução path→escopo) e nunca bloqueando a
  remoção do workspace em si — falha de resolução só loga e sai.
- Lacuna aceita, não coberta nesta rodada: "teardown de worktree quando for o
  checkout dele" (texto original do fast-follow) não tem hoje um evento real
  equivalente em `WorktreeManager` — todo `WorktreeRecord` é uma tarefa ou
  pane *dentro* de um checkout, nunca o checkout em si. Não fabriquei um
  gancho ali para não arriscar disparar a limpeza no lugar errado (ex.: numa
  tarefa órfã de um checkout ainda ativo). Se existir em outro lugar um
  evento real de "checkout inteiro descartado" fora do que investiguei, falta
  chamar `purgeProviderStateForCheckout` também dali.
- Evidência: `provider-state-purge.test.ts` (5 testes: remove só o checkout
  certo entre vários adapters/checkouts, no-op sem match, no-op sem árvore,
  rejeita `checkoutId` malicioso preservando arquivo fora da árvore, nunca
  segue symlink). `workspace-store-provider-state-purge.test.ts` (2 testes:
  `workspace:remove` purga só o checkout do path removido, e a remoção do
  workspace segue funcionando mesmo quando o checkout não resolve).
- Validação: `npx vitest run src/main/persistence/provider-state-purge
  src/main/persistence/workspace-store src/main/runtime/worktree-manager
  src/main/orch/ephemeral-artifact-purge` → 5 arquivos / 15 testes, 0
  falhas (worktree-manager e ephemeral-artifact-purge intocados, rodados
  para regressão).
