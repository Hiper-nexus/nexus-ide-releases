# F-654 — No Windows nenhuma worktree gerenciada nascia: toda aba nova do "+" falhava ao criar a pasta

## F-654 | categoria: funcional | severidade: alta | status: corrigido
- Tela/fluxo: Windows, 0.76.104+ (F-162). Abrir uma aba nova pelo "+", "Montar meus terminais" ou o wizard; também escritor isolado (`nexus_pane_spawn({ isolatedWriter: true })`), missão planejada e candidato da fila de merge.
- Arquivo:linha: `src/main/runtime/worktree-manager.ts` (caminho `<runtime>\worktrees\project-<64>\checkout-<64>\task-<64>`), `src/main/runtime/merge-queue.ts` (`merge-candidates\scope-<64>\candidate-<64>`), com validação por igualdade exata em `worktree-state.ts` e `sqlite-workflow-state-stores.ts`.
- Passos: 1) Windows, projeto Git com commit. 2) Abrir aba nova. 3) O Main chama `git worktree add` para a pasta da aba.
- Esperado: a aba ganha a própria worktree, como no macOS.
- Observado: `fatal: '$GIT_DIR' too big`. O Git para Windows exige `<worktree>\.git` com no máximo PATH_MAX - 40 = 220 caracteres (`setup.c`), ou seja, worktree com até 215; `core.longpaths` não levanta esse teto. Só o diretório de runtime do checkout (`%APPDATA%\NexusIDE\project-runtime\projects\project-<64>\checkout-<64>`) já tem ~219 caracteres, e o caminho completo da worktree ~440. Medido neste PC com git 2.55.0.windows.3: 214 aceito, 216 recusado.
- Evidencia: a comparação 0.76.102 × 0.76.105 no Windows trouxe 13 testes novos falhando, todos do F-162 (`pane-space-worktree`, `mission-execution-scope`, conclusão pela aba, push do branch da aba). Um diagnóstico com git real mostrou o `'$GIT_DIR' too big`.
- (resolvedor) Correcao: `managed-worktree-layout.ts` é a única fonte do caminho físico. No win32 as worktrees moram em `<project-runtime>\wt\<checkout16>\t-<task24>` e os candidatos em `<project-runtime>\mc\<scope16>\c-<cand24>` (~110 caracteres em produção), derivados dos mesmos ids; macOS e Linux mantêm o layout histórico byte a byte. Criação, validação do estado (que no win32 aceita também o caminho antigo, para registros que só falharam), recuperação de runtime relocado e fila de merge derivam do mesmo módulo; o registry passa as raízes curtas. Testes: `managed-worktree-layout.test.ts` (layout POSIX inalterado; caminho de produção do Windows abaixo do teto, o antigo acima), e os 13 testes do F-162 passam no Windows. Os testes de aba que adulteram o `.git` (oculto no Windows, 'w' dá EPERM) passam a reescrevê-lo com 'r+', e as pastas temporárias vêm de `realpathSync.native`.
- Limite conhecido: projeto aberto por grafia não canônica (caixa diferente ou nome curto 8.3, aceita pela identidade desde o F-648) ainda não cria worktree — `readRepositorySnapshot` e a checagem da raiz Git da worktree comparam por string com a grafia do disco. Canonizar a raiz na origem muda a identidade de checkouts em unidade de rede mapeada; fica para um item próprio.
