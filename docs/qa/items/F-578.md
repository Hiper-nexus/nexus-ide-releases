# F-578 — Pane Claude fica "carregando" para sempre: ~500 MB de MCPs npx re-baixados por pane (cache dentro do HOME descartável)

## F-578 | categoria: performance | severidade: alta | status: corrigido

- Tela/fluxo: qualquer pane da família Claude aberto pela mão do operador —
  o pane nasce com HOME efêmero e fica minutos em tela preta/spinner.
- Arquivo:linha: `src/main/orch/mcp-server.ts` `prepareAgentSpawnDecoration`
  (HOME efêmero sem redirecionamento de cache de pacotes).
- Passos: 1) abrir um pane Claude; 2) observar a tela preta por ~30-60s+;
  3) fechar e reabrir — o mesmo tempo de espera se repete em CADA pane.
- Esperado: boot na casa dos segundos depois do primeiro pane, como num
  terminal comum onde o cache de pacotes é quente.
- Observado: todo pane re-baixa os servidores MCP `npx`/`uvx` do perfil
  herdado do operador (~16 servidores do `.nexus/mcp-hub.json` +
  conectores da conta) — medido **~475 MB em <1 min** dentro do overlay
  (`~/.nexus/ephemeral/<tok>/.npm`, `.cache/uv`), com o processo principal
  a ~99% de CPU em callbacks de fs durante o spawn. "Tudo que faço fica
  carregando": o app inteiro engasga junto.
- Causa (reproduzida nesta máquina, 17/09): gerentes de pacote resolvem o
  cache a partir do `$HOME` (`~/.npm`, `~/.cache/uv`). Como o HOME do pane
  é descartável, o cache morre no teardown — cold-cache eterno por pane.
  Reprodução fiel com PTY real (`script`): o claude 2.1.273 renderiza a
  TUI sozinho, mas só depois de ~30s de download dos MCPs; sem eles, ~2s.
  O bug de auth do F-575 já estava resolvido no mesmo pane observado
  (`auth status` → `loggedIn: true` com o keychain linkado) — o que o
  usuário via como "travado" era este segundo problema.
- Correção (`mcp-server.ts`): para panes da família Claude com HOME
  efêmero, o spawn agora aponta os caches de pacote para uma raiz durável
  **por adapter** — `<userData>/provider-cache/<adapter.id>/{npm,xdg,uv}`
  via `npm_config_cache`, `XDG_CACHE_HOME` e `UV_CACHE_DIR`. O download
  acontece uma vez por máquina; panes seguintes saem a quente. Escopo por
  `adapter.id` preserva o isolamento: um pane third-party (GLM/LongCat)
  nunca escreve no cache que a toolchain do pane nativo executa.
- Limites deliberados: só o caminho `usesClaudeHomeLayout` ganha a raiz —
  os outros adapters já isolam seus próprios homes duráveis
  (`provider-state-env.ts`); caches de log do próprio CLI
  (`~/Library/Caches/claude-cli-nodejs`) continuam descartáveis.
- Evidência: teste novo em `mcp-server-governed-profile.test.ts` (2 casos:
  claude e glm com raízes distintas e fora do HOME), 28/28 no arquivo;
  `npx cowsay` com o env aponta para a raiz durável e o segundo run sai em
  0.77s vs 2.8s a frio. `npm run typecheck` limpo.
