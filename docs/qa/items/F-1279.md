# F-1279 — Limite da API do GitHub virava erro vermelho citando o slug legado

## F-1279 | categoria: funcional | severidade: media | status: corrigido
- Tela/fluxo: checagem de atualização pelo espelho público (`api.github.com`, anônimo). É o caminho do macOS sem `gh` e do Linux manual/portátil.
- Arquivo:linha (antes):
  - `src/main/updater.ts:213-215`: `fetchPublicJson` tratava 403/429 como erro qualquer, sem ler `X-RateLimit-Remaining` nem `Retry-After`.
  - `:854` e `:896-898`: a mensagem usava `errors.at(-1)` / `publicErrors.at(-1)`, ou seja, sempre o último slug tentado. Pela ordem de `src/main/update-repos.ts:22-25`, esse é o legado `cleofasvolarehost/nexus-ide-releases`.
- Relacionado a F-1278 (mesmo caminho de erro). Achado da revisão sênior do updater.
- Passos:
  1. Esgotar a cota anônima da API (60 req/h por IP, comum em rede compartilhada) ou receber 429 com `Retry-After`.
  2. Abrir o app ou clicar em "Verificar agora".
- Esperado: limite da API não é falha de atualização. O app não sabe nada novo, então mantém o que mostrava, registra no `update.log` e não insiste no outro slug, que divide a mesma cota.
- Observado:
  - a fase ia para `error` em vermelho, e uma oferta `available` já mostrada sumia;
  - o slug legado era consultado logo em seguida, gastando mais uma requisição da cota;
  - a mensagem citava `cleofasvolarehost/nexus-ide-releases`, que não é a origem real.
- Evidencia (RED, fonte anterior), em `updater.test.ts`:
  - "F-1279: cota da API pública esgotada…" (403 + `x-ratelimit-remaining: 0`) falha com `expected 'error' not to be 'error'`.
  - "F-1279: 429 com Retry-After mantém a oferta…" (Linux manual) recebe `phase: 'error'` e `error: "checagem falhou: cleofasvolarehost/nexus-ide-releases: releases públicos: HTTP 429"`, no lugar de `available`.
  - "F-1279: falha genérica dos dois espelhos cita o canônico…" falha com `expected 'checagem falhou: cleofasvolarehost/ne…' to contain 'Hiper-nexus/nexus-ide-releases'`.
- (resolvedor) Correcao:
  - Causa: o cliente da API pública não distinguia "cota esgotada" de "falha". O laço de slugs seguia tentando e reportava o último erro, não o primeiro.
  - `updater.ts`:
    - `fetchPublicJson` lança `PublicApiRateLimited` quando vem 403/429 com `x-ratelimit-remaining: 0` ou com `Retry-After`. Os demais 403/429 continuam como erro comum.
    - `loadPublicReleaseJson` e `loadReleaseJson` param no primeiro slug limitado.
    - A mensagem de erro genérica passa a usar o primeiro erro, que é o do espelho canônico.
    - `performCheck` e `performManualCheck` guardam fase e erro de antes do `checking`. Em limite de API, `keepStateWhenRateLimited` restaura os dois, grava `checkedAt` (F-1278) e loga `check:rate-limited` no `update.log`.
  - Testes novos em `updater.test.ts`:
    - macOS, 403 + `x-ratelimit-remaining: 0`: a fase fica `idle`, sem erro, com `checkedAt`; `fetch` é chamado uma vez; o log registra o limite.
    - Linux manual, 429 + `Retry-After` depois de uma checagem com oferta: a oferta `available` continua e o slug legado não é consultado.
    - 503 nos dois espelhos: o erro cita `Hiper-nexus/nexus-ide-releases`.
- Validacao: `vitest run` dos 6 arquivos do updater (`updater`, `update-source`, `updater-download`, `updater-feed`, `updater-mixed-platform-releases`, `linux-self-update`): 107 testes passaram. `tsc --noEmit` terminou com 0.
