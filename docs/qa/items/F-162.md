# F-162 — Abas independentes compartilham arquivos e branch

## F-162 | categoria: funcional | severidade: alta | status: corrigido
- Tela/fluxo: nova aba pelo botão +, Montar meus terminais e nova missão pelo wizard.
- Arquivos: `src/main/pty/pane-space-worktree.ts`, `src/main/pty/pty-ipc.ts`, `src/renderer/state/layout-store.ts`, `src/main/orch/tools-panes.ts`.
- Passos: abrir duas abas no mesmo projeto; editar ou trocar a branch numa delas; consultar os arquivos na outra.
- Esperado: cada nova aba tem pasta e branch próprias; panes dentro da mesma aba compartilham essa pasta. O operador aprovou essa política em 26/09/2026.
- Observado: `spaceId` separava só a apresentação; todo spawn herdava o cwd principal. Evidência de campo e causa do diff enganoso em F-161.
- Correcao: novas abas recebem `isolateSpace`; Main resolve a raiz autorizada e aloca uma worktree durável via WorktreeManager. Criação simultânea na mesma aba compartilha uma única reserva. O caminho efetivo volta ao layout, persiste e é reutilizado no resume. Helpers herdam o executionScope do pai; promoção para missão grava o mesmo escopo. Writers de abas distintas não disputam a trava de um mesmo checkout físico.
- Preservação: abas antigas não migram; a base das novas é HEAD, sem copiar WIP; fechar pane/aba não apaga worktree nem branch. Worktree ausente/substituída ou troca de workspace durante criação recusa o spawn, sem fallback para a pasta compartilhada. Projetos sem Git/commit precisam continuar na aba existente ou inicializar seu repositório antes de criar uma aba isolada.
- Limite: worktree separa arquivos/HEAD/index, não é sandbox das ferramentas nativas. O banco de objetos e refs Git continua compartilhado, como em toda worktree. Não há merge automático.
- Evidencia: teste com Git real cobre duas abas simultâneas, mesma aba com dois spawns, WIP principal preservado, branches distintas, restart, troca da branch principal e substituição por symlink. Testes IPC cobrem shell/agente e mudança de autoridade durante await.
- Missões: `workspaceBinding` é emitido pelo Main na preparação e entra no hash da review. O start materializa a pasta antes do despacho; retomada resolve o registro existente. Adoção é revista antes do start e conserva a aba do pane escolhido, inclusive pane legado no checkout principal. Contratos sem binding não migram; o store recusa trocar/remover o vínculo.
- Execução: `mission-execution-scope.ts` separa a pasta física do escopo do banco. Primeira onda, respawn, reviewers, watchdog de HEAD, coleta de arquivos, scanner, sensores mecânicos, fingerprints, gate de artefatos, Pet Studio, abertura da entrega e push usam a pasta da missão. Hubs MCP e selos de anexos continuam sendo consultados no escopo de coordenação; grants permanecem os existentes.
- Entrega: checkout novo altera o mtime de todos os arquivos. Missões em aba usam o SHA-base durável para reconhecer alterações Git, sem contar esses mtimes como trabalho entregue. Push sem upstream nomeia explicitamente a branch atual da aba; destino de branch divergente é recusado.
- Limite avançado: PREVC que altera contexto, sensores do workflow congelado, criação de worktree de tarefa e `isolatedWriter` são recusados explicitamente nas abas isoladas; a mensagem aponta os panes da aba e a revisão automática. O fluxo standard/free do wizard continua operante. Esses caminhos antigos permanecem disponíveis nos escopos legados; nenhum deles pode cair silenciosamente no main.
- Evidência adicional: teste com Git real percorre prepare → start → primeira apresentação → Retomar → pasta removida; primeira onda persiste o executionScope correto. Testes da conclusão real usam versões opostas em main/aba e comprovam que o scanner e o gate de artefatos observam a aba. Teste de push confere cwd/ref sem executar publicação real.
- QA visual/E2E com agentes reais e gate empacotado ficam para a validação final do candidato pelo coordenador; não houve release neste lote.
- Revisão Claude Opus 5.5 (CLI, somente leitura): varredura de PTYs aposentados agora recebe `record.worktreePath`, nunca o checkout coordenador; preparação de reversibilidade e coleta de arquivos do handoff resolvem a mesma pasta física do comando; missão legada explícita usa sua própria raiz, não a aba do chamador. Grant legado que não pode cumprir isolamento é recusado. Pasta ausente recebe orientação para restaurar a worktree ou abrir nova aba, preservando branch e registros antigos. Testes focados adicionais: 256 aprovados antes da última regressão de missão-alvo.

- Validação local (26/09): rodada ampliada de 55 arquivos, 1.442 testes aprovados e 2 skips preexistentes; após os últimos guards, 7 arquivos/114 testes aprovados. `tsc --noEmit`, `npm run security:renderer-sinks` (0 sinks) e `git diff --check` passaram. Vitest executado pelo Node 22.23.2, sem rebuild de módulos nativos.
