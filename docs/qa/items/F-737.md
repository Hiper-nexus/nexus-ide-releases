# F-737 — Texto dos hooks chegava corrompido aos agentes no Windows

## F-737 | categoria: funcional | severidade: media | status: corrigido
- Tela/fluxo: hooks aditivos no Windows (`/hook/delegate`, `/hook/triage`, `/hook/integration`, `/hook/regression`). Atinge a doutrina do Maestro (F-701/F-708), que no Codex só chega por esse canal, a triagem de Bash e os avisos dos portões.
- Arquivo:linha: `src/main/orch/hook-http.ts` (`sendHookJson` e o 400 de `handleHookJsonPost`), `src/main/orch/hook-status-endpoint.ts`.
- Passos: 1) Maestro Codex ou Claude no Windows. 2) Um prompt passa pelo hook `UserPromptSubmit` e o Nexus responde com `additionalContext` em português.
- Esperado: o agente recebe "VOCÊ É O MAESTRO DESTA MISSÃO (vale a sessão…".
- Observado (auditoria de 02/10, rollouts do Codex): "VOCÃ Ã O MAESTRO DESTA MISSÃO (vale a sessÃ£o…". O mesmo acontecia com "missÃ£o" no Maestro Claude.
- Evidencia: no Windows o hook roda em PowerShell 5.1 e lê `$response.Content` do `Invoke-WebRequest`. O servidor respondia `content-type: application/json` sem charset, e nesse caso o PowerShell 5.1 decodifica como ISO-8859-1. Reproduzido nesta máquina com um servidor local e o mesmo JSON:
  - sem charset → `VOCÃ Ã O MAESTRO DESTA MISSÃO (vale a sessÃ£o)`, igual ao texto dos rollouts;
  - com `charset=utf-8` → texto correto.
  - O prelúdio dos hooks já põe o console em UTF-8; a quebra estava só na decodificação da resposta.
- Causa: resposta JSON dos hooks sem `charset=utf-8`.
- (resolvedor) Correcao:
  - `HOOK_JSON_CONTENT_TYPE = 'application/json; charset=utf-8'` em toda resposta dos hooks aditivos (inclusive o 400) e do `/hook/status`.
  - A mudança é só no servidor: vale também para os panes já abertos, cujo comando de hook não muda.
  - O curl do macOS/Linux repassa os bytes e não é afetado.
  - Teste novo: `hook-http.test.ts`.
