# F-404 — archiveWorktree autorizava remoção com status desconhecido e reportava sucesso falso

## F-404 | categoria: seguranca | severidade: alta | status: corrigido
- Tela/fluxo: ciclo de vida de worktree isolado — verificação de estado limpo antes de
  arquivar/remover. Sem superfície de UI hoje (ver F-405: o módulo não está ligado),
  mas é o caminho que qualquer integração futura vai herdar.
- Arquivo:linha: `src/main/runtime/worktree-lifecycle.ts:63` (catch fail-open em
  `checkWorktreeStatus`) e `src/main/runtime/worktree-lifecycle.ts:157` (guarda de
  falha de remoção em `archiveWorktree`).
- Passos: 1) chamar `checkWorktreeStatus()` num worktree onde `git status` falha por
  qualquer motivo que não seja "diretório não existe" — `index.lock` retido por um
  agente concorrente, timeout, permissão, repositório corrompido; 2) observar o
  retorno; 3) chamar `archiveWorktree()` sem `force`.
- Esperado: um estado que não pôde ser verificado nunca autoriza uma operação
  destrutiva. O projeto já aplica essa regra em outro lugar — `EndpointClaim.kind` em
  `src/main/pty-daemon/endpoint-ownership.ts` é `'claimed' | 'incumbent-live' |
  'unverifiable'`, e `docs/architecture/pty-daemon-spec.md` escreve "nunca colapsar
  'não sei' em 'morto'".
- Observado: dois defeitos distintos na mesma função.
  1. **Fail-open.** O `catch` de `checkWorktreeStatus` devolvia
     `{ isClean: true, dirtyFiles: [] }` para *qualquer* exceção, com o comentário
     "consider clean to allow prune". O comentário justificava um caso (diretório já
     removido) mas a guarda cobria todos. Um `git status` que falha por contenção de
     lock — cenário real quando vários agentes operam no mesmo checkout — era lido
     como "worktree limpo", liberando `git worktree remove` e a deleção de branch
     sobre mudanças não commitadas.
  2. **Sucesso falso.** A guarda da falha de remoção era
     `if (!options.force && status.dirtyFiles.length > 0) throw err`, que não
     implementa a intenção declarada no próprio comentário ("if removal failed because
     the worktree directory is already deleted/missing, continue to prune"). Para um
     worktree limpo cuja remoção falhou, `dirtyFiles.length` é 0, a exceção era
     engolida e a função retornava `ok: true` sobre um worktree que continua no
     disco. `dirtyFiles` não tem relação com "diretório ausente".
- Evidencia: o teste anterior não pegava nenhum dos dois porque o mock de `GitRunner`
  nunca lançava exceção e os caminhos eram fabricados (`/tmp/wt`), então o `catch` e a
  guarda de remoção nunca eram exercidos. `npx vitest run
  src/main/runtime/worktree-lifecycle.test.ts` na versão antiga: 8 testes verdes com
  ambos os defeitos presentes.
- Correcao: `WorktreeStatusCheck.isClean: boolean` substituído por
  `state: 'clean' | 'dirty' | 'missing' | 'unverifiable'` mais `reason?`.
  `checkWorktreeStatus` agora testa `existsSync(worktreePath)` **antes** de chamar git
  — diretório ausente é `missing` (fato conhecido, prune é a ação correta, nenhum dado
  em risco) — e qualquer exceção do git vira `unverifiable` com a mensagem preservada.
  `archiveWorktree` recusa `dirty` **e** `unverifiable` sem `force`, lançando o novo
  `WorktreeStatusUnknownError` no segundo caso. A guarda de remoção passou a
  `if (status.state !== 'missing') throw err`, que é a intenção que o comentário
  descrevia. Testes reescritos com diretórios temporários reais
  (`mkdtempSync`) para que os três estados não-missing alcancem o git de fato, mais
  três casos novos: `unverifiable` recusa sem `force`, `force` o sobrescreve, e falha
  de remoção sobre worktree existente propaga em vez de retornar `ok: true`.
- Validacao: `npx vitest run src/main/runtime/worktree-lifecycle.test.ts` 13/13
  verdes; suíte adjacente (worktree-metadata, mission-worktree-orchestrator,
  worktree-branch-slug, ui-theme) 49/49 verdes.
  `npm run security:renderer-sinks` 0 sinks. `grep -rn "isClean" src/` vazio — nenhum
  consumidor do campo removido. `npx tsc --noEmit` não reporta erro em nenhum arquivo
  deste finding; o typecheck do repositório está vermelho em
  `src/main/orch/mission-independent-review-gate.test.ts` por trabalho não commitado de
  outra sessão, sem relação com este arquivo.
- Limites: a correção não torna o caminho seguro para ser ligado — ver F-405. E o
  comportamento `force: true` continua intencionalmente destrutivo.
