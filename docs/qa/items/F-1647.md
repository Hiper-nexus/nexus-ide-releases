# F-1647 — Instalador POSIX perde o PATH que localizou o runner

## F-1647 | categoria: funcional | severidade: alta | status: corrigido
- Tela/fluxo: Providers, instalar/atualizar Codex, MiniMax, MiMo Code e Muse em Macs com ou sem Homebrew.
- Arquivo:linha: `src/main/path-resolver.ts:148`, `src/main/persistence/provider-config-store.ts:3482`, `src/main/persistence/provider-config-store.ts:3957` (base `3d0cae3c8`).
- Passos: abrir o app pelo Finder com PATH mínimo e npm encontrado somente pelos fallbacks; tentar instalar uma CLI. No Intel, repetir com Node 22 keg-only somente em `/usr/local/opt/node@22/bin`.
- Esperado: descoberta consistente de Node/npm Intel e ARM e subprocesso capaz de encontrar o Node, preservando a prioridade da escolha explícita do usuário.
- Observado: o fallback de Node 22 contemplava somente o prefixo ARM. Encontrar npm por fallback não transportava seu `effectivePath` ao filho: o shebang `/usr/bin/env node` falhava com `node: No such file or directory`. A seleção manual também podia manter o PATH antigo sem reler o login shell.
- Evidencia: testes de filesystem virtual e executor simulado, usando os resolvedores reais de PATH. A causa específica no Mac do relato ainda depende do erro e da arquitetura observados; nenhum install nativo macOS foi executado.

## Correção implementada

- Adicionado `/usr/local/opt/node@22/bin` à lista existente de `commonCliBinDirs`; sem novo resolver, dependência, download ou alteração da prioridade dos PATHs explícitos.
- Regressão em `path-resolver.test.ts` exercita `buildEffectivePath` e `resolveCliBinary` com filesystem virtual: encontra Node/npm tanto no prefixo ARM quanto Intel sem PATH de login, e não anuncia o keg ausente. Não cria diretórios de sistema nem executa Node/npm do Mac.
- RED: ARM passou e Intel falhou por resolução ausente antes da alteração. GREEN no Windows/Node 22.23.2: `node node_modules/vitest/vitest.mjs run src/main/path-resolver.test.ts src/main/path-resolver-boot.test.ts` — 30 passados, 22 skipped (inclui boot POSIX). Não constitui teste nativo de instalação macOS.
- Após handoff explícito do owner de F-1646, `resolveInstallRunner` conserva o `CliBinaryResolution` existente; `resolveRunnerPath` mantém sua API. O filho POSIX recebe o PATH herdado seguido dos diretórios resolvidos, deduplicados: um Node escolhido no PATH continua na frente. Env fixo da receita é mesclado sobre esse ambiente, sem descartá-lo nem alterar o ambiente do Main.
- Seleção manual e provisionamento inicial chamam `refreshUserPath` antes de selecionar receita. O updater automático já chega por `rescanAdapterBinaries`, que faz essa atualização. Preparação/execução continuam usando a identidade canônica do adapter entregue pelo F-1646.
- `runPosixScriptRecipe` executa bash resolvido por caminho absoluto e preserva `env?: Readonly<Record<string, string>>`. Teste prova `MUSE_LOGIN=0` e `MUSE_NO_MODIFY_PATH=1` no filho, com o PATH resolvido, sem mudar `MUSE_LOGIN` no Main. Receita oficial Muse pertence à entrega F-1648.
- TDD do ambiente: 4 RED (npm Intel/ARM, script POSIX, seleção manual após login PATH) + 2 controles de Node explícito já verdes → 6 GREEN. Regressões F-1646: 4 GREEN preservados.
- Rodada integrada: `node node_modules/vitest/vitest.mjs run src/main/persistence/provider-config-spawn.test.ts src/main/adapters/windows-npm-shim.test.ts src/main/adapters/cli-install-recipes.test.ts src/main/adapters/cli-auto-update.test.ts src/main/path-resolver.test.ts src/main/path-resolver-boot.test.ts --maxWorkers=1 --reporter=dot` — 306 passados, 23 skipped, exit 0. Fixtures Windows simulam o ambiente macOS; não são instalação nativa nem prova de disponibilidade de provider.
- Oxlint focado, `lint:main-sync`, `security:renderer-sinks` e `git diff --check`: exit 0. `node node_modules/typescript/bin/tsc --noEmit --incremental false`: exit 0 nesta rodada. A falha transitória anterior de imports durante o WIP de F-1646 não é usada como resultado atual.
- Não há bootstrap, instalação global, mudança em receita/versão ou alteração de auth nesta entrega. Corrigido com evidência de fixtures; não marcar como verificado em hardware macOS.

## Reuso identificado para a integração

- `path-resolver.ts`: `refreshUserPath`, `buildEffectivePath`, `resolveCliBinary` e `CliBinaryResolution.effectivePath` reutilizados; nenhum resolvedor paralelo foi criado.
- `video/video-engine.ts`: `resolveNodeRuntime` sonda versão/binário reais e `npmCliCandidates` localiza npm junto desse Node. É detecção, não bootstrap; a política de HOME/ambiente do motor de vídeo não deve ser aplicada às CLIs por acidente.
- `pty/node-version-path.ts`: `candidateNodeBinDirs`/`resolveInstalledNodeBin` já conhecem Intel/ARM/nvm, mas apenas encontram instalações existentes.
- `adapters/cli-install-recipes.ts`: `npmPrefixRecipe` preserva o prefixo de atualização; `adapters/codex-windows-prefix.ts` trata somente a exceção Windows. Não há helper genérico de prefixo npm gravável para primeira instalação.
- Não localizado provisionador Node no produto. O download com checksum em `scripts/linux-release-container.sh` é exclusivo da imagem Linux de build; não é bootstrap desktop reutilizável.
- Próximo preflight proposto, ainda sem implementação: executar a sonda de Node com o MESMO env da invocação, localizar/verificar npm correspondente, consultar `npm prefix -g` sem instalar e testar acesso ao destino. Retornar motivo estruturado antes de qualquer escrita para runtime ausente/incompatível ou prefixo não gravável. Não fixar Node 22 como requisito universal nem usar Electron como substituto implícito. A preparação de runtime ausente requer desenho separado; sem presunção de Homebrew.
- Contexto histórico da base: sem npm/brew, os quatro providers relatados eram bloqueados pelo seletor. Isso não caracteriza a receita Muse nova de F-1648 nem prova a configuração do Mac do relato. Captura de stdout e bootstrap permanecem fora deste recorte.
