# F-1288 — nexus_handoff_submit estourava o prazo do cliente MCP no portão de regressão e o reenvio duplicava o handoff

## F-1288 | categoria: infraestrutura | severidade: média | status: corrigido
- Tela/fluxo: `nexus_handoff_submit` de CLI cujo cliente MCP derruba a chamada aos 60 s.
- Arquivo:linha (antes): `src/main/regression-gate/regression-gate-handoff.ts` — `HANDOFF_REGRESSION_BUDGET_MS = 100_000`, afinado só para o `tool_timeout_sec=120` do Codex.
- Passos:
  1. Worker chama `nexus_handoff_submit` com testes impactados e máquina sob carga.
  2. O portão de regressão roda sincronamente antes da resposta e vence o próprio orçamento (100 s) com "Verificação excedeu o prazo… 0 rodaram, 10 não — resultado NÃO verificado".
  3. O cliente MCP já tinha desistido aos 60 s; o agente reenvia pelo shim do shell.
- Esperado: a tool responde DENTRO do prazo do cliente; um reenvio idêntico não duplica o handoff.
- Observado: o submit respondia só depois de 100 s — após o timeout do cliente. O reenvio via shim produzia o MESMO handoff duas vezes no Maestro.
- Evidencia (RED, fonte anterior): `regression-gate.test.ts` › "F-1288: portão lento corta no próprio orçamento, que cabe no prazo do cliente MCP (60 s)" falha com `expected 100000 to be less than 50000`.
- (resolvedor) Correcao:
  - Causa: orçamento total do portão (100 s) acima do MENOR prazo de cliente que chama o submit (60 s do MCP de algumas CLIs).
  - `regression-gate-handoff.ts`: `HANDOFF_REGRESSION_BUDGET_MS = 45_000`. Escolhido cortar o orçamento (opção 2) em vez de responder cedo com veredito posterior (opção 1): os testes do portão pinam a devolução SÍNCRONA (`retry` lança para o agente, 2 devoluções/sessão → `exhausted` = blocked, nunca success) — resposta antecipada quebraria essa semântica. 45 s deixam ~15 s de folga para o que roda depois do gate (revisão Jev, persistência) e seguem abaixo do `tool_timeout_sec=120` do Codex.
  - Vencido, o gate corta como antes: `unavailable` → aceito e NÃO verificado (fail-open honesto, invariante preservado).
  - Reenvio idêntico: o dedupe por `rawPayloadSha256` no handoff-store já cobria (teste existente "binds replay identity to the full raw payload before compaction" em `tools-domain-handoff.test.ts`) — nenhuma mudança necessária.
- Validacao (worktree, node@22): `regression-gate.test.ts` 75/75 (inclui os casos retry/exhausted/unavailable intactos); `handoff-regression-gate.integration.test.ts` passou; `tsc --noEmit` 0.
- Revisão de ponta (Fable, 12/10), limite aceito: 45 s às vezes cortam suíte grande e o resultado vira "aceito, não verificado" (prefixo visível no resumo, fail-open honesto, nunca falso vermelho). Falta um alarme de frequência por sessão; fica para a próxima onda.
- 2ª revisão de ponta (Fable, 12/10): aceito com ressalva. O alarme de frequência do corte de 45 s entra na próxima onda, porque regressão é a dor nº 1 do operador.
