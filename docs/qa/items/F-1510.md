# F-1510 — Windows: `git worktree prune` do Nexus nunca roda (`C:/…` contra `C:\…`)

## F-1510 | categoria: funcional | severidade: media | status: corrigido
- Renumerado na integração com a origin (0.76.252): este achado era o F-1456 da frente de squads (nunca publicado) e virou F-1510 para não colidir com a numeração que a origin publicou (F-1436..F-1451).
- Tela/fluxo: coleta de worktrees de writers parados → `WorktreeRuntimeRegistry.collectAgedPaneWriterWorktrees` → `WorktreeManager.pruneManagedWorktrees` (`src/main/runtime/worktree-manager.ts`).
- Arquivo:linha: `src/main/runtime/worktree-manager.ts:1489-1492` (antes) — `new Set(records.map(r => r.worktreePath))` + `known.has(worktree.path)`, com `worktree.path` vindo de `parseWorktreeList` (`:150-162`).
- Passos: 1) No Windows, um writer de pane do Nexus deixa a worktree registrada no Git e a pasta some (fechamento, limpeza manual). 2) A coleta periódica roda.
- Esperado: o prune tudo-ou-nada roda quando todo `prunable` é worktree do Nexus, liberando a branch para o `branch -d` seguinte.
- Observado: sempre `{ skipped: 'prunable-not-nexus' }`; as entradas `prunable` do Nexus acumulam no repositório do operador e as branches delas não saem.
- Causa raiz: o `git worktree list --porcelain` do Windows imprime `C:/Users/…/wt/…` e o registro guarda `C:\Users\…\wt\…`; a comparação era de string exata. O comparador certo (`areWorktreePathsEqual`, `worktree-path-compare.ts`) já é o da remoção (`findRegisteredDeletableWorktree`).
- Correcao: o conjunto de conhecidos é comparado com `areWorktreePathsEqual` (barras e caixa do Windows; POSIX segue normalizado como antes). O prune continua tudo-ou-nada: worktree adotada (F-1429) e worktree manual do operador seguem impedindo o prune. Commit: ver `git log --grep F-1510`.
- Evidencia:
  - RED (código antigo): `worktree-manager.test.ts` "F-1510: prune reconhece a worktree do Nexus na grafia do Git" → `expected { skipped: 'prunable-not-nexus' } to deeply equal { pruned: 1 }`. O teste já existente `worktree-runtime-registry.test.ts` "faz prune só quando todo prunable é registro Nexus atual" falhava no Windows com a mesma diferença (`:1555`).
  - GREEN: o teste novo passa; no teste do registry a asserção do prune (`:1555`) passa e ele segue até `:1570`, onde para numa limitação de ambiente do Windows do próprio teste (`git worktree add` com caminho de 3×64 caracteres: `fatal: '$GIT_DIR' too big`). Arquivo `worktree-manager.test.ts` inteiro: 61 passaram; as 3 falhas restantes são as mesmas da base (F-980; F-1429 parte 2 (a); "prune não esquece…", que falha na comparação literal `worktree C:\…` × `worktree C:/…` do próprio teste depois de confirmar o `skipped`).
