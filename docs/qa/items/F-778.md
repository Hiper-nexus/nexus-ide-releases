# F-778 — Portão de integração F-234 barra sincronização fast-forward com upstream e omite merge com destino implícito

## F-778 | categoria: seguranca | severidade: alta | status: corrigido
- Tela/fluxo: PreToolUse/Bash hook em `/hook/integration` (portão de integração F-234).
- Arquivo:linha: `src/main/orch/hook-integration-endpoint.ts:27`
- Passos:
  1) Falso positivo: no terminal ou hook, com branch local `main` rastreando `origin/main` (0 commits à frente), executar `git merge --ff-only origin/main`.
  2) Falso negativo: no branch `main`, executar `git merge feature` sem veredito de modelo de ponta.
- Esperado:
  1) `git merge --ff-only origin/main` comprovado como sincronização de upstream (HEAD ancestral do alvo, zero commits exclusivos locais) deve passar sem acionar o portão de revisão deliberado.
  2) `git merge feature` estando no `main`/`master` deve ser detectado como integração real no branch protegido e bloqueado pelo portão (`review_required`).
- Observado:
  1) Falso positivo (trace 2026-10-03T13:47:38Z): `git merge --ff-only origin/main` com 0 commits à frente foi bloqueado com `decision: 'block'` ("árvore suja — commite e peça o veredito do HEAD").
  2) Falso negativo: `git merge feature` com branch atual sendo `main` retornou `{}` (hit: false) porque a regex `INTEGRATION_SEGMENT` exigia "main" explícito no argv.
- Evidencia:
  - Trace `main.trace.ndjson` (2026-10-03T13:47:38.055Z).
  - Reprodução em teste com repositório real em `hook-integration-endpoint.test.ts`:
    - `igual ao upstream com --ff-only passa sem exigir veredito` falhou com `decision: block`.
    - `atrás do upstream com --ff-only passa sem exigir veredito` falhou com `decision: block`.
    - `git merge feature estando no main exige gate` falhou com `{}`.
    - `detecta direção no integrationCommandHit pelo branch atual do cwd` falhou com `false`.
- (resolvedor) Correcao:
  - Implementada `isExemptFastForwardSync` em `src/main/orch/hook-integration-endpoint.ts`: isenta exclusivamente quando o comando for `--ff-only` sem composição ambígua, o alvo for exatamente o ref remote-tracking upstream da branch atual (`main`/`master`), os SHAs forem revalidados e o Git comprovar por `merge-base --is-ancestor` e `rev-list <target>..HEAD --count` que HEAD é ancestral do alvo (zero commits locais exclusivos). Qualquer divergência, commits locais à frente, alvo diferente do upstream ou composição com push/navegação mantém o portão deliberado.
  - Implementada detecção de direção em `integrationCommandHit`: quando o cwd aponta para repo em branch `main`/`master`, qualquer `git merge` para dentro dela é classificado como tentativa de integração.
  - Testes em repositório Git temporário real cobrindo: igual/atrás do upstream com `--ff-only` (passa), à frente ou divergente (gate), branch feature (gate), alvo diferente do upstream (gate), mistura com push no mesmo comando (gate), merge de feature no main (gate), e direção detectada em `integrationCommandHit`.
- (Maestro, revisão da integração) Ajuste de desempenho: a primeira versão perguntava a branch ao git (`spawnSync` no Main) em TODO Bash de pane de missão, antes de olhar o comando. Com ~16 panes isso soma processos git síncronos no thread principal (o mesmo Main congelou 11 min nesta missão sob carga de hooks). Agora `integrationCommandHit` só consulta a branch quando o segmento é um `git merge`; teste novo com GitRunner espião prova que `ls`/`git status` não chamam git (falha na primeira versão, passa depois).
