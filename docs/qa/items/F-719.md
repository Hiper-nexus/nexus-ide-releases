# F-719 — Login GitHub/Google na tela de acesso fingia sucesso e engolia a falha

## F-719 | categoria: fluxo | severidade: alta | status: corrigido (app e backend: GitHub e Google)
- Tela/fluxo: tela de acesso ("Seu acesso ao NexusIDE") e Ajustes → Minha conta → "Entrar com GitHub/Google".
- Arquivo:linha: `src/main/auth-client.ts` (`beginLogin`), `src/main/deep-link.ts` (ramo `auth`), `src/renderer/components/settings/AccountSection.tsx` (`startLogin`).
- Passos: 1) Abrir o app sem sessão. 2) Clicar em "Entrar com GitHub". 3) Observar a tela.
- Esperado: a tela diz que está esperando o navegador e, se o servidor recusar ou a troca do código falhar, diz por quê e como seguir.
- Observado: o clique abria o navegador, a tela chamava `refreshAccess()` na hora e liberava o botão, sem nenhum estado de espera. Se o backend recusava, a pessoa via JSON cru numa aba. Se a troca do código falhava depois, só saía `[auth] exchange falhou` no console.
- Evidencia: em 01/10/2026 `GET https://api.nexuside.app/v1/auth/github?app_state=x&code_challenge=y` → HTTP 503 `{"ok":false,"error":"Este login ainda não está disponível."}` (idem Google), com `/health` 200. O servidor no ar não é o `server/` deste repo (mensagens diferentes) e o projeto Railway documentado tem todos os deploys FAILED desde 13/08.
- Causa: `beginLogin` devolvia `{ ok: true }` assim que `shell.openExternal` era chamado; o resultado do deep link nunca chegava ao renderer.
- (resolvedor) Correcao:
  - `beginLogin` consulta o servidor antes de abrir o navegador (`probeLoginEndpoint`, `redirect: 'manual'`, só falha definitiva 4xx/5xx ou rede) e devolve mensagem para a pessoa. O login pendente só nasce depois da checagem.
  - Novo evento `auth:login-result` (Main → renderer) com texto pronto; `finishAuthDeepLink` registra só o código da falha.
  - `useNexusLogin`: estados `opening`, `waiting` (com prazo de 10 min), `failed`; "Abrir de novo" e "Escolher outro método".
  - Tela de acesso redesenhada (`components/access/*`): ação principal por motivo de bloqueio, título por motivo, terminais em linhas.
  - Testes: `auth-client.test.ts`, `auth-deep-link.test.ts`, `auth-login.test.ts`, `use-nexus-login.test.tsx`, `access/*.test.ts(x)`; `AccountSection.test.tsx` e `license-lifecycle.test.tsx` ajustados ao novo comportamento.
- **Backend (corrigido em 01/10/2026):** `api.nexuside.app` é o Worker `~/dev/nexus-cloud-api`, não o `server/` deste repo. Dois defeitos, ambos lá:
  - Sem `GITHUB_OAUTH_ID`/`GITHUB_OAUTH_SECRET` o Worker responde 503 de propósito. OAuth App do GitHub criado e credenciais gravadas.
  - `providerJson` usava `fetch(..., { redirect: 'error' })`, valor que o workerd rejeita (só `follow`/`manual`): toda troca com o provedor falhava com 502 genérico, e os testes passavam por usarem fetch simulado. Trocado por `manual` (3xx continua recusado), com teste que trava o modo e log do motivo para `wrangler tail`.
  - O callback desktop passou a terminar numa página HTML (deep link em botão), e erro virou página legível, com CSP próprio.
- **Teste em dev:** o vault é desligado por padrão em dev (F-105), então a sessão não é gravada (`exchange-storage`). Use `NEXUS_DEV_VAULT=1 npm start` e responda "Sempre Permitir" ao Keychain.
- **Google (corrigido em 01/10/2026):** projeto Google Cloud `NexusIDE`, cliente Web com o callback da API, secret e Client ID no Worker (`auth.google=true`). O app do Google está em modo teste; publicar na tela de consentimento antes de abrir para clientes.
- **Stripe (modo teste):** produto, preço R$ 59,99/mês, portal e webhook provisionados; `billing.available=true`. Falta o ensaio completo e a virada para live (go-live §2.9 a §3).
