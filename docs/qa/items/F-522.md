# F-522 — Primeiro banco de projeto entra em safe-read-only no Windows

## F-522 | categoria: funcional | severidade: alta | status: corrigido
- Tela/fluxo: primeira abertura empacotada no Windows; smoke funcional de
  configurações, layout, telemetria e orquestração.
- Arquivo:linha: `src/main/runtime/project-runtime-migrations.ts:271`
- Passos: 1) gerar o NUPKG Windows x64; 2) extrair e iniciar `nexus-ide.exe`
  com o smoke empacotado; 3) aguardar a primeira abertura do runtime SQLite.
- Esperado: o backup obrigatório é tornado durável e todas as migrações criam
  `workspace_layout`, `usage_events` e os demais schemas antes dos IPCs.
- Observado: havia duas incompatibilidades Windows no backup. `VACUUM INTO`
  recebia um caminho de 312 caracteres sem o namespace Win32 e falhava com
  `SQLITE_CANTOPEN`. Depois de criado, o arquivo era aberto somente para leitura;
  `FlushFileBuffers` exige `GENERIC_WRITE` e falhava com `EPERM`. Ambas entram
  corretamente em `backup_failed`/safe-read-only antes das migrações.
- Evidencia: Actions run 4: renderer montou, seguido de `no such table:
  workspace_layout`, `no such table: usage_events`, runtime safe-read-only e
  `[smoke] functional-failed: settings-ipc`. O probe nativo do run 6 comprovou:
  caminho cru de 312 caracteres → `SQLITE_CANTOPEN`; caminho namespaced →
  `VACUUM` aprovado; `fsync` com `r` → `EPERM`; `fsync` com `r+` → aprovado.
- (resolvedor) Correcao: o construtor SQLite nativo e `VACUUM INTO` recebem
  `path.toNamespacedPath` no Windows, mantendo o caminho canônico humano no
  health/backup e preservando o contrato das factories injetadas. O arquivo de
  backup abre com `r+` antes do fsync, enquanto o fsync best effort do diretório
  preserva o descritor `r` usado no POSIX. Alterados
  `project-runtime-migrations.ts`, teste co-localizado e gate Windows. Validado
  localmente com 40 testes de runtime/layout/gamificação, typecheck e renderer
  sinks. A verificação do finding exige o próximo run no Windows real.
