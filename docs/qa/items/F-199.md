# F-199 — Portão de regressão recusava toda entrega de writer em projeto com a config do Jest fora da raiz

## F-199 | categoria: funcional | severidade: alta | status: corrigido
- Tela/fluxo: `nexus_handoff_submit` de writer (helper que escreve código) numa missão do saasbarbearia; o portão de regressão roda os testes impactados antes de aceitar a entrega.
- Arquivo:linha: `src/main/regression-gate/regression-gate.ts:1268` (`runTests` chama `jest --json --outputFile … --passWithNoTests --runTestsByPath …` sem `--config`); `src/main/regression-gate/regression-gate.ts:1056` (`parseJestLikeReport` conta "Test suite failed to run" como regressão e como teste executado); `src/main/regression-gate/regression-gate.ts:614` (`detectRegressionRunner` só olha dependências).
- Passos: 1) Projeto com a config do Jest em `tests/jest.config.js` (transform `ts-jest`, `rootDir: ".."`) e sem config na raiz; os scripts rodam `jest --config tests/jest.config.js …`. 2) O Maestro abre um writer isolado. 3) O writer entrega.
- Esperado: o portão roda os testes impactados com a config do projeto; problema de invocação vira "não verificado", nunca bloqueio.
- Observado (29/09, missão "Missão · Terminais" do saasbarbearia): os três writers GLM tiveram a entrega recusada duas vezes cada ("devolução 1/2" e "2/2", 13:48–14:47) com "Seu diff quebrou 36/63/69 arquivo(s) de teste impactado(s)". Todas as falhas eram "Test suite failed to run — SyntaxError: <worktree>/tests/api/….test.ts" ou "Jest encountered an unexpected token": sem `--config`, o `ts-jest` não carrega e nenhum teste TypeScript é lido. O próprio writer diagnosticou "as 69 falhas do portão são artefato de invocação, não do diff". Cada writer gastou duas rodadas tentando corrigir falhas que não existiam; o Maestro passou a fazer o trabalho de escrita sozinho.
- Evidencia: `audit_events` do checkout (`nexus_handoff_submit` com `outcome=error`, 6 recusas de 3 sessões) e o relatório do writer `pty-mumyod9n-7`; `package.json` do saasbarbearia (todos os `test:*` passam `--config tests/jest.config.js`).
- Relacionado: F-198, F-373, F-374 (o mesmo fluxo de missão com helpers).
- (resolvedor) Correcao: duas camadas em `regression-gate.ts`. (A) `detectRegressionRunner` ganha `config` (posix, relativa ao pacote): quando o pacote não tem config própria (`jest.config.*`/chave `jest`; `vite.config.*`/`vitest.config.*`), varre `pkg.scripts` e aceita `--config <p>`/`--config=<p>`/`-c <p>` só de comandos do próprio runner (`jest`/`vitest` ou caminho terminado neles), separadores de shell encerram o comando; resolve contra o pacote e só aceita arquivo real dentro do root; a mais usada pelos scripts vence. `runTests` chama `jest --config <cfg> --json …` / `vitest run --config <cfg> --reporter=json …`. `GATE_VERSION` → `regression-gate-v2` (a config entra na identidade do cache). (B) `parseJestLikeReport` separa suítes que não carregaram ("Test suite failed to run" + SyntaxError/unexpected token/import-fora-de-módulo, sem asserção executada) em `loadFailures` — fora de `failures` e de `ran`, com o arquivo acusado extraído da mensagem — regex lazy até a extensão de fonte, aceitando caminhos com espaços (`~/Library/Application Support/…` dos worktrees isolados) e formatos `SyntaxError: <path>: msg` e `Details:\n<path>:linha`. Mensagem sem caminho extraível segue falha (conservador); ofensor provado fora do diff (fora do root, `node_modules/`) vira não-verificado. Na agregação, a falha de carga só conta contra o diff se o arquivo quebrado estiver nele ou se ele tocou config do runner/transform (`*.config.*`, `.babelrc*`, `tsconfig*.json`, `package.json`, ou a descoberta); senão vira aviso "não conseguiu carregar" e a suíte fica não verificada. Testes: `regression-gate.test.ts` (descoberta, `--config` na linha de comando, classificação nos dois sentidos, handoff aceito-não-verificado).
