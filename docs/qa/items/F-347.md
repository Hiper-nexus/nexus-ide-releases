# F-347 — Uma tecla num pane de missão concluída-não-revisada destrói o vínculo pane↔missão

## F-347 | categoria: funcional | severidade: critica | status: corrigido
- Correcao: a rota rápida ganhou as duas guardas que faltavam, extraídas como
  predicado puro `terminalDeadPaneFastPathApplies({link, paneState, missionOwns})`
  em `src/renderer/terminal/mission-owned-pane-policy.ts` (junto com
  `decideTerminalMissionDeadPaneKey`, que é a política irmã), e `terminal-host.ts`
  passou a consultá-lo em vez de testar `terminalLink !== 'live-or-unknown'`
  isoladamente. O predicado devolve `false` quando `missionOwns` é verdadeiro
  (restaurando F-108: done sem carimbo do humano ainda é revisão, o coordenador
  continua dono) e quando `paneState === 'hibernated'` (pane hibernado tem botão
  de acordar e não é estado preso). Nos dois casos a tecla cai na rota antiga,
  `decideExitedPaneKey`, que já tratava corretamente.
  O tipo `TerminalMissionLink` foi movido de `terminal-host.ts` para o módulo de
  política — é tipo de política, e a casa dele é ao lado de `ExitedPaneKeyAction`.
  O propósito da rota rápida foi preservado, não removido: ela continua cobrindo o
  **estado preso** (missão terminal, pane sem posse, estado que a rota antiga
  silenciaria com `'ignore'`), que é o único caso para o qual existe.
- Sete testes novos em `mission-owned-pane-policy.test.ts`, incluindo o caso exato
  do finding (done + worker + `missionOwns: true` → rota rápida **não** se
  aplica), posse de missão respeitada em qualquer `paneState`, hibernado nunca
  convertido em shell, e o estado preso continuando coberto.
- `ignoreMissionOwnership: terminalLink !== 'none'` foi **mantido**: com a rota
  rápida agora gated em `!missionOwns`, quando ela dispara não há posse a
  respeitar, então o flag é redundante mas inofensivo. Mexer nele ampliaria o
  diff sem ganho.
- Validacao: `npx tsc --noEmit` 0 erros; `mission-owned-pane-policy.test.ts` 54
  testes verdes (eram 47); suíte completa → 1283 arquivos / 12755 testes, 0 falhas.

- Tela/fluxo: missão concluída aguardando aprovação do operador → operador abre
  os terminais para ler o que cada worker produziu → clica num pane morto e
  pressiona qualquer tecla.
- Arquivo:linha: `src/renderer/terminal/terminal-host.ts:1283-1302` (o branch
  novo), com `terminalMissionLinkOf` em `:2379-2394`,
  `missionStillOwnsPane` em `:2357-2373`, `reclaimExitedPaneAsShell` em
  `:2448-2453` e `reclaimAsOperatorShell` em `:2462-2467`.
- Passos: 1) deixar uma missão terminar (`status: 'done'`, ainda não aprovada);
  2) abrir os terminais dela para revisar antes de aprovar; 3) clicar no pane de
  um worker e pressionar uma tecla.
- Esperado: o invariante que os comentários do próprio arquivo defendem (F-108):
  pane de missão não revisada não vira shell do operador. O caminho antigo
  devolvia `'resume-keyboard'` para **todo** pane de missão done-não-aprovada,
  via `decideExitedPaneKey` → `mission-owned-pane-policy.ts:184`.
- Observado: o branch novo dispara sempre que `host.sessionId` é nulo e a missão
  lê terminal, e **duas guardas do caminho antigo sumiram**:

  1. **`missionStillOwnsPane`** retorna `true` para missão done que o operador
     ainda não aprovou (`missionAwaitsOperatorReview`,
     `src/shared/mission-recovery-policy.ts:93-97`). O código novo chama
     `reclaimExitedPaneAsShell(pane, host, { ignoreMissionOwnership: terminalLink !== 'none' })`
     (`:1298-1300`), que **explicitamente pula** essa checagem (`:2448-2453`).
  2. **`paneState === 'exited'`** (`mission-owned-pane-policy.ts:182`) deixou de
     ser consultado, então panes `hibernated` ou presos em `busy` também são
     reclamados.

  Resultado: `keepReviewChannel` é `terminalLink === 'done' && pane.role ===
  'orchestrator'` (`:1291-1292`), portanto um **worker** recebe
  `'reclaim-shell'` → `reclaimAsOperatorShell(pane.id)` reescreve o `kind` do
  pane no layout persistido e o `useOrchStore` **apaga `paneMissions[pane.id]`**
  (`:2462-2467`). O canal de revisão daquele agente se perde, **não é
  desfazível pela UI**, e o board não consegue mais rotear para ele — antes de o
  humano ter aprovado.

  Efeito secundário: um pane não-missão hibernado (`hibernateHost` zera
  `sessionId`, `:2835`) cujo buffer diz literalmente *"Use ☀ para acordar"* agora
  vira shell nu na primeira tecla, em vez de esperar o botão de acordar.
- Evidencia: revisão de código do intervalo `3c61b149..HEAD`, escopo
  `src/renderer/**`, com a cadeia de chamadas e os números de linha acima lidos
  no fonte.
- Correcao sugerida: se a doutrina é "pós-missão nunca é mudez", o predicado de
  propriedade tem que sobreviver. `done && !approved` deve rotear para
  `resume-keyboard` / `keep-history`, e `ignoreMissionOwnership` deve ser
  `terminalLink === 'none'` apenas — não `!== 'none'`, que é exatamente o
  complemento do que a guarda precisa.
- Por que não foi corrigido aqui: `terminal-host.ts` tem 3133 linhas, é o
  componente central do host de terminal, e a outra sessão está ativa nesta área
  (panes/handoffs, segundo o usuário). Mexer ali agora é a colisão de maior
  risco disponível.
- Bloqueia release? **Sim.** Perda irreversível de estado de revisão por uma
  tecla, num fluxo que existe justamente para o humano conferir antes de aprovar.
- Relacionado: F-345 e F-346 (as outras duas regressões de estado deste
  intervalo), F-108 (o invariante original que os comentários do arquivo citam).
