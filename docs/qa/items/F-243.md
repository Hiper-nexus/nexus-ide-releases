# F-243 — Maestro Claude sem janela de compactação (cacheRead ~859 k/mensagem)

## F-243 | categoria: custo | severidade: alta | status: corrigido
- Tela/fluxo: o Maestro (orquestrador Claude de missão) rodava com a janela de
  contexto cheia do Claude Code — perto de 900 k tokens relidos a cada turno.
- Arquivos: `src/main/pty/pty-manager.ts`, `src/main/pty/pty-manager.test.ts`

## Evidência
`usage_events` de 30/09 (mission-defa0de5): Claude Fable 5.1 como Maestro,
828 mensagens, 1,1 M tokens de saída, ~US$ 533 estimados no dia;
`cacheReadTokens` ≈ 859 k POR mensagem no fim do dia. Os adapters host-Claude
(glm, glm-flash, deepseek, muse-claude) já definem
`CLAUDE_CODE_AUTO_COMPACT_WINDOW=1000000`; o adapter `claude` nativo não
definia nada — e o binário honra a variável (confirmado no claude 2.1.286:
"CLAUDE_CODE_AUTO_COMPACT_WINDOW is set and takes precedence",
eventos `tengu_auto_compact_*`).

## Causa raiz
Sem `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, a auto-compactação só dispara perto do
teto nativo do modelo; numa missão longa o contexto do Maestro cresce até
~900 k e cada turno relê a janela inteira no cache.

## Correção
No env de spawn (`pty-manager`), quando `adapter.id === 'claude'` &&
`authority.context.role === 'orchestrator'` && missão presente && a variável
não está definida: `CLAUDE_CODE_AUTO_COMPACT_WINDOW=400000`
(`MAESTRO_AUTO_COMPACT_WINDOW_TOKENS`). O Maestro coordena — não precisa de
900 k de contexto relido a cada turno; 400 k mantém o resumo e corta o custo
por turno pela metade. Workers e panes do operador inalterados; adapters
host-Claude preservados pelo guard `=== undefined`.

## Testes
- Orquestrador claude de missão recebe `CLAUDE_CODE_AUTO_COMPACT_WINDOW=400000`;
  worker claude e pane do operador não recebem.
- `glm` orquestrador mantém `1000000` (env.static do adapter vence).

## Verificação
`npx vitest run src/main/pty/pty-manager`; `npm run typecheck`.
