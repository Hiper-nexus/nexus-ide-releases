# F-1433 — Spinner congelado lia `working`/1.0 para sempre e o juiz da conclusão não recebia os limites declarados da leitura mecânica

## F-1433 | categoria: funcional/orquestração | severidade: alta | status: corrigido
- Tela/fluxo: (A) `nexus_pane_read` / `nexus_pane_read_many` em `mode:'digest'` → classificação do tail do pane; (B) `nexus_mission_set_status done` → verificador de conclusão de código → prompt do revisor independente (juiz frontier).
- Arquivo:linha (após a correção):
  - `src/main/orch/pane-output-digest.ts:93` (`SPINNER_STALL_AGE_MS = 120_000`), `:120-139` (`DigestOptions.lastOutputAgeMs` / `PaneTailDigest.lastOutputAgeMs`), `:483-506` (eco da idade nos dois returns do digest).
  - `src/main/orch/pane-registry.ts:85-94` (re-export de `paneSessionLastOutputAt`, o getter que já existia em `pane-session-output.ts:156`, F-1381).
  - `src/main/orch/tools-panes.ts:3284-3288` (`sessionOutputAgeMs`), `:3327-3357` (`stalled` → `unknown`/0.2 + hint com a idade), `:3409` e `:3484` (idade passada em `pane_read`/`pane_read_many`).
  - `src/main/orch/mission-code-completion.ts:30-37` (`MissionCodeCandidate.declaredLimits`), `:118` (`declaredLimitNote` exportado, F-1430), `:200-202` (`forReview` com os limites antes de `ensureIndependentReview`).
  - `src/main/orch/mission-code-completion-production.ts:63-75` (`declaredLimitPromptLines`), `:86` (seção no `reviewerPrompt`).
- Passos (campo 13/10, release 0.76.243):
  1. **(A)** Um worker com a CLI travada (hook pendurado, rede morta) para de emitir bytes, mas o último quadro de spinner continua no buffer do PTY. O orquestrador lê o pane em digest.
  2. O digest marca `noReadableText: 'spinner'` e `tools-panes` mapeava isso para `state: 'working'`, `stateConfidence: 1` — para sempre, sem qualquer noção de silêncio.
  3. **(B)** A verificação mecânica declara limites (teto de 384 KiB por arquivo, orçamento de 8 MiB etc.) com `declaredLimits`; `release-notes.ts` (485 KB, alterado) fica fora da leitura de conteúdo.
  4. O prompt do juiz (`reviewerPrompt`) só recebia `unreadPaths`/`absentPaths` (F-1428) — nunca os `declaredLimits` (F-1430). O juiz revisava sem saber que arquivo executável alterado não foi lido.
- Esperado: (A) com saída recente o spinner continua `working`/1.0; sem saída nova além do limiar o digest NÃO afirma trabalho — estado desconhecido, confiança baixa, `lastOutputAgeMs` presente e `hint` com há quanto tempo não sai nada. (B) o prompt do juiz lista cada limite declarado (motivo + até 20 arquivos + "+N", com destaque de código executável) e manda ler esses arquivos diretamente; sem limites, o prompt não muda.
- Observado: (A) spinner congelado lia `working`/1.0 indefinidamente (regressão silenciosa do F-1425); (B) prompt sem nenhum menção aos limites declarados — o juiz não sabia do `release-notes.ts` fora da leitura.
- Evidencia: RED → `npx vitest run src/main/orch/pane-output-digest.test.ts src/main/orch/tools-panes-peer-read.test.ts src/main/orch/mission-code-completion-production.test.ts --maxWorkers=2`: 4 falhas (`expected undefined to be 5000`, `expected NaN >= 5000`, `expected 'working' not to be 'working'`, `toContain('src/shared/release-notes.ts')`); o teste "sem limites idêntico ao de antes" já passava antes do fix (congela o baseline).

## Causa raiz
- **(A)** O F-1425 derivou "trabalho ativo" só do PRESENCE do quadro de spinner, sem tempo. O timestamp de última saída já existia (`paneSessionLastOutputAt`, F-1381, usado pelo supervisor de delegação e pelo auto-close) mas o caminho do digest não o consultava.
- **(B)** Os `declaredLimits` nasceram no F-1430 dentro de `CivilianMechanicalVerification` e foram escritos só na nota de conclusão (`mission-code-completion.ts:212`). O objeto `MissionCodeCandidate` entregue ao runtime da revisão era montado ANTES da verificação e não os carregava — `reviewerPrompt` nunca os via.

## Correção
### 1 — o digest carrega a idade da saída e desqualifica o spinner congelado (`pane-output-digest.ts` + `tools-panes.ts`)
- `SPINNER_STALL_AGE_MS = 120_000` (constante nomeada). `digestPaneTail` ganha `DigestOptions.lastOutputAgeMs` e ecoa `lastOutputAgeMs` no resultado (presente nos dois returns, inclusive no do spinner-only).
- `pane_read`/`pane_read_many` medem a idade via `sessionOutputAgeMs` (wrapper fino sobre `paneSessionLastOutputAt`, já re-exportado por `pane-registry`; sem registro → campo ausente, comportamento antigo preservado).
- Em `paneDigestResult`: spinner-only **e** idade > limiar → `state: 'unknown'`, `stateConfidence: 0.2`, `needsHuman: 0`, e `hint` com a idade (`sem saída nova há 3m 0s: spinner pode estar congelado (CLI travada); mode:'full'…`). Spinner com saída recente (ou sem registro de idade) segue `working`/1.0 — F-1425 continua verde.
- Vocabulário: `'stalled'` **não** existe no caminho do `pane_read` nem no classificador Jev (`JEV_PANE_STATES` = working/waiting_for_human/finished/errored/idle_prompt); `'unknown'` é o estado de "não sei" que já existe (`PaneRuntimeState`, `orch-types.ts:803`) e é o que o comentário do próprio `paneDigestResult` já chamava de "sem estado (unknown)".

### 2 — os limites declarados atravessam para o prompt do juiz (`mission-code-completion.ts` + `mission-code-completion-production.ts`)
- `MissionCodeCandidate` ganha `declaredLimits?: readonly CandidateQualityDeclaredLimit[]`; `ensureMissionCodeCompletion` monta `forReview = { ...work, declaredLimits: verification.declaredLimits }` (só após o gate de falha real) e entrega ao `ensureIndependentReview`.
- `declaredLimitNote` (F-1430: motivo + 20 arquivos + "+N" + destaque de código executável) virou `export` e foi reutilizado — sem reescrita da regra. `declaredLimitPromptLines` acrescenta a instrução ("leia-os diretamente (git diff/leitura própria) quando forem relevantes") e devolve `[]` sem limites: o prompt fica byte a byte o mesmo de antes.
