# F-668 — No Windows o brief multi-linha chegava ao worker Claude só com a 1ª linha

## F-668 | categoria: funcional | severidade: alta | status: corrigido
- Tela/fluxo: Windows, CLI instalada pelo npm (atalho `claude.cmd`). Orquestrador abre helper Claude com `nexus_pane_spawn`; o brief vai no argv do spawn.
- Arquivo:linha: `src/main/pty/pty-manager.ts` (desvio do `.cmd` do npm só existia para o Codex e exigia `node.exe` ao lado do atalho), `src/main/adapters/windows-npm-shim.ts` (novo `windowsNpmShimSpawn`).
- Passos: 1) Missão da aba no hipergo. 2) Orquestrador solta helpers Claude (analista e writer).
- Esperado: o helper recebe o brief inteiro e começa a tarefa.
- Observado (28/09 13:37): o analista respondeu "Sua mensagem chegou só com o título '## Nexus execution authority'"; o writer Claude morreu em 2 s.
- Evidencia: o `claude` do PATH é `claude.cmd` do npm (`"%dp0%\...\claude.exe" %*`). O ConPTY executa `.cmd` pelo `cmd.exe`, que corta o argumento na primeira quebra de linha, expande `%VAR%` dentro do texto e limita a linha a 8K. O desvio para o executável real só existia para o Codex, e só com `node.exe` ao lado do atalho — o Codex reinstalado em `~/.local/bin` também passava pelo `cmd.exe`.
- (resolvedor) Correcao: `windowsNpmShimSpawn` usa o resolvedor verificado (`windowsNpmShimInvocation`: mesmo pacote, entrypoint exato) para toda CLI embutida e acha o `node.exe` ao lado do atalho ou no PATH; o spawn direto (sem sandbox) roda o `.exe` do pacote ou `node.exe` + script, nunca o `cmd.exe`. Testes: `windows-npm-shim.test.ts` (F-668), `pty-manager.test.ts` ("worker claude no Windows nasce no executável do pacote") — falha no código antigo.
