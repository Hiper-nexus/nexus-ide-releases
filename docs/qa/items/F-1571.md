# F-1571 — Auto-update deixa o Claude Code como stub (npm 12) e toda missão nasce morta

## F-1571 | categoria: funcional | severidade: alta | status: corrigido
- Tela/fluxo: atualização automática das CLIs (boot e tique diário) → qualquer pane Claude; Quadro da missão → "Por que parou".
- Arquivo:linha: `src/main/adapters/cli-install-recipes.ts` (`npmRecipe`, ramo Claude de `selectCliUpdateRecipe`); `src/main/persistence/provider-config-store.ts` (`startCliAutoUpdate` → `run`; handler `installCli`); `src/renderer/components/mission/MissionInspector.tsx` (fallback de "Por que parou").
- Passos: 1) Windows com Node do WinGet e npm 12.2.0; Claude Code 2.1.300 instalado pelo npm e funcionando. 2) Abrir o Nexus 0.76.316 com atualização automática ligada. 3) Criar uma missão.
- Esperado: a atualização deixa o Claude na versão nova e funcionando; se algo falhar, a CLI continua respondendo e a falha aparece com a causa.
- Observado: o auto-update rodou `claude update`, que chamou `npm install -g @anthropic-ai/claude-code@2.1.303`. O npm 12 bloqueia scripts de instalação por padrão e sai com código 0; o `postinstall` (`node install.cjs`, que copia o binário nativo de `claude-code-win32-x64` sobre `bin/claude.exe`) não rodou e ficou o stub de 500 bytes, que imprime "claude native binary not installed" e sai com 1. O Nexus só registrou `cli-update failed/install-failed`. Todo Maestro morria ~7,6 s depois do spawn (três vezes seguidas), o pane dizia "processo caiu" e o Quadro afirmava "Sem última tela registrada (a missão foi encerrada por uma build anterior)" numa missão criada naquela build. Com `beforeVersion` nulo o auto-update nunca mais tentava, embora o painel prometesse "o Nexus tenta de novo".
- Evidencia: `%LOCALAPPDATA%/npm-cache/_logs/2026-10-19T11_32_02_181Z-debug-0.log` ("1 package had install scripts blocked… Run `npm install -g --allow-scripts=@anthropic-ai/claude-code`", `exit 0`); `logs/lifecycle-2026-10-19.ndjson` (`cli-update claude failed install-failed` e três `agent-pty-exit` do orquestrador de `mission-63dbe51e`, `exitCode -1`, `uptimeMs ~7650`, `terminationOrigin null`); journal da missão sem nenhum evento de tela. Prova em prefixo temporário (19/10): `npm install -g @anthropic-ai/claude-code@2.1.303` sem nada → `bin/claude.exe` de 500 bytes; com `--allow-scripts=@anthropic-ai/claude-code` ou com `npm_config_allow_scripts` no ambiente → 290 MB. `claude update` 2.1.300 → 2.1.303 com `npm_config_allow_scripts` no ambiente → binário completo; sem a variável → "Successfully updated" com exit 0 e o stub de 500 bytes.
- (resolvedor) Correcao: (1) toda receita npm libera os scripts do PRÓPRIO pacote da CLI (`--allow-scripts=<pacote>`, pacote por último; o ramo npm de atualização agora preserva as flags da receita). (2) `claude update` numa instalação npm (`/node_modules/@anthropic-ai/claude-code/` no realpath) recebe `npm_config_allow_scripts=@anthropic-ai/claude-code` no ambiente — o updater da Anthropic continua dono do canal (F-360). (3) O auto-update nunca deixa a CLI pior: se depois de atualizar o lançador do pane não responde, reinstala na hora pela receita npm do mesmo prefixo (`selectCliRepairRecipe`, com `--allow-scripts`) e registra `updated/repaired`; sem reparo possível registra `broke-cli`. CLI que já passou numa checagem e hoje não responde ganha UMA reinstalação npm por sessão do app (sem laço; CLI que nunca respondeu não é reinstalada às cegas). (4) "Atualizar CLI" com a CLI sem responder escolhe a reinstalação npm (o stub não roda `claude update`); update manual que quebra a CLI diz que o próximo clique a reinstala. (5) Maestro de missão que sai sozinho grava a última tela (`recordMissionOrchestratorExitScreen` no tap de saída, mesma chave de idempotência da terminação pedida) e o Quadro deixou de culpar uma "build anterior" quando não há tela. A máquina do operador foi reparada à mão em 19/10 rodando o `install.cjs` do pacote. Validação: `npx vitest run` dos arquivos tocados (1508 testes), `npm run typecheck`, `npm run security:renderer-sinks`; mutação que desliga o reparo derruba os casos novos. As 28 falhas restantes em `src/main/adapters` e `src/main/persistence` no Windows são da base pré-existente (exec-bit POSIX, Keychain, `sips`) e não tocam estes arquivos.
