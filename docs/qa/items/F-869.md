# F-869 — Fechar o monitor Bubblewrap não prova o fim de sua namespace PID

## F-869 | categoria: seguranca | severidade: alta | status: corrigido
- Tela/fluxo: lifetime físico de comandos Linux do Main; retenção de permit e cleanup.
- Arquivo: `src/main/orch/owned-linux-command.ts`; teste co-localizado.
- Esperado: liberar a responsabilidade apenas depois do encerramento de todos os processos da namespace capturada, incluindo reparent/setsid, junto com o fechamento real do filho externo.
- Observado: o monitor de Bubblewrap retorna quando o processo inicial termina, enquanto seu PID 1 pode ainda estar vivo. `close` do wrapper ou EOF de sync-fd isolados não demonstram teardown completo.
- Evidencia primária: [Bubblewrap monitor/reaper](https://github.com/containers/bubblewrap/blob/main/bubblewrap.c#L452-L620) distingue a saída do processo inicial da espera do reaper. [Handshake e gate](https://github.com/containers/bubblewrap/blob/main/bubblewrap.c#L2948-L3306) escreve info antes do gate, mantém sync-fd no reaper e só faz setsid depois do block-fd. [Kernel PID namespace](https://github.com/torvalds/linux/blob/master/kernel/pid_namespace.c#L180-L265) encerra/recolhe os membros; [exit_notify](https://github.com/torvalds/linux/blob/master/kernel/exit.c#L575-L718) só instala EXIT_ZOMBIE depois dessa fase. Fontes inspecionadas em 03/10/2026.
- (resolvedor) Correcao: `prepareOwnedLinuxCommand(plan)` é puro antes do spawn. Aceita somente a forma canônica gerada pelo Main, conserva confinamento/mounts/rede e adiciona info/block/sync nos FDs privados 3/4/5. `waitForExit(proc)` vincula listeners imediatamente, limita o protocolo, fixa os diretórios proc e lê birth/UID/NSpid/parent/grupo/imagem por FD. O gate só recebe um byte após a prova. UID-map transitório é esperado no mesmo descritor fixado. A promessa exige desaparecimento ou zombie do PID 1 original e `close` real; erro/perda de identidade mantém a responsabilidade.
- Cancelamento: antes de liberar o gate, só o grupo do filho destacado e ainda não recolhido pode ser sinalizado, depois da captura. Depois, somente seu `ChildProcess.kill` exato; nunca PID 1 numérico nem varredura por PPID. `dispose` não fecha block-fd em ambiguidade: EOF também libera o gate. A semântica existente de `--die-with-parent` encerra daemons de background quando o monitor morre; não foi criada uma promessa de persistência. A janela de registro de parent-death depois do gate conserva prova pendente se a namespace não terminar.
- Validação: 18 testes de IO/FD/identidade/ordem/erros passaram; fixture real Bubblewrap opt-in não rodou no macOS. Incluem fechamento concorrente: refs dos descritores são retiradas antes do await, evitando close duplicado/reuso de fd. Typecheck, main-sync e renderer sinks passaram com Node 22.23.2/mutex da release, sem installs/rebuilds. Em container temporário da imagem Ubuntu 26.04 já local, sem rede/configuração adicional, a leitura de proc por FD fixado terminou em desaparecimento após o exit do processo de teste; isso prova somente essa operação de kernel, não a integração Bubblewrap.
- Limitação explícita: fonte e kernel simulados não são prova de Linux Bubblewrap nem de host nativo assinado. O CI Linux pode executar `NEXUS_LINUX_OWNED_COMMAND_TEST=1 node node_modules/vitest/vitest.mjs run src/main/orch/owned-linux-command.test.ts --maxWorkers=1`; exige o bwrap já instalado e namespace permitida.

## API para a integração do Main

```ts
const owned = prepareOwnedLinuxCommand(canonicalPlan);
const child = spawn(owned.plan.file, owned.plan.args, {
  cwd: owned.plan.cwd, env: owned.plan.env, detached: true, stdio: owned.stdio,
});
const physicalExit = owned.waitForExit(child); // bind imediato, antes de awaits
// cancelamento: void owned.stop();
await physicalExit; // só agora release do permit/cleanup
owned.dispose();
```

Não houve alteração de `process-sandbox`, Host, OCI, MCP/env, UI, brokers C6 ou
do runtime/harness F-863. A integração do chamador pertence ao root.
