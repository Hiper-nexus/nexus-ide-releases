# F-1014 — O app do celular não via Git nem arquivos de um pane do desktop Nexus

## F-1014 | categoria: funcional | severidade: media | status: corrigido
- Tela/fluxo: app móvel (`mobile/`) › host Nexus › pane › Alterações / Arquivos.
- Arquivo:linha (antes): `mobile/src/transport/nexus-bridge-rpc-adapter.ts:40-42` (`files.` e `git.` na lista `UNSUPPORTED_AREAS`; todo `git.*`/`files.*` respondia `nexus_host_unsupported`), `src/main/remote/remote-bridge.ts:1015-1016` (`default: unknown command` — a bridge não tinha comando de Git nem de arquivos), `mobile/src/nexus-host/NexusHostScreen.tsx:38-40` (nota "Não disponível em host Nexus: … arquivos, Git …").
- Passos: 1) Parear o app com o desktop Nexus (F-994). 2) Abrir um pane de agente. 3) Tentar ver o que o agente mudou no checkout (git status / diff) ou ler um arquivo.
- Esperado: ver as alterações do checkout daquele pane, abrir o diff de um arquivo e navegar/ler arquivos — só leitura, com a mesma autoridade do desktop.
- Observado: nenhuma tela; `git.status` e `files.list` voltavam "Git (git.status) não disponível em host Nexus". O único caminho era digitar `git diff` no PTY do agente e ler a saída do terminal.
- Evidencia: leitura do código acima e o teste `remote-bridge.mobile-app.test.ts` de F-994 (passo 7 recusava `git.status`).
- (resolvedor) Correcao:
  - Protocolo novo da bridge, no formato `{id, type, ...}` de sempre: `git.status {paneId}`, `git.diff {paneId, path, staged?, untracked?}`, `files.list {paneId, path?}`, `files.read {paneId, path}`. Todos são `READ_ONLY` na `mobile-companion-policy` (`mobileRpcKindForBridgeType`); stage/commit/checkout/escrita não têm comando e caem em `unknown command`.
  - Desktop (`src/main/remote/remote-workspace-rpc.ts`): o pane precisa existir e ser LEGÍVEL pelo escopo do aparelho (`authorizePaneAccess(..., 'read')`, a mesma regra de `pane.read`); a raiz é o checkout DO PANE (`executionScope` do worker em worktree, senão `scope`), resolvida com `realpath` e conferida contra o `rootRealPath` que o Main registrou (diferente = `checkout-identity-changed`); pane de navegador não tem checkout. Caminho: string ≤ 4096, sem controle/NUL/`\`, relativo (`/` e `C:` = `absolute-path`), sem `..` (`parent-traversal`), sem segmento `.git` em qualquer caixa (`git-internals`), sem segmento que case o `SECRET_BASENAME_PATTERN` da orientação (`.env*`, `*.pem|key|p12|pfx`, `id_rsa`, `id_ed25519`, `credentials.json`, `secret(s).json|yaml` → `secret-file`); cada componente existente que for link simbólico precisa resolver com `realpath` para dentro da raiz real (`path-escapes-checkout`; link quebrado também) e, resolvido, não pode cair em `.git`/segredo. Recusas são `not authorized: <motivo>`; erros do git saem na primeira linha, sem o caminho absoluto do checkout.
  - Serviços reaproveitados do desktop (nada de PTY, nada de `git` novo): `gitScmStatus` e `gitFileDiff` (`src/main/integrations/git-workspace.ts`, os do painel Git — runner endurecido, `--no-ext-diff`, config executável do repo recusada), `listDir` (explorador de arquivos, `src/main/persistence/files-ipc.ts`, agora exportado junto com `looksBinary`) e `openWorkspaceFileForRead` (`src/main/orch/workspace-file.ts`: abre com `O_NOFOLLOW`, recusa link e hardlink, confere o descritor). Esses continuam como segunda camada atrás do guarda de caminho.
  - Limites: leitura e diff cortados em 256 KB com `truncated: true` (o diff já vinha cortado em 512 K caracteres pelo desktop); binário (NUL nos primeiros 8000 bytes, ou "Binary files … differ" do git) vem como `binary`; até 1000 entradas por pasta. O status não leva `remote` (a URL pode carregar credencial) nem a saída crua do porcelain; arquivo de segredo aparece no status marcado `restricted` (o diff é recusado) e some da listagem de pastas (junto com `.git`, links e `node_modules`, que o explorador já escondia).
  - App: `mobile/src/transport/nexus-bridge-git-files.ts` (API `nexus.workspace` + roteamento dos nomes do Orca: `git.status`, `git.diff {worktree:'id:<pane>', filePath, staged}`, `files.list`, `files.read {relativePath}`; a resposta do status é compatível com `readMobileGitStatusResult`; patch unificado → linhas do diff do app). O adaptador só removeu `git.status/git.diff/files.list/files.read` da recusa — o resto de `git.*`/`files.*` segue "Escrita no Git (…)"/"Escrita e busca de arquivos (…) não disponível em host Nexus". Sem chamada nova a `sendRequest` na UI (o inventário do porto RPC não cresceu).
  - Tela: `mobile/src/nexus-host/NexusPaneWorkspace.tsx`, aberto pelos botões **Alterações** e **Arquivos** no detalhe do pane (`NexusHostScreen.tsx`, blocos marcados F-1014). Alterações: branch e upstream, seções Alteradas / Novas / Preparadas, letra de status, cadeado nos protegidos; tocar abre o diff com `MobileDiffReviewLine` (prop nova `readOnly`: a linha não vira botão de nota) e o realce de sintaxe por bloco da revisão. Arquivos: navegação por pasta e leitura com número de linha. Estados de carregando, vazio (com ação) e erro (texto em pt-BR a partir da recusa + "Tentar de novo").
  - F-1000 (recusa de caracteres de controle em `pane.input`) intocado.
- Validacao: por launchd (fora do pane, Node 22).
  - `src/main/remote/remote-bridge.mobile-app.test.ts` (bridge REAL em processo, checkout git REAL em disco com alteração, preparado, novo, binário, arquivo de 300 KB, `.env` versionado e links para fora): status e diffs pelo app (patch, preparado com os nomes do Orca, arquivo novo, binário, diff grande cortado em ≤ 256 K), worker lendo a PRÓPRIA worktree, lista e leitura (limite de 256 KB, binário, `.git`/`.env`/links escondidos), recusas (`leak.txt`→fora, `leakdir/secret.txt`, `files.list leakdir`, diff de arquivo novo que é link para fora, `..`, absoluto, controle, `.git/config`, `.GIT/config`, `.env`, diff de `.env`, `envlink`→`.env`), autorização por pane (outro projeto, checkout que não é o próprio realpath, pane inexistente), cliente cru (mesmo `id` duas vezes = duas respostas iguais sem efeito; `git.commit`/`git.stage`/`git.checkout`/`files.write` = `unknown command`; HEAD e arquivo intactos; status sem `remote`/`raw`), queda de socket com re-auth, revogação → `auth-failed` ("pareie de novo") e novo pareamento lendo de novo. Junto com `remote-bridge.test.ts`, `remote-bridge.approval.test.ts` e `mobile-companion-policy.test.ts`: 76/76; `src/main/remote` inteiro + `files-ipc.test.ts` + `workspace-file.test.ts`: 41 arquivos / 304 testes.

  - App: `nexus-bridge-rpc-adapter.test.ts` (mapeamento dos nomes do Orca, recusa da bridge como falha do host, recusa de forma sem ir à bridge, escrita ainda recusada) 17/17, `nexus-bridge-git-files.test.ts` 5/5, `MobileDiffReviewLine.test.tsx` 4/4, `unvalidated-rpc-request-port-boundary.test.ts` 8/8. `npm run typecheck` 0, `npm run lint:main-sync` 0 (sem processo síncrono novo), `tsc --noEmit` do mobile 0, oxlint dos arquivos tocados 0 erros.
- Limite: nada rodou num aparelho nem em simulador — a tela `NexusPaneWorkspace` não foi renderizada; só a lógica e o transporte foram provados em Node. `gitScmStatus`/`gitFileDiff` são síncronos no Main (como no painel Git do desktop): um repositório enorme segura o Main pelo tempo do `git status`, limitado pelo teto de 60 mensagens/min por aparelho. A deduplicação por id da bridge existe só para `pane.input` (`messageId`); Git e arquivos são só leitura, então um reenvio apenas lê de novo.
