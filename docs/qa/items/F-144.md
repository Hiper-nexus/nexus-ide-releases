# F-144 — `catch {}` sem log no scanner de qualidade faz falha do scanner ser indistinguível de "scanner indisponível", e o gate aceita as duas como conclusão

## F-144 | categoria: seguranca | severidade: alta | status: aberto
- Tela/fluxo: conclusão de missão no lane standard com squad — o caminho
  `nexus_mission_set_status(done)` → verificação automática → gate de revisão
  independente.
- Arquivo:linha: `src/main/orch/civilian-auto-review.ts:287-289` (o catch),
  `src/main/orch/civilian-delivery-completion.ts:1177` (a prova `unavailable`),
  `src/main/orch/mission-independent-review-gate.ts:252-259` (o gate que aceita).
- Passos: 1) missão standard com squad; 2) fazer `runCandidateQualityAnalysis`
  lançar — timeout, permissão, repositório grande demais, **ou um bug no
  próprio scanner**; 3) concluir a missão.
- Esperado: uma falha do scanner ser distinguível de uma indisponibilidade
  legítima, e pelo menos registrada.
- Observado: o catch é nu e não loga nada:

  ```ts
  } catch {
    return { kind: 'defer-to-roster-review' };
  }
  ```

  Dali sai a prova em `civilian-delivery-completion.ts:1177`:
  `{ status: 'unavailable', note: 'Scanner indisponível; conclusão pela política
  de entrega existente.' }`, e o gate em `mission-independent-review-gate.ts:252-259`
  devolve `ok: true` para **ambos** os status — o que muda é só o rótulo:

  ```ts
  if (isAutomaticCompletionProof(input.automaticProof, input.scope, input.mission)) {
    return {
      ok: true,
      reviewerHandoffId: input.automaticProof.status === 'verified'
        ? 'main-automatic-verification' : 'main-check-unavailable',
    };
  }
  ```

  **A política em si é deliberada e está documentada no nome do teste**:
  `mission-independent-review-gate.test.ts:144` chama-se *"accepts an explicit
  unavailable check without misrepresenting it as a verified review"*. Ou seja,
  "se o scanner não pôde rodar, não bloqueie a entrega, mas rotule" é uma
  decisão consciente, com trilha de auditoria no `reviewerHandoffId`. **Este
  finding não contesta essa política.**

  O que ele contesta é que o `catch {}` sem log **alimenta** essa política com
  uma entrada que ninguém consegue distinguir. Um bug no scanner, um `throw` de
  um sensor novo, ou um timeout transitório produzem exatamente o mesmo resultado
  que uma indisponibilidade legítima: missão concluída, rótulo
  `main-check-unavailable`, e **nenhuma linha de log** dizendo o que falhou. O
  efeito prático é que uma regressão no scanner desliga silenciosamente a
  verificação automática de todas as missões, e o único sintoma visível é um
  rótulo que já era esperado em casos normais.
- Agravante de escopo, verificado: para o lane **ops**, `missionRequiresIndependentReview`
  cobre ops (`mission-independent-review-gate.ts:97-101`) mas
  `missionRequiresAutomaticCompletionReview` **não** cobre (`:133-138`), e
  `mission-delivery-artifact-gate.ts:162` retorna `true` em `allowsTextDelivery`
  para `lane === 'ops'`. Uma missão ops+squad pode então concluir só com uma
  string de resumo — sem arquivo, sem revisão e, se o scanner lançar, sem
  verificação. Se isso é a intenção para ops, vale documentar; se não é, é um
  segundo finding.
- Evidencia: `sed -n '283,292p' src/main/orch/civilian-auto-review.ts`;
  `grep -n "unavailable" src/main/orch/civilian-delivery-completion.ts` → linha
  1177; `sed -n '252,259p' src/main/orch/mission-independent-review-gate.ts`;
  `sed -n '144,154p' src/main/orch/mission-independent-review-gate.test.ts`.
- Correcao sugerida (mínima, não contesta a política): logar o erro no catch de
  `civilian-auto-review.ts:287` antes de retornar `defer-to-roster-review`, e
  carregar a mensagem na `note` da prova em `civilian-delivery-completion.ts:1177`
  para que o rótulo `main-check-unavailable` seja diagnosticável depois do fato.
  Opcionalmente, distinguir `unavailable-because-error` de
  `unavailable-because-not-applicable`, já que hoje os dois chegam ao gate com o
  mesmo status.
- Por que está `aberto` e não foi corrigido aqui: o arquivo é de outra sessão,
  que está trabalhando ativamente em panes/handoffs neste momento, e o
  comportamento está travado por teste. Mudar a semântica de `ok: true` sem quem
  escreveu a política é sobrescrever uma decisão deliberada numa fronteira que o
  `AGENTS.md` declara sensível. O log sugerido é aditivo e não contradiz nenhum
  teste, mas ainda assim pertence a quem é dono do arquivo.
- Bloqueia release? **Sim, na minha leitura** — não porque a política esteja
  errada, mas porque uma release notarizada não deveria levar uma verificação de
  segurança cuja falha é invisível. O mínimo aceitável antes de publicar é o log.
- Relacionado: F-145 (a outra garantia perdida no mesmo caminho de conclusão),
  F-404 (o mesmo padrão de colapsar "não sei" numa resposta terminal, corrigido
  em `worktree-lifecycle.ts`).
