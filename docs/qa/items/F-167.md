# F-167 — Pane de missão concluída trava com "o main recusou a digitação neste pane"

## F-167 | categoria: funcional | severidade: alta | status: corrigido
- Tela/fluxo: missão concluída ("Pronto para revisar") → Terminais/Stage → digitar no Maestro ou no worker. Relacionado a F-115, F-149 e F-348 (mesmo sintoma, outra causa).
- Arquivo:linha: `src/main/orch/pane-registry.ts` (`retireStaleMainOwnedPane`), `src/renderer/terminal/terminal-host.ts` (`requestDeadMissionPaneRevive`), `src/renderer/terminal/mission-owned-pane-policy.ts`.
- Passos: 1) Missão rodando no projeto A. 2) Trocar para o projeto B (os panes da missão ficam headless e o xterm estacionado guarda o id da sessão). 3) A missão conclui; o reconciliador de autoridade (`terminateUnauthorizedMissionRuntimes`, 1 s) mata os PTYs de missão fora de `running`. 4) Voltar ao projeto A e digitar.
- Esperado: o pane mostra a sessão encerrada; tecla no Maestro pede ajuste, tecla no worker abre shell (política existente).
- Observado (missão `mission-50c084cc…`, 26/09): o Claude orquestrador saiu às 13:18:34.1, 46 ms depois do `done`; o Codex parou de logar às 13:18:16. O exit não tinha renderer para receber (`session.wc = null`), então o xterm voltou com o id morto e cada rajada de teclas imprimia "[nexus] o main recusou a digitação neste pane." (print do operador, 13:21). Mesmo com o exit entregue, a tecla no Maestro de missão concluída tentava religar a CLI, que o main recusa fora de `running`, e a tecla sumia.
- Evidencia: `cost-state` final do transcript do orquestrador (`totalDuration` 321583 ms desde `startTime`), `missions.updated_at` 1790439514085, logs do Codex em `provider-state/codex/…/logs_2.sqlite`, scrollback persistido dos panes 3 e 4 só com as recusas.
- (resolvedor) Correcao: 1) Ao aposentar um pane headless cuja sessão já morreu, o Main entrega `pty:exit` ao renderer que apresenta o mesmo workspace (escopo exato); outro projeto não recebe nada. O host segue o caminho normal de pane encerrado. 2) Tecla no Maestro morto de missão concluída faz o mesmo que "Pedir um ajuste" (`mission.command resume`); o main religa o Maestro esperando a orientação, e o pane não religa a CLI por conta própria (evita dois Maestros).
- Validação: `pane-registry-main-owned.test.ts` › "delivers the lost exit…" e `mission-owned-pane-policy.test.ts` › "tecla no Maestro morto de missão concluída pede ajuste" falham no código antigo. Pane registry (73 testes) e política (57 testes) passaram no Node 22.23.2.
- Limite: o exit entregue usa código 0 (o código real não fica guardado para sessão sem renderer). O reconciliador continua matando o runtime de missão fora de `running` por desenho; o canal de intervenção é o ajuste.
