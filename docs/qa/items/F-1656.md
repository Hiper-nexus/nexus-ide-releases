# F-1656 — `nexus_browser_open` com `device` mata o Main (SIGSEGV em null+0xf8)

## F-1656 | categoria: funcional | severidade: alta | status: corrigido

- Tela/fluxo: navegador embutido de agente; `nexus_browser_open({device:'mobile'})` num pane recém-criado.
- Arquivo:linha: `src/main/browser/browser-manager.ts:298` (`applyBrowserDeviceEmulation` → `wc.enableDeviceEmulation`), chamado de `navigateBrowserEntry` (`:1370`) via `src/main/orch/tools-browser.ts:149`.
- Passos: 1) pane Claude de agente (`pty-mvl0n80j-1`) chama `nexus_browser_open` com `{url:"https://navalhago.app/barbeariademo", device:"mobile", title:"Demo booking"}`; 2) o pane nasce escondido (`view.setVisible(false)`) e sem documento commitado (o `about:blank` de nascimento não navega); 3) `applyBrowserDeviceEmulation` chama `wc.enableDeviceEmulation` antes do primeiro `loadURL`.
- Esperado: o pane abre emulando mobile; o Main continua vivo.
- Observado: crash do processo principal, `EXC_BAD_ACCESS (SIGSEGV) at 0xf8` na main thread.
- Evidência:
  - Relatório `~/Library/Logs/DiagnosticReports/nexus-ide-2026-10-23-104249.ips` (0.76.423, Electron 43.8.3, pid 17415, uptime 1890 s).
  - O símbolo do relatório (`node::sqlite::DatabaseSync::ShouldIgnoreSQLiteError +265984`) é o exportado mais próximo (266 KB à frente). Simbolizado com o pacote oficial `electron-v43.8.3-darwin-arm64-symbols.zip` (módulo `4C4C44DE-5555-3144-A185-4BB45395351F`): frame 0 = `electron::api::WebContents::EnableDeviceEmulation`, chamado pelo dispatcher gin `void (WebContents*, DeviceEmulationParams const&)` a partir de um microtask (`MicrotaskQueue::PerformCheckpoint`). Disassembly no endereço `+0x38`: `ldr x0, [x0, #0xf8]` com `x0 == 0` — é `frame_host->GetView()->GetRenderWidgetHost()` com `GetView()` nulo.
  - Causa no Electron 43.8.3 (`shell/browser/api/electron_api_web_contents.cc`): `EnableDeviceEmulation` não checa `frame_host->GetView()` (continua assim no `main` do Electron).
  - Correlação: audit `nexus_browser_open` `intent` às `2026-10-23T13:42:46.804Z` sem `ok`; `browser-profile.json` gravado 13:42:46; crash 13:42:47.183 (o intervalo é o `await prepareNavigation` — DNS/policy — cuja continuação roda em microtask, como o stack mostra).
  - Antes: teste `browser-manager-actions.test.ts` (RED) provando `enableDeviceEmulation` no primeiro load do pane novo; depois do fix, 91/91.
- Correção: `BrowserEntry.renderViewReady`, marcado no commit do primeiro documento (`did-navigate`, que já reaplicava a emulação a cada navegação). `applyBrowserDeviceEmulation` agora:
  - aplica a UA imediatamente (não depende de render view e precisa valer para o primeiro request);
  - registra `entry.emulatedViewport` e só chama `wc.enableDeviceEmulation` quando `renderViewReady`; sem commit o viewport entra no `did-navigate`, antes do `did-finish-load`, pelo mesmo caminho que já reaplicava a emulação;
  - o `disableDeviceEmulation` recebe a mesma cerca (desligar num widget inexistente desreferencia o frame host). O `entry.emulatedViewport` continua sendo o intent, então a emulação pedida antes do primeiro documento não se perde.
- Testes: 3 testes existentes ajustados para o contrato novo, 1 teste de regressão explícito ("never calls the native emulation on a pane that has not committed a document") e fixture `bootCommitted()` para os cenários de `nexus_browser_responsive` num pane que já commitou (o `getURL()` do fixture já devolvia página, mas nenhum `did-navigate` era emitido).
- Validação executada: `npx vitest run src/main/browser/ src/main/orch/tools-browser-workspace.test.ts` — **365/365**; `npm run typecheck` — **exit 0**.
- Limites: não reproduzido no app empacotado (o gatilho exige o nativo do Electron; a prova é a simbolização + o teste de contrato). O caminho do operador (`browser:deviceEmulation` sobre pane já carregado) não mudou de comportamento.
