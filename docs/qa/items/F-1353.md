# F-1353 — `resume` de um writer glm fechado recusava com "conversa original indisponível"

## F-1353 | categoria: funcional | severidade: alta | status: corrigido
- Tela/fluxo: `nexus_pane_spawn({ resume: <paneId> })` numa missão → `captureMissionPaneResume` → `getProviderPaneSession(scope, paneId, adapterId, accountId)`.
- Arquivo:linha (antes): `src/main/usage/usage-service.ts`, `#onSessionDictated`. A função saía na primeira linha para qualquer adapter que não fosse `claude` ou `codex`, antes de gravar a linha `provider_pane_sessions`.
- Passos (ao vivo, 12/10, 07:00):
  1. O writer do F-1303 roda no adapter `glm` (binário do Claude Code com `--model glm-5.3 --session-id <uuid>`), na worktree `.harvest/s240-f1303`.
  2. O pane entrega o handoff `success` e fecha sozinho (autoClose) às 06:33.
  3. O Maestro pede `nexus_pane_spawn({ resume: 'pane-mv51n116-1o', prompt: … })`.
- Esperado: nasce um pane que retoma a conversa na mesma worktree.
- Observado: `resume_context_unavailable: conversa original indisponível; nenhum pane novo foi iniciado`.
- Evidencia (leitura em cópias dos bancos, sem tocar no original):
  - O registro do pane existe em `mission_panes` (`adapter_id=glm`, `account_id` nulo, `cwd=.harvest/s240-f1303`).
  - A conversa NÃO se perdeu. O transcrito `provider-state/glm/checkout-ef0be…/claude/projects/-Users-…-harvest-s240-f1303/3d11ad03-405d-4bd2-9248-0867239f88e5.jsonl` (810 KB) tem `sessionId` igual ao nome do arquivo, ou seja, o id ditado no spawn das 06:22.
  - Em `provider_pane_sessions` não há NENHUMA linha `glm`, nem desse pane nem de outro. As 248 linhas são 211 `claude`, 26 `codex` e 11 `mimo-code`.
  - As hipóteses do brief foram descartadas:
    - "HOME efêmero apagado": o transcrito mora no overlay durável `provider-state/<adapter>/<checkout>`, não no HOME do pane.
    - "overlay num caminho que o resume não consulta": o resume procura por id na tabela, não no disco.
  - Causa confirmada: o id ditado nunca virou linha. O lookup de resume (`#resumeSessionForPane`) e a cópia para o pane novo (`copyProviderPaneSession`) já aceitam qualquer adapter; faltava só gravar.
  - RED (fonte anterior), `usage-service-execution-roots.test.ts` › "F-1353…": `expected "vi.fn()" to be called with arguments … Number of calls: 0`.
- (resolvedor) Correcao:
  - Causa raiz: `#onSessionDictated` descartava o id ditado (`--session-id`) de todo adapter sem telemetria de uso. Sem a linha `provider_pane_sessions`, `captureMissionPaneResume` recusava, e o transcrito estava salvo.
  - Fix: para esses adapters, a linha passa a ser gravada com o escopo do token da sessão, o pane e a conta do spawn. A telemetria de uso continua só para `claude`/`codex`.
  - Adapters cobertos (todos com `sessionIdArg` e `resumeIdArgs`): glm, glm-flash, deepseek, longcat, qwen, grok, openclaude e muse-claude.
  - Arquivos: `src/main/usage/usage-service.ts` e `src/main/usage/usage-service-execution-roots.test.ts`.
  - Não feito: o fallback `resume.mode: 'fresh-in-worktree'` para adapters que realmente não guardam conversa recuperável por id. Para o glm a conversa é guardada, então a condição do brief não se aplica a ele. O fallback mexeria no fluxo de `resume` de `tools-panes.ts`, a mesma região do rework→resume (fix/s240-loop) e do F-1334, e ainda precisaria de uma fonte para o brief original. Ver a observação abaixo.
  - Observação: kimi, devin, agy, muse e opencode não têm `sessionIdArg`, e nenhuma linha deles aparece na tabela. O `resume` desses adapters continua recusando. É o candidato natural para o fallback, num F próprio.
  - Limite: o pane `pane-mv51n116-1o`, fechado antes do fix, segue sem linha. A conversa dele só volta à mão: `claude --resume 3d11ad03-…` com o mesmo overlay, na mesma worktree.
