# F-615 — Duas contas Claude exibiam a cota da sessão nativa

## F-615 | categoria: funcional | severidade: alta | status: corrigido
- Tela/fluxo: Ajustes → Uso e cotas; Nexus Redline; escolha automática por
  folga.
- Arquivo:linha: `src/main/adapters/managed-claude-auth.ts`,
  `src/main/quota/claude-account-usage.ts`.
- Passos: 1) Ter duas contas Claude; 2) deixar uma sessão gerenciada vazia ou
  morta; 3) atualizar cotas.
- Esperado: cada linha usa somente credencial ancorada na própria conta; sem
  prova, mostra "Sem leitura".
- Observado: a existência do diretório `auth/` era aceita como credencial.
  `claude /usage` apontado para diretório vazio caía na sessão nativa e copiava
  os mesmos 3% / 73% / 48% para outra conta.
- Evidencia: reprodução local em 21/09/2026 com
  `CLAUDE_SECURESTORAGE_CONFIG_DIR` vazio e comparação com a saída nativa.
- (resolvedor) Correcao: `managedClaudeAuthHasCredential` exige arquivo OAuth
  utilizável ou item Keychain scoped; diretório vazio nunca autoriza a sonda.
  Validação: `npx vitest run
  src/main/adapters/managed-claude-auth.scope-proof.test.ts
  src/main/quota/claude-account-usage.test.ts`.

## Nova reprodução — cache compartilhado (21/09/2026)

- Screenshot do operador: duas contas distintas exibem os mesmos percentuais semanais.
- Mesmo com credencial scoped, `/usage` ainda usava o `CLAUDE_CONFIG_DIR` nativo e seu `cachedUsageUtilization`. O leitor de cache local descartava os UUIDs de identidade antes de validar a cota.
- Correção adicional: cada sonda gerenciada recebe config privado ao lado do auth; cache de perfil exige UUID não vazio e igual entre `oauthAccount` e `cachedUsageUtilization`, além de timestamp não futuro e dentro de 30 minutos.
- Três regressões falharam antes da correção; 22 testes focados passaram depois. Consulta real à API Claude durante a investigação respondeu HTTP 429, portanto validação dos percentuais vivos permanece limitada pelo provider.

## Confirmação real das duas contas — 21/09/2026

- Credenciais salvas vencidas eram reconhecidas como sem login pela CLI; controle com token válido confirmou que os diretórios isolados funcionam.
- A API de perfil confirmou a conta b nativa. Seu próprio perfil gerenciado foi recuperado; a sonda de produção retornou 12% nas 5 horas e 75% semanal, com `cliLoggedIn: true`.
- A conta adm retornou `invalid-grant` na renovação e recebeu nova autorização humana isolada. Um primeiro login da conta errada foi recusado antes de materializar. Depois da autorização correta, o servidor confirmou a identidade; a sonda de produção retornou 0% nas 5 horas e 6% semanal, com `cliLoggedIn: true`.
- Novo fallback somente leitura verifica a identidade em `/api/oauth/profile` antes de permitir que uma sessão nativa atual atenda à mesma conta salva com cópia vencida; não renova nem persiste o token nativo.
- Regressões do helper e integração: 29 testes passaram. Matriz expandida: 571 testes em 44 arquivos passaram; typecheck e renderer-sinks passaram.

## Reaberto — credencial gerenciada com identidade trocada (22/09/2026)

- Novos prints do operador: rail e Redline mostram 5h 2% / semanal 86% para **duas linhas Claude com e-mails diferentes**.
- O snapshot Redline tem dois `accountId` distintos mas as mesmas janelas. A credencial gerenciada da linha “Conta Claude” respondeu HTTP 200 no endpoint de perfil da Anthropic com o e-mail da linha “retorno”; `/usage` desse token respondeu exatamente 2% / 86%. A sessão gerenciada de “retorno” estava expirada. Nenhum token, fingerprint ou e-mail completo foi impresso.
- A correção anterior checava se o escopo tinha credencial e se o cache local casava seus próprios UUIDs, mas aceitava `/usage` sem provar que o token ainda pertencia à conta rotulada. O read-back gerenciado também podia copiar um blob de outra identidade ao vault pelo critério de frescor.
- Esperado: percentual só entra após prova de identidade do provider para o e-mail da conta; mismatch vira leitura ausente e re-login acionável. Um pane pinado a essa conta não deve usar a credencial de outra.

## Correção do caso reaberto — 22/09/2026

- Linhas Claude salvas só aceitam `/usage` obtido com token cujo perfil no servidor confirma o e-mail da conta. A sonda não publica a saída do CLI quando arquivo e Keychain divergem. Se o item Keychain efetivo existe mas não pode ser lido, a leitura fica indisponível; 401/403 e 429 continuam distintos. Uma prova positiva recente vale só para o mesmo access token e fica apenas em memória.
- A UI, o seletor e o arquivo do Redline ocultam percentuais antigos quando a identidade diverge e pedem novo login. Cache local de utilização não é publicado como leitura fresca sem carregar seu horário real.
- Spawn direto, de missão e por failover exige prova antes de materializar. A materialização recusa item Keychain scoped trocado ou ilegível. Cadastro e re-login Claude consultam o perfil antes de deduplicar, inclusive quando uma linha antiga contém o token da outra; falha na gravação não libera o bloqueio anterior.
- Token vencido sem prova anterior da identidade não tem refresh automático pelo Nexus: a conta pede novo login, preservando a sessão da conta irmã. A CLI continua dona da renovação de seus escopos gerenciados.
- Validação local: testes focados de conta/spawn (280), cota/Redline (50), renderer (58), `npm run typecheck` e `npm run security:renderer-sinks` passaram. O teste dos arquivos alterados e os gates do candidato de release seguem separados.
