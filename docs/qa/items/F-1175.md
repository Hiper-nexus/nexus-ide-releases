# F-1175 — `CommandReceiptStore.acceptCommandEffect` sem chamador de produção: não ligado, com o que falta

## F-1175 | categoria: orquestracao | severidade: baixa | status: documentado (não ligado de propósito)
- Fluxo: recibo de comando + efeito no outbox na mesma transação (ORC-04, porte da política T3 `CommandReceiptStore.ts` @ 26285ab).
- Arquivo:linha:
  - `src/main/orch/command-receipts.ts:284` — `acceptCommandEffect(outbox, receiptInput, effectInput)`.
  - Único chamador fora de teste: `acceptDispatchCheckpointEffect` (`command-receipts.ts:519`), que por sua vez não tem chamador de produção; o próprio docstring diz "Isolated legacy/schema acceptance helper. No production dispatch calls it".
  - Testes que o exercitam: `effect-outbox.test.ts` (aceite, idempotência, conflitos de identidade, F-1073) e `command-physical-settlement.test.ts:60,70` (efeito legado `checkpoint.capture` sem prova fica adiado/podado).
- Histórico (por que hoje não tem chamador):
  - F-1040 (revisão do PR #126) ligou `acceptCommandEffect` em `dispatchToolCall`: recibo + `checkpoint.capture` antes do handler MCP.
  - F-1084 (`029241de6`, "record bounded logical dispatch lifecycle") tirou essa ligação de propósito: o `checkpoint.capture` genérico "pretendia completar o handler" sem provar captura Git nem término do processo. O despacho MCP passou a usar `acceptDispatchObservation` (recibo `dispatch.observation` com sequência de evento SQLite real) e, para processos próprios, `dispatch.physical-settlement` com prova de saída. O handler de `checkpoint.capture` registrado no boot (`registerUnprovenCheckpointHandler`, `orchestration-coordinator.ts:91`) só adia: nunca fabrica prova.
  - O checkpoint Git real do fim de turno é outro caminho (`handoff-checkpoint.ts` → `captureHiddenCheckpoint`) e não passa pelo outbox — o que o F-1173 expõe na tela.
- Candidato natural investigado: comando de missão do renderer (`ORCH_CHANNELS.missionCommand` → `orch-ipc.ts:2010` → `MissionEngine.command`, `mission-engine.ts:467`). É o único produtor "comando do usuário → efeito" que caberia num recibo idempotente. **Não foi ligado**, porque o desenho não está fechado e ligar muda a semântica da missão:
  1. **Sem identidade de comando:** `missionEngineCommandSchema` (`src/shared/mission-engine-contract.ts:361`) é strict e não tem `commandId`. Um recibo idempotente exige um id estável gerado no renderer por intenção (por clique, reaproveitado no retry). Isso muda o contrato compartilhado, a ponte do preload e todos os chamadores do renderer.
  2. **Efeito sem executor:** os tipos que corresponderiam (`direct` → `turn.steer`, `stop` → `turn.interrupt`, `retry-kickoff` → `turn.restart`, `answer-question` → `runtime-request.respond`) são `PROCESS_BOUND` e não têm handler registrado. O dreno falha de vez efeito sem handler (`effect-outbox-worker.ts:44`). Ligar o recibo sem mover a execução para um handler deixaria uma linha `failed` (ou presa) para cada comando que já foi executado em linha.
  3. **Execução síncrona hoje:** o IPC executa a porta do motor em linha e devolve o `MissionSnapshot` atualizado. Passar pelo outbox tornaria o comando assíncrono (resposta = recibo aceito, efeito depois), mudando o que a tela mostra logo após "Enviar orientação"/"Parar".
  4. **Perda do processo:** `reconcileAfterProcessLoss` (`effect-outbox.ts:667`) cancela `PROCESS_BOUND` pendente ou em execução. Uma orientação aceita com recibo e ainda não executada sumiria num restart do Main com status `cancelled` — hoje ela simplesmente falha na hora e a tela mostra o erro.
  5. **Gate de conclusão:** `assertCompletionEffectsSettled` (`automatic-completion-proof.ts:40`) bloqueia `completeMission` enquanto houver efeito aberto no thread. Efeito de comando do usuário sem dreno prenderia a conclusão da missão (`completion_effects_pending`).
  6. **`stop` e `answer-question`** já têm prova e confirmação próprias (`runOperatorMissionStop` com prova física de saída; `runOperatorClarifyAnswer` com a pergunta durável). Um segundo recibo em volta deles precisaria provar que não duplica nem contradiz essas provas.
- O que falta para ligar com segurança (próxima onda, uma decisão de produto antes):
  - `commandId` opcional no contrato do comando + geração no renderer por intenção, com teste de retry após timeout devolvendo o mesmo recibo.
  - Handlers registrados para os tipos `turn.*` que chamem as portas do motor, com a classe certa (talvez `replay_safe` para `direct` idempotente por id, em vez de `process_bound`).
  - Resposta do IPC: esperar o assentamento com prazo (mantém a tela síncrona) ou expor o recibo e o estado na tela.
  - Teste de integração no ponto de chamada (`orch-ipc` → recibo → dreno → porta do motor), restart no meio, e o gate de conclusão com efeito aberto.
- Decisão desta onda: não ligar. Nenhum código de produção mudou para este item; `acceptCommandEffect` continua coberto pelos testes de contrato.
- Validação (Node 22): `effect-outbox.test.ts` 38/38 e `command-physical-settlement.test.ts` 6/6 continuam verdes no HEAD desta branch. Busca de chamadores: `grep -rn "acceptCommandEffect\|acceptDispatchCheckpointEffect" src` → só `command-receipts.ts` e os dois testes.
