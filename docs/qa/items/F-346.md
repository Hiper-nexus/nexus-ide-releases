# F-346 — Objetivo, título e anexos do projeto A migram para o projeto B e são persistidos lá

## F-346 | categoria: usabilidade | severidade: critica | status: aberto
- Tela/fluxo: trabalhar no projeto A → fechar o projeto → abrir o projeto B pela
  rail.
- Arquivo:linha: `src/renderer/state/mission-setup-store.ts:615-635` e
  `:644-660`; fechamento em `src/renderer/state/product-navigation-store.ts:133`
  (`closeWorkspace: () => open(launcherDestination)`) → `App.tsx:946` monta
  `<MissionSetup home />` → `setWorkspace(null)`.
- Passos: 1) no projeto A, preencher o rascunho (objetivo, título, aceite,
  `contextPaths`); 2) fechar o projeto; 3) abrir o projeto B pela rail, sendo B
  um projeto sem rascunho.
- Esperado: cada projeto ter o seu próprio rascunho.
- Observado: `setWorkspace(null)` **não reseta mais o rascunho** — preserva
  `current.draft` tal qual. O `pending` é então calculado como
  `!current.workspacePath && !draftTextFieldsEmpty(current.draft)`, expressão que
  **não distingue** "texto digitado enquanto não havia pasta" de "sobra da pasta
  que acabei de fechar". Ao abrir B, `applyPending` copia objetivo, título,
  aceite **e `contextPaths`** para o rascunho de B, e
  `persistWorkspaceDraft(B, draft)` **grava isso em localStorage sob a chave de
  B**.

  Duas consequências, e a segunda é a grave:
  1. O formulário de criação de B apresenta o pedido de A como se fosse de B —
     um resultado errado apresentado como correto.
  2. `contextPaths` são caminhos de arquivos **da árvore de A**. Eles são
     entregues a agentes cujo CWD é B, apontando para arquivos que não existem em
     B. E ficaram persistidos: reabrir B amanhã mostra o mesmo estado.
- Evidencia: revisão de código do intervalo `3c61b149..HEAD`, escopo
  `src/renderer/**`. O teste novo em `mission-setup-store.test.ts:168-173`
  ("preserva a ideia ao fechar o projeto sem pasta") fixa a **primeira metade**
  desta cadeia — mas nunca abre um segundo projeto em seguida, então a suíte não
  alcança o vazamento. Um teste verde aqui não é evidência de ausência.
- Correcao sugerida: `pending` precisa carregar a procedência. Ou
  `setWorkspace(null)` marca o rascunho como "órfão, não transportável" e só o
  preserva para exibição, ou `pending` guarda o `workspacePath` de origem e
  `applyPending` recusa quando o destino é um projeto diferente. A segunda opção
  também resolve F-345, porque torna explícito o caso "digitei sem pasta" versus
  "sobrou de outra pasta".
- Por que não foi corrigido aqui: mesmo motivo de F-345 — arquivo de outra sessão
  ativa nesta área, com testes que ela escreveu.
- Bloqueia release? **Sim.** É contaminação durável entre projetos, e entrega a
  agentes caminhos de uma árvore que não é a deles.
- Relacionado: F-345 (a mesma transferência de `pending` no outro sentido),
  F-347 (a terceira regressão deste intervalo em estado de missão/pane).
