# F-1384 — `index.lock` órfão de 0 byte nas worktrees de writer

## F-1384 | categoria: funcional | severidade: media | status: corrigido
- Tela/fluxo: writers e o orquestrador recebem `fatal: Unable to create '.git/worktrees/<writer>/index.lock': File exists` em `git add`/`git checkout`. O lock tem 0 byte e não há processo git vivo.
- Arquivo:linha (antes): `src/main/runtime/git-command.ts`.
  - `AsyncProcessGitRunner.run` usava `killSignal: 'SIGKILL'` no timeout.
  - `safeGitEnvironment` não desligava os locks opcionais, então todo `git status` do Nexus regravava o index da worktree.
- Passos e observado (ao vivo, 12/10): o lock apareceu às 07:01, 07:14, 07:41 e 08:06 em `.git/worktrees/<writer>/index.lock`, sempre com 0 byte e sem dono.
- Esperado: nenhum git do Nexus deixa lock na worktree de um writer.
- Evidencia e causa confirmada:
  - A hipótese do checkpoint NÃO se confirma. O checkpoint oculto (`hidden-checkpoint.ts`) e a salvaguarda (`isolated-writer-salvage.ts`) já usam índice privado (`GIT_INDEX_FILE` em `nexus-git-index-*` no tmp) e nunca tocam o index da worktree.
  - Causa confirmada:
    - O runner assíncrono do Nexus mata o git no timeout com SIGKILL. O Git só apaga os lockfiles quando trata o sinal, e com SIGKILL ele não roda essa limpeza.
    - Reprodução manual: um `git add` segurado por um filtro clean lento, morto com `kill -9`, deixa `.git/index.lock` com 0 byte (o mesmo do incidente). Com `kill -TERM`, o Git apaga o lock.
  - Por que o lock existia: o `git status` do Nexus regravava o index da worktree (refresh opcional). Isso cria `index.lock` e o renomeia; o inode do index muda a cada `status`.
  - Quem roda git na worktree do writer na hora da entrega:
    - `collectFilesModified` (`worker-files-modified.ts`, chamado pela via rápida na entrega) roda `git status --porcelain` com `timeoutMs: 5_000` e SIGKILL.
    - Também rodam `worker-delivery-evidence`, `integration-review-gate`, `tools-git` (status) e o portão de regressão.
    - Numa worktree grande, com a máquina em swap, 5 s estoura.
  - RED (fonte anterior), `src/main/runtime/git-command.test.ts` › "F-1384…":
    - "Git que estoura o timeout do runner sai limpando o próprio index.lock": `expected true to be false`. O lock ficou.
    - "git status do Nexus não regrava o index da worktree": `expected 169894537 to be 169894507`. O inode mudou, ou seja, o index foi regravado via `index.lock`.
- (resolvedor) Correcao (`src/main/runtime/git-command.ts`):
  - `safeGitEnvironment` passa `GIT_OPTIONAL_LOCKS=0` a todo git do Nexus. Leitura (`status`, `diff`) não pega mais o `index.lock` da worktree. Locks obrigatórios (`add`, `commit`, `checkout`) não mudam.
  - O timeout do `AsyncProcessGitRunner` mata com SIGTERM. O Git trata o sinal, apaga os próprios lockfiles e sai. O `ProcessGitRunner` (spawnSync) já usava SIGTERM, o padrão.
- Fora do escopo:
  - Git rodado pela própria CLI do worker (rodapé de branch do TUI, `git status` do agente) e morto pelo kill da árvore no fechamento do pane não passa por este runner.
  - Não foi feita limpeza automática de lock órfão. Provar "sem processo vivo" exige inspecionar processos, e um `git add` longo também segura um lock de 0 byte.
- Validacao:
  - Depois do fix: `git-command` 13/13 (11 + 2 novos).
  - Vizinhos: `hidden-checkpoint`, `isolated-writer-salvage`, `handoff-checkpoint` e `worktree-manager`. Nos 5 arquivos, 99/99.
  - `tsc --noEmit -p tsconfig.json` (com F-1381 junto): 0 erros.
