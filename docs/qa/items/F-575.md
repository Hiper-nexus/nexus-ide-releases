# F-575 — Pane Claude abre "Not logged in" e o /login nunca persiste (keychain invisível no HOME efêmero)

## F-575 | categoria: funcional | severidade: alta | status: corrigido

- Tela/fluxo: qualquer pane do Claude nativo aberto pela mão do operador
  ("+ Pane", terminal de login de conta, operator-choice) — o fluxo padrão de
  uso diário.
- Arquivo:linha: `src/main/orch/mcp-server.ts:1080` (HOME efêmero
  incondicional para `usesClaudeHomeLayout` desde o F-567, 0.76.45);
  `src/main/orch/hooks-gen.ts` `prepareEphemeralHome`.
- Passos: 1) abrir um pane Claude; 2) o CLI sobe com
  "Not logged in · Run /login" mesmo com a máquina autenticada
  (`claude auth status` → `loggedIn: true` no shell real); 3) fazer /login
  dentro do pane; 4) fechar e reabrir — volta a pedir login.
- Esperado: pane nativo enxerga a sessão da assinatura (Keychain) e um /login
  feito dentro dele persiste como num terminal comum.
- Observado: "Not logged in" em todo pane novo; login dentro do pane some com
  o overlay — "o Nexus não segura o terminal Claude".
- Causa (reproduzida nesta máquina, 17/09): o macOS monta a lista de busca de
  keychains a partir do `$HOME` **do processo** —
  `~/Library/Keychains/*.keychain-db`. Com `HOME=~/.nexus/ephemeral/<token>`
  (F-567 estendeu o HOME privado a TODOS os panes Claude), o login keychain
  real sai da busca: `security list-keychains` no HOME efêmero mostra só
  `/Library/Keychains/System.keychain`. Sem o item "Claude Code-credentials"
  o CLI reporta `loggedIn: false`, e um /login grava a credencial num
  `login.keychain-db` descartável dentro do overlay — apagado no teardown,
  antes mesmo de qualquer sync-back. Panoramas:
  - `HOME=<efêmero> claude auth status` → `"loggedIn": false`;
  - `HOME=<efêmero> security find-generic-password -s "Claude
    Code-credentials"` → item não encontrado;
  - com `Library/Keychains/login.keychain-db` linkado → `loggedIn: true` com
    o e-mail da conta, e `security add-generic-password` no HOME efêmero
    grava no keychain REAL (verificado).
- Por que só os panes da mão quebravam: workers/orquestradores gated recebem
  `CLAUDE_CODE_OAUTH_TOKEN` por env (`isolatedHome` ⇒
  `nativeClaudeSubscriptionEnv`), caminho deliberado da 0.19.30. O pane
  direto tem `isolatedHome=false` (mesmo predicado de `shouldUseEphemeralHome`)
  — sem token E sem keychain. No Linux/Windows o problema não existe: o
  segredo é `~/.claude/.credentials.json`, já linkado no overlay.
- Correção (`hooks-gen.ts`): quando o overlay carrega a identidade nativa
  (`carryNativeClaudeAuth`) e o pane NÃO é gated por hooks
  (`gateHooks === false` — o mesmo sinal que decide o token de env), o
  `prepareEphemeralHome` linka cada `*.keychain-db` de
  `~/Library/Keychains` para `<overlay>/Library/Keychains/` (helper
  `linkDarwinUserKeychains`, darwin-only, best-effort por arquivo). Leitura e
  escrita atravessam o link: o pane usa a linhagem viva do perfil real —
  refresh compartilhado com o CLI nativo e os demais panes, /login
  persistindo no keychain de verdade. É a semântica exata do HOME real de
  antes do F-567.
- Limites deliberados: panes gated seguem no token de env (superfície mínima
  — o keychain inteiro num worker seria exposição sem ganho); overlay de
  terceiro (`gateHooks` false mas sem `carryNativeClaudeAuth`) nunca recebe o
  link; nenhum grant de sandbox novo é necessário — panes não-gated não são
  Seatbelt e os gated não recebem o link. Sync-back de `.credentials.json` /
  identidade (overlay-auth-syncback) permanece como estava: no macOS o
  /login vai direto ao keychain e o arquivo nunca materializa no overlay.
- Evidência RED→GREEN: os 4 testes novos em
  `hooks-gen.claude-auth.test.ts` falhavam antes da correção (link ausente);
  depois, 21/21 no arquivo, 84/84 nos arquivos focados (hooks-gen*, spawn-
  home-policy, mcp-server-governed-profile). `npm run typecheck` limpo.
  Reprodução manual do fluxo inteiro documentada acima com `security` e
  `claude auth status`.
