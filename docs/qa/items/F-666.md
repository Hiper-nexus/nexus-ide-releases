# F-666 — Worker Codex em worktree isolada morria em 15 s no Windows (e, vivo, não conseguia rodar nada)

## F-666 | categoria: funcional | severidade: alta | status: corrigido
- Tela/fluxo: Windows, Codex 0.157.1. Orquestrador da missão abre um writer Codex (`nexus_pane_spawn` com `executionMode: isolated_worktree`), que roda no perfil governado (`prepareCodexGovernedSession`).
- Arquivo:linha: `src/main/orch/cli-prompt-autoresponder.ts` (sem assinatura para o "Folder access" do Codex), `src/main/orch/cli-mcp-session-codex.ts` (`features.code_mode_host = false` no perfil governado).
- Passos: 1) Missão da aba no hipergo. 2) Orquestrador solta um helper Codex para escrever em paralelo.
- Esperado: o Codex abre na worktree, recebe o brief e executa.
- Observado (28/09 12:11): `pane-muldy6m4-4` (codex, gpt-6-sol) ficou ocioso em 0,9 s e morreu aos 15 s sem nenhum log; o orquestrador concluiu que "todo executor roda em Codex e quebra" e seguiu sozinho.
- Evidencia: sonda com o perfil governado real numa worktree: o Codex 0.157 abre "Folder access — 1. Open restricted / 2. Quit (enter continue · esc quit)" para pasta `trust_level = "untrusted"` (o perfil marca assim de propósito) e ninguém respondia; o brief caía no modal. Passando da tela, o primeiro comando falhava com "code-mode host is disabled": o Codex instalado executa toda ferramenta pelo code-mode host, que o perfil governado desliga. Com o host ligado o mesmo comando roda.
- (resolvedor) Correcao: assinatura `codex-folder-access-restricted` lê a tela e leva o cursor até "Open restricted" (nunca "Trust and continue"), segurando o brief enquanto a tela está aberta; `codexGovernedCodeModeHost()` liga o host no Windows (o macOS governa o binário fixado e mantém desligado). Testes: `cli-prompt-autoresponder.test.ts` ("Folder access" F-666), `cli-mcp-session-codex.test.ts` (code-mode host F-666). Sonda manual com o Codex real: tela respondida e comando executado.
