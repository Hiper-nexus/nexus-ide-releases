# F-338 — Tokens de status ficam em 2.3:1 no tema claro, abaixo dos 3:1 que o DESIGN.md afirma

## F-338 | categoria: visual | severidade: alta | status: corrigido
- Tela/fluxo: `nexus-light` — pontos de estado de agente (6pt), pills de status,
  palavras de status na rail, na timeline e no board.
- Arquivo:linha: `src/renderer/styles/base.css:273-291` (bloco
  `[data-theme='nexus-light']`, que não declara nenhum `--status-*`) contra
  `src/renderer/styles/base.css:53-57` e `:70-77` (valores `:root`).
- Passos: 1) selecionar `nexus-light`; 2) medir o contraste de `--status-*` e
  `--status-dot-*` contra `--bg` (`#f7f8fb`) e `--bg-elevated` (`#ffffff`).
- Esperado: `DESIGN.md` §2, linha "Pontos de estado de agente (6pt)":
  "Croma 90%, **WCAG 3:1**". E §2 na família de status: "saturação sRGB ~55-60%".
- Observado: os tokens da banda **escura** são usados sem ajuste num fundo claro.
  Contraste medido contra `#ffffff`:

  | Token | Valor | vs `#ffffff` |
  |---|---|---|
  | `--status-success` | `#6cb17b` | **2.56:1** |
  | `--status-danger` | `#d8847b` | **2.80:1** |
  | `--status-warning` | `#c09664` | **2.70:1** |
  | `--status-merged` | `#a890d5` | **2.76:1** |
  | `--status-dot-success` | `#35c264` | **2.32:1** |
  | `--status-dot-danger` | `#f7796d` | **2.65:1** |
  | `--status-dot-warning` | `#db932e` | **2.55:1** |

  Todos abaixo do piso de 3:1 que o documento afirma. Contra `--bg` (`#f7f8fb`)
  é marginalmente pior. São 21 pares reprovados (7 tokens × `--bg`,
  `--bg-elevated`, `--bg-bar`).

  A causa é a banda de lightness: os tokens foram gerados em L=0.70 (pills) e
  L=0.72 (dots), o que é correto para superfícies escuras — onde medem
  5.9:1 a 8.5:1 — e insuficiente para superfícies claras.
- Evidencia: `npm run design:palette-check` → `"count": 21`, `"F-338": 21`,
  `ok: true` porque todos estão na lista de gaps conhecidos do gate.
  `src/renderer/styles/palette-gen.test.ts` › "the dark status band therefore
  fails 3:1 on the light background — F-338" fixa a falha como expectativa, para
  que ela não suma em silêncio nem seja "corrigida" por acidente.
- Correcao proposta (não aplicada): a banda clara já existe e já foi validada em
  `src/renderer/styles/palette-gen.ts` como `LIGHT_STATUS_BAND` (L=0.50, croma
  60% do gamut max) e `LIGHT_STATUS_DOT_BAND` (L=0.62, croma 90%). Ela gera:

  | Token | Banda clara |
  |---|---|
  | `--status-success` | `#3e704a` |
  | `--status-danger` | `#9d433b` |
  | `--status-warning` | `#7b5d39` |
  | `--status-merged` | `#7347af` |
  | `--status-dot-success` | `#299f51` |
  | `--status-dot-danger` | `#f12e2f` |
  | `--status-dot-warning` | `#b37824` |

  O teste "the generated light band clears 3:1 on the same background" confirma
  que esses valores passam contra `#f7f8fb` e `#ffffff`. Aplicar é acrescentar o
  bloco ao `[data-theme='nexus-light']` — `renderPaletteCss(generatePalette(
  GENERATED_LIGHT_STATUS_TOKENS))` emite o CSS pronto.
- Correcao aplicada (junto com F-337, porque separadas se quebravam):
  `base.css` passou a declarar no bloco `[data-theme='nexus-light']` os sete
  tokens da banda clara — pills `--status-success #3e704a`, `--status-danger
  #9d433b`, `--status-warning #7b5d39`, `--status-merged #7347af` (L=0.50, croma
  60% do gamut) e dots `--status-dot-success #228845`, `--status-dot-danger
  #d02727`, `--status-dot-warning #9a671d`.
  **O L dos dots é 0.555, não o 0.62 que a regra daria sobre branco puro.** A
  diferença é consequência direta de F-337: com a rampa clara descendo a
  `--surface-3 #cdd5e2` (L=0.871), um dot em L=0.62 mede **2.30:1** sobre ela —
  abaixo do piso. A doutrina deriva lightness do piso de contraste contra as
  superfícies onde o token realmente pousa, então o piso aqui é `--surface-3`, e
  0.555 é o L mais alto em que os três hues ainda passam 3:1 em todas.
  Pior caso medido depois da correção, todos sobre `--surface-3`: success 3.92 ·
  danger 4.31 · warning 4.10 · merged 4.37 · dot-success **3.04** · dot-danger
  3.55 · dot-warning 3.28. `dot-success` passa com 0.04 de folga de propósito — é
  o token vinculante, como `success` é na banda escura.
- Validacao: `npm run design:palette-check` → exit 0 com `findings: 0` e
  `knownGaps: 0`. Os 21 gaps registrados sob este finding foram removidos do
  `KNOWN_GAPS` do gate, e `check-palette-contrast.test.mjs` agora assera que o
  conjunto de gaps é **vazio** — então o próximo tema adicionado começa como
  finding, não como gap aceito. `palette-gen.test.ts` inverteu os dois testes que
  fixavam a falha (eles diziam no próprio comentário "when this is fixed, this
  test must be inverted") e passou a asserar que os valores declarados no CSS são
  exatamente os que `generatePalette(GENERATED_LIGHT_STATUS_TOKENS)` produz.
  82 testes verdes no conjunto de estilos + gates.
