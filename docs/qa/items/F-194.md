# F-194 — Jev mandava quase toda tarefa delegada para o tier `hard` (o mais caro)

## F-194 | categoria: desempenho | severidade: alta | status: corrigido
- Tela/fluxo: `nexus_route_task` e auto-route do `nexus_pane_spawn` (superfície Jev `taskRouting`).
- Arquivo:linha: `src/main/orch/jev-task-routing.ts` (`TASK_ROUTING_QUESTIONS.tier`); `src/main/orch/route-pipeline.ts` (`scoreRouteCandidate`, termo `cost` do tier `hard`).
- Passos: 1) Delegar tarefas comuns do dia a dia (mapear código só lendo, diagnosticar um teste, revalidar uma correção, implementar uma feature pequena). 2) Ler o `tier` que o Jev devolve.
- Esperado: só trabalho de raciocínio profundo vai para `hard`; o resto vai para `medium`, com modelos mais baratos.
- Observado: no diário do Jev de 25/09 a 28/09, 50 das 72 classificações de tier foram `hard` e nenhuma `easy`. Reavaliei o texto antigo sobre as 78 tarefas reais delegadas no mesmo período (tirei os textos do `audit_events`): 60 `hard`, 10 `medium`, 4 `trivial`, 4 `critical`. Mapeamentos e diagnósticos só leitura iam para o tier mais caro. No tier `hard`, o custo quase não pesava (×0,5 por degrau), então um modelo caro ganhava de um barato com a mesma nota de benchmark.
- Evidencia: `/tmp/nexus-release/jev-eval/results.jsonl` e `results-v2.jsonl` (mesmas 78 tarefas, texto atual × texto novo, chamadas reais ao Jev 1.13); testes abaixo.
- Relacionado: F-189 (benchmark oficial na rota), F-675.
- (resolvedor) Correcao: texto novo da pergunta de tier, com critérios concretos: `trivial` nunca inclui julgar código; `medium` passa a cobrir mapear/diagnosticar código só lendo, conferir poucos achados e revalidar correção pequena; `hard` fica para raciocínio profundo entre muitos componentes e review sênior de diff/branch/release. No mesmo conjunto de 78 tarefas, 32 foram para `hard`, 39 para `medium`, 4 para `trivial` e 3 para `critical`, e a confiança ≥ 0,6 subiu de 55 para 59. O piso de code review (`codeReviewTierFloor`) continua segurando review de código em `hard`. O custo no tier `hard` passou a pesar ×1,5 por degrau (igual ao `medium`), então um modelo barato com nota próxima vence o caro; `critical` continua ×0,5. Testei também um texto novo para a pergunta de esforço: ele subiu o esforço (30 `high` contra 20), então a pergunta de esforço ficou como estava. Testes: `route-pipeline.test.ts` (dois candidatos `hard` com nota próxima: o barato vence; com diferença ≥ 4 pontos, o forte vence).
