# F-1450 — Squad salvo com `ownsPlanDocs` não abria: o rascunho recusava o roster inteiro e o editor não tinha saída (Bug8)

## F-1450 | categoria: funcional | severidade: alta | status: corrigido

- Tela/fluxo: Configurações → Squads → criar/abrir um squad → erro ao abrir / em "Usar integrantes" (relato do cliente no Windows; o mesmo no Mac — código de renderer compartilhado, reproduzido no Darwin).
- Arquivo:linha (após a correção):
  - `src/renderer/state/mission-setup-store.ts:790` (`setRoster` rebaixa `ownsPlanDocs` na fronteira do rascunho), `:800` (membro entra sem o campo).

- Passos (campo 13/10, relato do cliente no Windows):
  1. Criar um squad (ou partir de um builtin de plano / cópia dele, que carrega legitimamente `ownsPlanDocs`).
  2. Abrir o squad salvo (ou tocar "Usar integrantes" no setup da missão).
  3. A abertura falha com erro — e o editor não expõe o campo para remover: beco sem saída, o squad fica inutilizável.
- Esperado: squad salvo abre no editor e em "Usar integrantes"; autoridade de documento de plano continua main-owned (o rascunho não a concede nem a carrega).
- Observado: erro na abertura sem caminho de saída na interface.

## Causa raiz
- Squads salvos carregam legitimamente `ownsPlanDocs`: o schema de `shared/orch-types` o define, os builtin de plano o trazem e as cópias do usuário o herdam.
- O rascunho de mission-setup valida com `strictRosterSchema`, que recusa o campo, e `setRoster` (`mission-setup-store.ts`) recusava o roster INTEIRO por causa dele. Como o editor não expõe `ownsPlanDocs`, o usuário não tinha como remover o campo: erro permanente num squad válido.

## Correção
- `mission-setup-store.ts`: `setRoster` rebaixa `ownsPlanDocs` na fronteira do rascunho — cada membro entra sem o campo (destructure em `:800`). Rebaixar não concede nada: o rascunho simplesmente não carrega a autoridade, que segue main-owned.
- O schema persistido continua recusando `ownsPlanDocs` onde ele não é legítimo: a fronteira de persistência não foi tocada, só a entrada no rascunho.
