# F-564 — Publicação macOS não tem caminho próprio no publicador

## F-564 | categoria: processo | severidade: media | status: aberto
- Tela/fluxo: release manual de uma versão que só tem candidato macOS, sem
  build Windows na mesma versão.
- Arquivo:linha: `scripts/publish-release.mjs:1220`
  (`if (authoritative) requireWindowsRunId(environment);`, dentro de
  `publishManualReleaseCore`, aberto em `:1211`, com `authoritative` definido em
  `:1214-1216`), `scripts/windows-release-candidate.mjs:35-39`
  (`requireWindowsRunId` exige `NEXUS_WINDOWS_RELEASE_RUN_ID` casando
  `/^[1-9]\d*$/` e falha com "Mac-only publication is disabled"),
  `scripts/publish-release.mjs:1329-1332` (o caminho autoritativo carrega o
  candidato Windows assinado, sem ramo macOS-only) e `:1338` (compõe os assets
  Windows no pacote), `package.json` (existem `release:publish` e
  `release:publish:windows`; **não** existe `release:publish:macos`) e a
  doutrina em `docs/RELEASE.md:6,38,93,100-101`.
- Passos:
  1) Com a versão já no commit final e o candidato macOS materializado, rodar
     `npm run release:publish` sem `NEXUS_WINDOWS_RELEASE_RUN_ID`.
  2) Observar onde o publicador para.
  3) Rota executada hoje no lugar: publicar à mão, espelhando a sequência do
     script.
- Esperado: um alvo selado `npm run release:publish:macos`, que não exija run
  Windows, com as mesmas provas da publicação canônica: recibo do gate de
  release e SHA-256 conferido nos dois repositórios (canônica e espelho).
- Observado: não existe caminho macOS-only no publicador. `publish-release.mjs`
  para fail-closed em `:1220`, antes de qualquer upload, com
  "Mac-only publication is disabled" (`windows-release-candidate.mjs:37`).
  A doutrina vigente é explícita em bloquear, e não em permitir: candidato
  Windows assinado obrigatório (`RELEASE.md:6`), "Sem worker válido, a
  publicação Mac também é bloqueada" (`RELEASE.md:100`) e "As duas plataformas
  entram na mesma transação de drafts já existente" (`RELEASE.md:101`), com o
  espelho recebendo DMG, ZIP, Setup Windows x64, NUPKG completo e `RELEASES`
  (`RELEASE.md:38`).
  Resultado prático em 2026-09-16: a 0.76.42, que só tinha candidato macOS, foi
  publicada à mão espelhando o script — draft → upload `--clobber` → edit
  `--draft=false`, canônica primeiro e só então o espelho, 9 assets na canônica
  e apenas DMG/ZIP no espelho (o espelho ficou sem os assets Windows que
  `RELEASE.md:38` descreve como estado publicado).
- Evidencia: recusa determinística no código citado, sem depender de estado de
  máquina — `requireWindowsRunId` (`scripts/windows-release-candidate.mjs:35-39`)
  roda sempre que `authoritative` (`scripts/publish-release.mjs:1214-1220`);
  relato do operador da sessão manual de publicação da 0.76.42 em 2026-09-16;
  `docs/RELEASE.md:59` ("A existência do workflow não prova que o worker CKA já
  foi provisionado") confirma que a dependência é de infraestrutura externa, não
  só de código — sem CKA, nenhuma plataforma publica.
- (resolvedor) Correcao: ainda não preenchida — finding aberto, e o caminho
  depende de decisão de doutrina, porque hoje o bloqueio é intencional:
  (a) criar o alvo macOS-only com caminho fail-closed próprio e provas
  equivalentes (recibo do gate, SHA-256 na canônica e no espelho), o que exige
  editar `docs/RELEASE.md:6,93,100-101` para admitir publicação de uma
  plataforma só; ou (b) declarar em `docs/RELEASE.md` que release só-macOS não é
  suportada e que a publicação manual não é rota aceita — e o achado passa a ser
  documentação, não código. Sem essa decisão, a única saída continua sendo a
  sequência manual de hoje, que não deixa recibo nem gate.
