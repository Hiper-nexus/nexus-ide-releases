### Causa raiz
Duas réguas para a mesma credencial (hipótese 3 do pedido):
1. A cota (F-1416) só pede re-login com prova: a própria CLI recusou a sessão,
   ou não existe refresh token no prazo. O spawn (F-639) pedia re-login quando
   o run da CLI não trocava o blob. Os casos "não renovou" e "recusou" davam o
   mesmo resultado, e o resultado do probe da CLI era descartado.
2. Conta só no cofre (Reserva, sem escopo) nunca era renovada no spawn
   (hipótese 2). O `ensureFreshClaudeSubscription` renova essa linhagem por
   HTTP, mas só a cota e o sweeper o chamavam, e o sweeper pula segredos fora
   do cache no boot frio.
3. Quando a conta precisava mesmo de login, nada marcava a linha: o painel
   seguia "Em uso" sem «Entrar novamente».

A hipótese 1 (o spawn atribuir à conta b a expiração da conta adm) foi
descartada. O spawn lê o escopo e o cofre da própria conta b
(`claudeAccountIsNativeLogin` é falso para ela) e o erro nomeia a conta cuja
credencial ele leu.

### Por que "expirou" sem ter expirado
O access token do Claude vence em horas. Uma conta parada a noite inteira
amanhece com o access token vencido e o refresh token vivo, e a CLI renova no
primeiro uso. Isso é o estado normal de uma conta logada. O Nexus confundia
esse estado com sessão perdida.

### Correção
- `verifyManagedClaudeAccountForSpawn` passou a devolver
  `ClaudeSpawnIdentity`, que tem um veredito novo, `renewable`. Ele vale quando
  o access token está vencido pelo relógio (ou dentro do skew), o refresh token
  está no prazo, não houve falha de refresh recente, a linhagem não aparece em
  outro store (login nativo ou outra linha do cofre: F-615/F-645), o candidato
  está no escopo gerenciado cuja CLI é dona da renovação e o refresh token dele
  é o MESMO que o cofre provou para esta conta. O relógio não diz de quem é um
  token vencido: um escopo com outra linhagem (um `/login` de outra conta
  dentro de um pane, por exemplo) nunca abre sem prova. Com `renewable` o pane
  abre com esse blob fixado (`expectedClaudeBlob`, F-1401) e a CLI dele renova
  sob o lock dela. O Nexus não rotaciona essa linhagem.
- Conta sem dono CLI (Reserva só no cofre, ou escopo com OUTRA linhagem mais
  velha que o cofre): o spawn chama `ensureFreshClaudeSubscription`. Ela renova
  por HTTP com todas as guardas e prova a conta no token novo antes de gravá-lo
  no cofre. O login nativo nunca passa por esse caminho.
- Prova de sessão morta: a CLI recusou ESTA linhagem no run de renovação (com
  o store legível depois do run, porque Keychain negado também diz "not logged
  in"), ou o access token venceu pelo relógio sem refresh token no prazo. Com a
  prova, `markClaudeSessionExpired` grava o mesmo cooldown de auth de 12 h da
  sonda de cota ("oauth session expired — pane Claude"). Assim `needsRelogin`
  liga e a linha da conta certa mostra "sessão expirada" com «Entrar
  novamente». A marca nunca sobrescreve um cooldown vivo (quarentena de
  identidade, limite de uso) e não sai se um re-login chegou durante a
  verificação. A limpeza segue os caminhos que já existem: novo login,
  renovação provada (`settleRenewedClaudeCredential`) ou leitura saudável da cota
  (`clearRefutedAuthCooldown`).
- 401/403 sobre token ainda no prazo continua recusando, mas não marca: o
  mesmo código vem de token sem o escopo `user:profile`.
- O run de renovação do login nativo usa `nativeProfile: true`, como a cota,
  sem herdar config dir nem token de outra conta do processo Main.
- Mensagem do pane: "A sessão de “X” expirou — use «Entrar novamente» nessa
  conta em Configurações › Contas de IA."
- Um clique a partir do pane (pedido do operador: "deveria então pedir login já
  que não está logado"). A recusa que se resolve com login (sessão expirada ou
  credencial de outra conta) devolve ao renderer a conta a reautenticar. Viajam
  só o adapter, o id e o rótulo (`AccountReloginRequest`, lista de permissão
  por zod), nunca e-mail ou token. O cartão "Não subiu" diz "A conta precisa
  entrar de novo" e mostra «Entrar novamente em “conta b”». O clique leva a
  Contas de IA e pede o login dessa conta. Quem abre o terminal de login
  continua sendo o `AccountsManager`, pelo mesmo caminho da linha: guarda a
  sessão atual antes, colhe o baseline e prova o login novo com
  `cliLoginProvedNewSession`. O pedido é consumido uma vez, só pela CLI dele, e
  vence em 60 s.
- Fora do escopo (sem mudança): 401 do provedor sobre token ainda no prazo
  continua recusando sem marcar, e a conta que é o login nativo continua só com
  o run da CLI no store nativo.

### Lacunas que ficam
- Escopo cuja CLI girou o refresh token à frente do cofre (o app fechou antes
  do read-back de 15 min) é indistinguível do escopo de outra conta enquanto o
  token está vencido. Ele recusa como `auth-unproven` ("Não deu para
  confirmar…", sem marca de 12 h e sem o botão). Isso falha fechado, de propósito: abrir um pane
  como outra conta é pior que pedir um login a mais.
- O run de renovação (`claude --print … /usage` no escopo) não regravou o
  Keychain do escopo da conta b em 22/10. A sonda de cota depende do mesmo run.
  Falta medir, com o Claude Code 2.1.308, se esse modo renova o token. Se não
  renovar, a cota de uma conta parada fica "indisponível" até um pane abrir.
- A conta só no cofre com refresh token morto só ganha a marca de 2 min de
  `markClaudeRefreshFailed`: o refresh HTTP (`refreshClaudeOauthBlob`) não
  separa `invalid_grant` de falha de rede. `refreshClaudeOauthBlobDetailed` já
  faz essa separação e pode ser usado para gravar o cooldown de 12 h só no
  `invalid_grant`.
