# F-1537 — Pane Codex não aceitava tecla nenhuma: lane do teclado congelada no snapshot do spawn e teclado morto após hibernação

## F-1537 | categoria: funcional/usabilidade | severidade: alta | status: corrigido
- Tela/fluxo: terminal do renderer (xterm do pane) → escrita no PTY (lane do operador via `orch.sendPaneOperatorInput` ou lane crua `pty.write`). Visto num pane Codex no Windows que abriu diálogo interativo (Folder access/approval) — o operador não conseguia digitar nada no pane.
- Arquivo:linha (após a correção):
  - `src/renderer/terminal/terminal-host.ts:1121` (`handlePaneKeyboardInput` — handler único do teclado, resolve o pane VIVO do layout por id a cada tecla).
  - `src/renderer/terminal/terminal-host.ts:1829` (startSpawn registra o handler via `handlePaneKeyboardInput`; o corpo inline de ~120 linhas foi extraído).
  - `src/renderer/terminal/terminal-host.ts:4491` (`deliverPaneUserInput` — roteador único de entrada: lane lida do estado ATUAL, lane crua CONFIRMADA (`writeConfirmed`) com fallback para a lane do operador, nunca fire-and-forget mudo).
  - `src/renderer/terminal/terminal-host.ts:2376-2388` (rehydrateHost religa teclado + `wireTermInteractions` no xterm novo).
  - `src/renderer/terminal/terminal-host.ts:2812` (`wireTermInteractions` — wiring do TERMO (parked-wake, ⌘C/⌘End) separado do wiring do ELEMENTO, para poder religar na reidratação).
  - `src/renderer/terminal/terminal-host.ts:4610` (portas `write:` de submit-prompt usam `deliverPaneUserInput`).
  - `src/renderer/components/CommandBlockMenu.tsx:250-262` ("Inserir" do histórico usa `writeToPane` — mesma rota do teclado; antes escrevia cruo fire-and-forget com toast de sucesso mesmo se o main recusasse).
- Passos (campo 14/10, Windows):
  1. **(A)** Pane cli-agent aberto sem papel/missão ("+ Pane" direto) é promovido a orquestrador ou adotado por missão da aba SEM respawn ("Tornar orquestrador", `adoptUserAgentSessionAsMissionOrchestrator` no Main muda `session.agent.role` no PTY vivo; o renderer só atualiza stores).
  2. O listener `onData` do xterm capturou o `pane` e o `missionId` NO SPAWN: a lane continuava "crua" para sempre. A tecla ia por `pty.write` (fire-and-forget, retorno booleano descartado).
  3. O Main recusa `writeSession` em sessão governada (`agent.role !== 'user'`) — recusa silenciosa: o aviso amarelo "[nexus] o main recusou a digitação" só existia no caminho `sendOperatorInputOrNotify`. Nada chega ao Codex.
  4. **(B)** Pane cli-agent vivo é hibernado (escondido com ≥ `HIBERNATE_MIN_LIVE_HOSTS` hosts vivos) e volta à tela: `virtualizeHost` descarta o xterm; `rehydrateHost` só religava `wireHostTerminalListeners` (título+scroll). O `onData` do teclado, o wheel, o handler de tecla custom e o paste eram registrados por spawn e morriam com o xterm antigo. O pane reidratado aceita foco e engole TODA tecla/paste em silêncio — o CLI parado num diálogo (Folder access F-666, aprovação, pergunta) nunca recebe resposta.
- Esperado: a lane de cada tecla segue o estado ATUAL do pane (layout + `paneMissions`), igual ao `writeToPane`; escrita crua é confirmada e, se recusada, cai na lane do operador com aviso throttle quando ambas recusam; um pane reidratado digita e cola como antes de hibernar.
- Observado: pane com foco que não aceita tecla nenhuma; sem erro, sem aviso, sem toast. Reproduzível em duas classes de pane: promovido/adotado em voo (A) e hibernado/reidratado (B).
- Evidencia: leitura do fluxo (renderer `terminal-host.ts`, `pane-input-route.ts`; Main `orch-ipc.ts` handler `paneOperatorInput`, `pty-manager.ts` `writeSession`/`orchWriteSession`) + testes RED→GREEN abaixo. Nenhum gate de `readOnly`/`busy` bloqueia stdin no Main — a perda é toda no renderer.

## Causa raiz
- **(A)** O handler de teclado resolvia a lane UMA vez, no spawn, a partir do snapshot do pane — promoção/adoption em voo não reexecutam `startSpawn`. E o caminho cru usava `pty.write` (send, retorno descartado), sem o fallback/aviso que a lane do operador tem.
- **(B)** `rehydrateHost` reconstruía o xterm mas não religava NENHUM listener de interação do term — só os de título/scroll. `host.spawnStarted` continua true, então nenhum caminho de "spawn de novo" roda.

## Correção
### 1 — handler único que lê o estado vivo (`handlePaneKeyboardInput`)
- O corpo do `onData` do spawn virou função própria; a cada tecla ela reencontra o pane no layout (`listPanes(root).find(id)`, fallback para o snapshot se o pane saiu do layout) e termina em `deliverPaneUserInput(pane.id, host.sessionId, data)`.

### 2 — roteador único de entrada (`deliverPaneUserInput`)
- `paneInputLane(pane, paneMissions[paneId])` lido AGORA (mesma decisão de `writeToPane`): lane do operador → `sendPaneInputOrNotify`; lane crua → `pty.writeConfirmed` (invoke, booleano) e, se recusada → `sendOperatorInputOrNotify` (que já avisa com throttle quando as duas recusam).
- `writeToPane`, `injectStagedPath`/`injectMainStagedPath`, wheel de página da TUI, `scrollPaneToBottom`, portas `write:` dos submit-prompt: todos passam a usar `deliverPaneUserInput`. Escrita crua fire-and-forget restou apenas onde o alvo é um SHELL novo criado pelo próprio chamador (ghost assist, catálogo de ops).

### 3 — reidratação religa o teclado
- `rehydrateHost` registra `handlePaneKeyboardInput` no xterm novo e chama `wireTermInteractions` (wiring do termo: parked-wake, ⌘C/⌘End) — extraído de `wireInteractions`, que mantém só os listeners do ELEMENTO (wheel, paste), registrados uma vez.

### 4 — "Inserir" do histórico não mente mais
- `CommandBlockMenu.insertHistoryCommand` valida sessão e usa `writeToPane` (rota do teclado): em pane governado o comando chega; se nada chega, a rota avisa — antes o toast dizia "Inserido no terminal" com a escrita recusada em silêncio.

## Como foi achado
- Brief do operador (14/10): pane Codex com diálogo interativo no Windows não aceitava teclas. Varredura do fluxo de entrada do renderer (xterm onData → lane → Main) achou as duas classes acima; os gates de Main (`readOnly`/`busy`/voo de término F-659) foram descartados como causa por leitura direta de `pty-manager.ts`/`orch-ipc.ts`.
