# F-1508 — Windows: PATH nunca é relido; CLI instalada com o app aberto fica "não instalada"

## F-1508 | categoria: funcional | severidade: alta | status: corrigido
- Renumerado na integração com a origin (0.76.252): este achado era o F-1454 da frente de squads (nunca publicado) e virou F-1508 para não colidir com a numeração que a origin publicou (F-1436..F-1451).
- Tela/fluxo: Providers › "Reexaminar CLIs" → `rescanAdapterBinaries` → `refreshUserPath` (`src/main/path-resolver.ts`); missão/squad → `mission-orchestrator-runtime.ts:222-226` ("não está instalada ou o binário não está executável").
- Arquivo:linha: `src/main/path-resolver.ts:207` (antes: `if (process.platform === 'win32') return process.env.PATH ?? ''`) e `:312` (antes: a releitura tardia saía na hora no win32); `windowsUserBinDirs` (`:112-122`) sem `%LOCALAPPDATA%\agy\bin`, `%LOCALAPPDATA%\Microsoft\WinGet\Links` e `%ProgramFiles%\nodejs`.
- Passos: 1) Nexus aberto. 2) Instalar uma CLI que entra no PATH do usuário (winget, instalador do agy, Node MSI). 3) "Reexaminar CLIs" e usar o squad com essa CLI.
- Esperado: o reexame enxerga a CLI nova, como um processo novo do Windows enxergaria.
- Observado: a "sonda de PATH" do Windows devolvia o PATH herdado pelo processo do app; o reexame só repetia o que já tinha. A CLI continuava "não instalada" até reiniciar o Nexus (e o reinício do auto-update herda o PATH velho).
- Causa raiz: no Windows não há shell de login para perguntar; o código devolvia o próprio `process.env.PATH`, que nunca muda depois que o processo nasce. O Windows monta o PATH de processos novos a partir do registro (máquina + usuário), e ninguém lia isso.
- Correcao: `probeLoginShellPath` no win32 lê o PATH de máquina e de usuário pelo PowerShell do System32 (`[Environment]::GetEnvironmentVariable('Path', 'Machine'|'User')`, já expandido, saída UTF-8 para nomes como `C:\Users\João`), assíncrono, com prazo e `windowsHide`; entradas vazias ou com `%VAR%` sem valor são descartadas e aspas tiradas. "Reexaminar CLIs" passa a ver o PATH novo. O boot do Windows não espera o PowerShell: a releitura entra em segundo plano (`retryLoginShellPathIfMissed`, que agora roda no win32 e só pede reexame quando o PATH mudou de fato). `windowsUserBinDirs` ganhou as três pastas faltantes. Nenhuma thread bloqueia (só `execFile` assíncrono). Commit: ver `git log --grep F-1508`.
