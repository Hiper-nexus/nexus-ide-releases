# F-1241 — Proveniência fixava a conversa do Codex fresco em qualquer evento, aceitava o thread de outro pane e despejava pins vivos

## F-1241 | categoria: seguranca | severidade: baixa | status: corrigido
- Tela/fluxo: proveniência de edição pelo hook de status (`recordHookEditProvenance`), no pane de CLI sem id de conversa no argv (Codex fresco).
- Arquivo:linha (antes):
  - `src/main/orch/hook-edit-provenance.ts:157-170`: `boundConversation` fixava o `session_id` do primeiro evento de QUALQUER tipo com `session_id`;
  - `:199`: o pin acontecia antes do filtro `tool-complete`;
  - `:54` e `:165-168`: `Map` global com despejo FIFO depois de 1024 sessões, inclusive de panes vivos.
- Relacionado a F-1237. Achado A1 da revisão sênior do `f11f3c746`.
- Passos:
  1. Pane Codex fresco com os hooks mudos (ou antes do SessionStart do CLI).
  2. O agente faz `curl` em `/hook/status` com o próprio bearer, `tool-complete` e o `session_id` do thread de OUTRO pane.
  3. As edições deste pane passam a ser gravadas como da conversa do outro. Quando o outro pane retoma esse thread, o portão de regressão dele conta essas edições como dele: falso bloqueio.
  4. Variante: depois de 1024 spawns, o pin de um pane vivo é despejado e o próximo evento fixa outro id.
- Esperado: só o SessionStart do próprio CLI fixa a conversa. Uma conversa que `provider_pane_sessions` já atribui a outro pane nunca é fixada. O pin vive enquanto a sessão viver.
- Observado: qualquer evento fixava, sem conferir o dono, e o pin podia ser despejado com o pane vivo.
- Evidencia: `hook-edit-provenance.test.ts`, três casos "F-1241". Na fonte anterior:
  - `tool-complete` com o thread de outro pane: `expected 1 to be +0` (fixou e gravou);
  - id de outro pane: a checagem de dono nunca foi chamada e o id foi fixado;
  - depois de 1100 spawns: `expected 1 to be +0` (o pin do pane 0 foi despejado e um thread forjado foi fixado e gravado).
  - `conversation-edit-store.test.ts`, "providerSessionHeldByOtherPane": `TypeError: providerSessionHeldByOtherPane is not a function`.
- (resolvedor) Correcao:
  - Causa: o pin era um atalho de "primeiro evento do canal", sem tipo de evento nem dono, guardado num cache global com despejo.
  - `hook-edit-provenance.ts`:
    - só `session-start` (Codex) e `session` (Kimi/Grok) fixam. Os demais eventos só concordam com um pin já existente;
    - antes de fixar, `heldByOtherPane` consulta `providerSessionHeldByOtherPane(adapterId, id, paneId)`. Se outro pane já tem o id, não fixa;
    - o pin agora fica num `WeakMap` chaveado pelo objeto de conversa (`providerConversation`) que o `Session` do pty-manager guarda. Ele vive e morre com a sessão viva. Respawn cria outro objeto, logo outro pin. Não há despejo.
  - `pty-manager.ts`: `SessionProviderConversation` ganha `paneId`, o pane dono da sessão.
  - `provider-session-store.ts`, `providerSessionHeldByOtherPane`:
    - procura linha com o mesmo adapter, o mesmo `session_id` e `pane_id` diferente;
    - não filtra por escopo, de propósito: o id da conversa é global, e a linha pode ter sido gravada com o escopo de execução ou com o de coordenação;
    - banco ausente ou erro devolve true: na dúvida, não fixa.
  - Não mudou: conversa com id no argv (`--resume` ou `--session-id` ditado) continua exigindo que o corpo concorde com o argv. Nenhum pin é usado nesse caso.
- Validacao (launchd): `hook-edit-provenance.test.ts`, `conversation-edit-store.test.ts` (SQLite real), `provider-session-store*.test.ts` e `hook-status-endpoint.test.ts`, 63/63. Também o ponta a ponta F-1237 do `pty-manager.test.ts`, que agora confere o `paneId`. Casos novos:
  - `tool-complete` e `user-submit` antes do SessionStart não fixam; depois dele, só o thread fixado grava;
  - o evento `session` (Kimi/Grok) fixa;
  - o id de outro pane é recusado, e o SessionStart legítimo depois ainda fixa;
  - com 1100 spawns no meio, o pin do pane 0 continua e o thread forjado é recusado;
  - SQLite real: id de outro pane (inclusive gravado com outro `checkoutId`) é "de outro"; o do próprio pane, o de outro adapter e o id desconhecido, não.
- Limites:
  - Um agente que mande um `session-start` forjado ANTES do SessionStart do próprio CLI ainda fixa um id que `provider_pane_sessions` não dá a nenhum outro pane. Como o id não é de conversa registrada de outro pane, não culpa ninguém. O pane só perde a própria proveniência (o portão segue a regra do mtime).
  - Se o outro pane ainda não gravou o thread em `provider_pane_sessions`, a checagem não o vê.
