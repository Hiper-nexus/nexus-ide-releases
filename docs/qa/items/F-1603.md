# F-1603 — Panes "piscando" entre Trabalhando/Aguardando sem missão rodando

**Status:** em investigação (repro pendente; monitor ativo)
**Data:** 2026-10-20
**Área:** Main `pty-manager.ts` (busy/idle) + renderer `session-state-store.ts` (hold)

## Sintoma (relato do operador)

Com apenas dois panes de agente abertos (sem missão rodando), o rail
"Terminais" e os chips dos panes alternam entre "Trabalhando" e "Aguardando"
repetidamente ("fica piscando aqui do nada").

Evidência capturada:
- 15:35 (dump AX): Pane 3 (codex gpt-6-astra) "Trabalhando" + contagem
  "1 trabalhando agora"; Pane 2 (Claude Opus 5.5) "Aguardando". Toolbar do
  Pane 3 dizia "Agente pronto — aguardando trabalho" (transição).
- 16:00 (captura do operador): Pane 2 "Trabalhando" (ponto rosa) + Pane 3
  "Aguardando"; contagem segue "1 trabalhando agora".
- 16:43–16:45 (poll passivo de ~2 min): tudo estável em "aguardando" — não
  reproduziu passivamente.

## Modelo do estado (confirmado no código)

1. `pty-manager.ts` `pushOutputEvent` (~1449): **qualquer chunk de saída do
   PTY** marca `session.state = "busy"` e publica `pty:stateChange`. O timer
   de idle (`armIdleTimer`) zera só após `idleTimeoutMs` de silêncio
   (resolveIdleTimeoutMs: type `timeout`.ms ou 800ms por adapter).
2. Renderer `session-state-store.ts`: `displayStates` segura busy 1400ms
   após o idle real (`SESSION_IDLE_DISPLAY_HOLD_MS`) — máscara para gaps
   curtos.
3. Consequência: para piscar, o pane precisa receber rajadas de saída
   espaçadas de >1,4s, repetidamente, sem missão.

## Fontes de atividade verificadas e descartadas

- **Nenhum timer do Main escreve nos panes periodicamente** (todos os call
  sites de `writeSession`/`orchWriteSession` são dirigidos por eventos:
  MCP, handoff, Enter de login, paste).
- **Outbox de handoff** (`handoff-delivery-outbox`, cadência 1s): a tabela
  `handoffs` do runtime do projeto aberto não tem linhas `queued`/por
  entregar (todas `delivered=1, submitted`) — sem candidatos a escrita.
- **DSR/consulta de posição de cursor**: não há envio de `\x1b[6n` etc.
- **Resize periódico**: `resize` só em foco/visibilidade (F-356); winsize
  igual não gera SIGWINCH.

## Hipóteses remanescentes (a confirmar com repro)

- H1: alguma CLI (Claude TUI fullscreen / Codex) repinta a tela numa
  cadência >1,4s quando em estado peculiar (ex.: prompt de confirmação
  pendente, banner, status bar animada) — o que geraria busy real.
- H2: resíduo de handoff "submitted" sem ACK numa sessão alvo ainda viva faz
  o outbox re-tentar entrega (via `onHandoffSubmitted`) para essa sessão.
  (Linhas `submitted` não são re-tentadas; confirmado no código — só
  candidatos não entregues.)
- H3: transições reais (turno chegando ao fim) durante o período observado —
  o "piscar" seria o hold de 1,4s em cada desfecho, amplificado pelo usuário.

## Monitor ativo

Poll de 1s dos rótulos AX do rail (`aguardando`/`trabalhando`) gravado em
`/tmp/nexus-flicker-monitor.log` com epoch — para capturar padrão, cadência e
duração quando voltar a ocorrer. Decisão de correção só após repro com
timestamp.
