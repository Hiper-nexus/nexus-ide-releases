# F-1298 — Worker travado numa chamada ao modelo fica "trabalhando" para sempre (spinner esconde o travamento)

## F-1298 | categoria: funcional | severidade: media | status: precisa-decisao
- Tela/fluxo: supervisão de workers (delegation-supervisor, `decideWorkerHung`, watchdog de zero entrega) e `nexus_mission_control`.
- Passos (visto ao vivo em 12/10, app 0.76.238):
  1. Worker MiMo Code (`mimo-v2.6-pro`) corrigindo F-1260/F-1261 numa worktree `.harvest`.
  2. Às 23:37 ele editou o último arquivo. Daí em diante a TUI só mostrou o spinner animando ("🛸").
  3. Às 00:44 (67 min depois), o processo `mimo` estava com 0% de CPU e nenhum processo filho, preso esperando uma resposta do modelo.
- Esperado: um worker sem progresso real (nenhuma ferramenta, nenhum arquivo, nenhum byte que não seja animação) por N minutos é sinalizado ao Maestro como travado, com o caminho de saída.
- Observado:
  - O pane seguiu `working`/`busy`, porque o spinner produz saída o tempo todo.
  - Nenhum alarme de travamento chegou: o `decideWorkerHung` e o watchdog de zero entrega veem atividade.
  - O Maestro só percebeu comparando o mtime dos arquivos da worktree.
- Evidencia: `ps` do processo do pane (`node …/mimo --trust --model xiaomi/mimo-v2.6-pro …`) com 0% de CPU e sem filhos; worktree sem mudança de 23:37 a 00:44; `nexus_pane_read` repetindo o mesmo texto com frames de spinner.
- Pergunta objetiva (precisa-decisao): qual é o sinal de progresso?
  - Opções para o "travado":
    - eventos de ferramenta do observer (só existem para CLIs com hook de ferramenta);
    - bytes de saída descontando frames de spinner (exige uma regra de spinner por CLI);
    - CPU da árvore de processos (custo de amostragem);
    - mtime da worktree do writer.
  - Cada opção tem falso positivo diferente; por isso não houve correção nesta rodada.
- Contorno usado: fechar o pane travado e concluir o trabalho a partir do diff parcial (F-1261).
