# F-656 — Build Windows morria em "SignerSign() failed" com o TSA da DigiCert instável

## F-656 | categoria: release | severidade: media | status: corrigido
- Tela/fluxo: `npm run make` assinado no Windows (SignTool, `NEXUS_WINDOWS_RELEASE_SIGNING=1`), release 0.76.108.
- Arquivo:linha: `forge.config.ts` (`createWindowsSignOptions`: `timestampServer` fixo em `http://timestamp.digicert.com`).
- Passos: 1) Com o TSA da DigiCert respondendo devagar ou truncado, rodar `npm run make`.
- Esperado: o build assina todos os binários; com o TSA padrão fora, dá para apontar outro servidor RFC 3161 sem editar código.
- Observado (27/09): `SignTool Error: An unexpected internal error has occurred` / `SignerSign() failed. (0x80093102)` — fim inesperado de dados ASN.1 na resposta do carimbo. Duas tentativas seguidas falharam em arquivos diferentes (depois de 12 assinados e depois de 2), então não era um binário específico. `curl` no timestamp.digicert.com: 9,8 s, 0,8 s e timeout de 20 s; Sectigo e GlobalSign respondiam em < 1 s.
- Evidencia: `out/make-076108-try1.log`, `out/make-076108-try2.log`.
- (resolvedor) Correcao: `windowsTimestampServer` lê `NEXUS_WINDOWS_TIMESTAMP_URL` só na execução que a define; só URL http/https é aceita (não dá para desligar o carimbo nem injetar argumento), e sem a variável nada muda — mesmo desenho do F-652 no macOS. Teste em `forge.config.test.ts`.
- Uso: `NEXUS_WINDOWS_TIMESTAMP_URL=http://timestamp.sectigo.com npm run make` quando o TSA da DigiCert falhar. Qualquer TSA RFC 3161 serve ao Authenticode; o carimbo continua obrigatório.
