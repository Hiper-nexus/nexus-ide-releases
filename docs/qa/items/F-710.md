# F-710 — Pane Grok morre com "failed to prepare the isolated grok agent runtime" na conta gerenciada

## F-710 | categoria: funcional | severidade: alta | status: corrigido
- Tela/fluxo: worker Grok de missão cuja conta escolhida é uma conta Grok gerenciada (`~/.nexus/managed-accounts/grok/<id>/home`), no Windows.
- Arquivo:linha: `src/main/orch/cli-mcp-session-artifacts.ts` (`linkEntry`).
- Passos: 1) Cadastrar uma segunda conta Grok (a conta `acct-muog8ivw-2` nasceu em 30/09 às 15:39). 2) A rotação escolhe essa conta para um worker.
- Esperado: o pane abre na conta escolhida.
- Observado (30/09): print do operador com "[nexus] failed to start: failed to prepare the isolated grok agent runtime". No trace, todo spawn Grok deu certo até as 14:40 e todos falharam depois (17:26, 17:43), na mesma versão 0.76.148.
- Evidencia: a mensagem esconde o `cause`. Reproduzido chamando `prepareGrokMcpSession` com o `GROK_HOME` da conta gerenciada: `EPERM: operation not permitted, copyfile '…\acct-muog8ivw-2\home\bundled' -> '…\bundled'`. Com o `~/.grok` nativo (pastas reais) passa. A conta gerenciada liga cada entrada ao perfil nativo, então `bundled` é um link para pasta.
- Causa: no Windows, `linkEntry` só perguntava "é pasta?" para entradas que não são link. Link para pasta caía no caminho de arquivo (hardlink, depois `copyFileSync` de diretório), e o Windows recusa.
- (resolvedor) Correcao: `linkTargetIsDirectory` segue o link (stat) para decidir. Link para pasta vira junção para a pasta real (`realpath`); link quebrado segue o caminho de arquivo, como antes. Teste: `cli-mcp-session-artifacts.test.ts` (F-710), com uma junção real para pasta. No código antigo ele falha com o mesmo `EPERM`. Conferido também com a conta real do operador.
