# F-1274 — Integração OSC 133: texto do hook vira nome de bloco e status lido por precmd atrasado

## F-1274 | categoria: funcional | severidade: media | status: corrigido (parcial — metade zsh não reproduz)
- Tela/fluxo: Command Blocks sobre PTY (integração de shell OSC 133 + tracker)
- Arquivo:linha: `resources/shell-integration/nexus-osc133.bash:24-42`, `src/main/terminal/command-block-tracker.ts:205-207`
- Passos (bash, reproduzido): 1) Abra um pane bash com a integração. 2) Rode `echo hi`. 3) Rode `echo hi2`. 4) Inspecione os Command Blocks.
- Esperado: blocos chamados `echo hi` e `echo hi2` com os próprios status.
- Observado (antes): o trap DEBUG dispara também para os comandos de `PROMPT_COMMAND`; o `133;E;__nexus_prompt_command` ficava pendente no tracker (`command_line` sobrescrevia `pendingCommand` incondicionalmente) e o bloco seguinte abria com esse nome. Além disso, a própria linha `trap`/atribuição do script disparava o trap recém-armado durante o `source`, deixando o texto pendente para o PRIMEIRO comando da sessão.
- Evidencia: RED com bash real (`src/main/terminal/shell-integration-osc133.shells.test.ts`, `bash --norc -i`): 3× `133;E;__nexus_prompt_command` por ciclo. RED no tracker (`command-block-tracker.test.ts`): sequência B/E(cmd)/C/B/E(hook)/C/D/A/B/E(cmd2)/C gravava o 2º bloco como `__nexus_prompt_command`.
- (resolvedor) Correcao:
  1. `nexus-osc133.bash`: `__nexus_preexec` não emite marcador quando o `BASH_COMMAND` é parte do `PROMPT_COMMAND` (mesma heurística do bash-preexec; teto: um comando do usuário cujo texto seja substring do PROMPT_COMMAND é pulado); o `trap DEBUG` passa a ser armado na ÚLTIMA linha do script, para as próprias linhas do source não dispararem.
  2. `command-block-tracker.ts`: `command_line` (133;E) é ignorado enquanto um bloco está `running` — E aninhado (DEBUG dentro de substituição de comando, partes do PROMPT_COMMAND) não sobrescreve mais o nome do próximo bloco.
  - GREEN: 108/108 em `src/main/terminal/`; typecheck do projeto limpo. RED reproduzido revertendo só `nexus-osc133.bash` (e antes do fix do tracker).
  - **Não reproduzido (zsh)**: a alegação de que o `precmd` do Nexus por último lê `$?` de um hook anterior (starship/p10k) não se confirmou no zsh 5.9 desta máquina: com um `precmd` anterior que falha (`ls /nonexistent`), o `133;D` do comando `true` continuou `0`. O zsh preserva `$?` entre as funções de `precmd`. Nenhuma mudança em `nexus-osc133.zsh`; o teste com zsh real (`shells.test.ts`, mock de precmd + `false` → `D;1`) fica como guarda de regressão.
