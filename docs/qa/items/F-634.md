# F-634 — Missão e panes de um workspace aparecendo e recebendo texto em outro

## F-634 | categoria: funcional | severidade: critica | status: corrigido
- Tela/fluxo: troca de projeto na barra de workspaces com missão viva; ditado, anexos e Jarvis logo depois da troca; recovery e reabertura de missão.
- Arquivo:linha: `src/renderer/state/layout-store.ts:516` (ramo `treeVersion !== versionAtStart` de `switchWorkspaceLayout`), `src/renderer/terminal/terminal-host.ts:3744` (`writeToPane` e submits resolviam host estacionado), `src/renderer/orch/orch-bridge.ts:493` (`recoverMissionPane` sem escopo depois do settle), `src/renderer/orch/mission-reopen.ts:176` (reabertura sem escopo depois do IPC).
- Passos: 1) Missão rodando no projeto A. 2) Trocar para o projeto B enquanto qualquer pane abre ou fecha. 3) Olhar o grid de B / ditar logo depois da troca.
- Esperado: B mostra só o que é de B; texto só entra em pane da tela; uma missão nunca mistura workspace.
- Observado: basta uma mutação da árvore durante a leitura do layout de B para `hydrate(..., { preserveLiveMissionPanes: true })` carregar TODOS os panes de missão da árvore viva — que ainda é a de A — para dentro de B (e a debounce gravá-los no layout de B). Ditado/anexo/Jarvis que guardaram o id do pane antes da troca digitavam no PTY estacionado de A. Recovery e "Retomar missão" montavam o pane de A na árvore de B quando a troca acontecia durante a espera.
- Evidencia: voice.log de 23/09 15:52 — ditado "front-end e-commerce" entregue ao `pane-6816a905` (saasbarbearia) com o operador no hipergo; teste `a missão do workspace que SAI nunca atravessa para o que entra` falha no código antigo com `['pane-mission-a', 'pane-mission-b']`.
- (resolvedor) Correcao: `switchWorkspaceLayout` fotografa os panes da árvore quando a troca começa (`outgoingPaneIds`); `hydrate` nunca carrega um deles — só a missão que aterrissou durante a leitura sobrevive. Digitação do renderer (`writeToPane`, `submitPromptToPane*`) recusa host estacionado (`typingSessionId`); a continuação automática do próprio pane continua. `recoverMissionPane` captura o escopo na chegada e desiste se o workspace mudou durante o settle (o Main já retoma headless). `reopenMission` confere o workspace depois de cada IPC. Testes: `layout-store.test.ts`, `terminal-host.test.ts`, `orch-bridge-recovery.test.tsx`, `mission-reopen.test.ts` — os quatro novos falham no código antigo.
