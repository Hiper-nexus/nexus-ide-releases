# F-509 — Nexus diz que a CLI `claude` não tem sessão com Claude Max logado (falso negativo Keychain-only)

## F-509 | categoria: auth-detection | severidade: alta | status: corrigido
- Tela/fluxo: nova missão ("Descreva e pronto" → "Quem faz o quê"). O papel
  "Coordenar e revisar" (Claude/claude-opus-5) exibe "A CLI `claude` (Claude
  Code) não tem sessão…" e o botão "Iniciar missão" fica bloqueado, embora o
  `claude` funcione normalmente no Terminal.
- Arquivo:linha: `src/main/adapters/subscription-auth.ts` (`detectSubscriptionAuth`
  caso `claude`, `hasSubscriptionAuth`, `refreshClaudeSubscriptionAuthCache`) e
  `src/main/pty/pre-spawn-probe.ts` (ramo `claude`, `failClosed`).
- Passos: 1) `claude auth login` feito no Terminal (Claude Max ativo);
  2) abrir o Nexus empacotado (`/Applications/NexusIDE.app`) e criar uma missão
  com Claude como coordenador; 3) observar o aviso de "sem sessão" + start bloqueado.
- Esperado: sessão OAuth viva do Claude Max reconhecida; `authStrategy` =
  `subscription` e missão liberada.
- Observado: `authStrategy` = `login-needed` com o `loginHint` estático de
  `src/adapters/builtin/claude.json:16`. Causa raiz (verificada nesta máquina):
  o Claude Code moderno no macOS é **Keychain-only** — `~/.claude/.credentials.json`
  **não existe** — e o app empacotado não consegue ler o segredo
  `Claude Code-credentials` via `security -w` (negação TCC/ACL). Toda leitura de
  storage falhava, e a negação era indistinguível de "não logado".
- Evidencia:
  - `ls ~/.claude/.credentials.json` → inexistente; `~/.claude.json` tem
    `oauthAccount.emailAddress = retornoja@gmail.com`, `organizationType = claude_max`.
  - `security find-generic-password -s 'Claude Code-credentials'` → item existe
    (conta `cleofasrocha`); payload (só forma, sem segredo) = `{claudeAiOauth, mcpOAuth}`,
    `access_len = 108`, `refresh_present = True`.
  - `claude auth status` → `{"loggedIn": true, "authMethod": "claude.ai",
    "subscriptionType": "max", …}` — a CLI atesta a sessão que o Nexus negava.
  - Processo Nexus em execução é o empacotado
    (`/Applications/NexusIDE.app/Contents/MacOS/nexus-ide`), sujeito à negação.
- Correção aplicada (fail-closed preservado — o fallback só ADICIONA um sinal
  positivo; qualquer falha/timeout cai no comportamento anterior):
  1. `subscription-auth.ts`: `claudeCliAuthStatusLoggedInSync/Async` — pergunta à
     própria CLI (`<bin> auth status`, binário resolvido por `resolveCliBinary`,
     timeout 5s/8s, nunca lança exceção; `loggedIn === true` é o único positivo).
  2. `hasSubscriptionAuth`: fallback positivo para `claude` quando o storage falha
     (cobre o gate sync da missão via `liveSquadRuntimeInventory`).
  3. `refreshClaudeSubscriptionAuthCache`: probe padrão agora é
     `probeClaudeNativeSessionAsync` (Keychain, depois CLI — inclusive no `reject`
     por negação; probes explícitos de teste inalterados). Cobre a tela de missão
     (snapshot + broadcast) e o painel de Providers.
  4. `pre-spawn-probe.ts`: ramo `claude` aceita `deps.claudeCliLoggedIn` (padrão =
     helper sync) **inclusive com `failClosed: true`** — atestação viva ≠ identidade
     por e-mail, que continua rejeitada no modo governado. Cobre o spawn do
     orquestrador (`mission-fast-lane.ts:2177`, `failClosed: true`).
- Validação: `npm run typecheck` limpo; `npx vitest run
  src/main/adapters/subscription-auth.test.ts src/main/pty/pre-spawn-probe.test.ts`
  → 97 passed; `src/main/adapters/auth-probe.test.ts` → 4 passed; verificação ao
  vivo com binário/sessão reais (`/tmp/live-claude-attestation.test.ts`, não
  commitado) → sync/async/`hasSubscriptionAuth('claude')` = true (3/3).
- Contenção/ação do usuário: nenhuma necessária após esta correção — ao abrir a
  tela de missão, o warm async atesta via CLI (~1s) e libera o start. Se o aviso
  reaparecer, `claude auth login` no Terminal continua sendo o caminho válido
  (re-logado de verdade, não o app Claude do Dock).
