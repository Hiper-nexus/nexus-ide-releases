# F-1330 — worker pede outro `adapterId` em `nexus_pick_account`/`nexus_account_windows` e recebe o próprio provider, em silêncio

## F-1330 | categoria: funcional | severidade: media | status: corrigido
- Tela/fluxo: `nexus_pick_account` e `nexus_account_windows` chamados por um worker.
- Arquivo:linha (antes): `src/main/orch/tools-pick-account.ts:53-56` e `src/main/orch/tools-account-windows.ts:46-48` — para `role === 'worker'`, o `adapterId` pedido era sobrescrito por `ctx.providerId`.
- Passos: 1) worker claude chama `nexus_pick_account{adapterId:'codex'}`; 2) idem `nexus_account_windows{adapterId:'codex'}`.
- Esperado: recusa explícita — o worker só enxerga o próprio provider, e a resposta diz isso.
- Observado: o pick volta com `adapterId 'claude'` e uma conta claude; as janelas listam 2 contas claude. Nenhum aviso: o agente acha que leu a cota do codex.
- Evidencia (RED, fonte da base cb3191f3f/04b5cc966 com os testes novos):
  - `tools-pick-account.test.ts` › "F-1330: worker asking for another adapter is refused, never silently swapped" → `AssertionError: expected true to be false`.
  - `tools-account-windows.test.ts` › "F-1330: worker asking for another adapter is refused, not silently swapped" → `AssertionError: expected true to be false`.
  - `Tests 2 failed | 7 passed (9)` antes; `9 passed (9)` depois.
- (resolvedor) Correcao:
  - Worker com `adapterId` pedido ≠ `ctx.providerId` → `available: false` com motivo que nomeia os dois providers (`decidedBy: 'unavailable'` no pick; `accounts: []` nas janelas). O scorer nem é consultado.
  - A fronteira não mudou: worker sem `adapterId`, ou pedindo o próprio provider, segue como antes; operador/orquestrador continua podendo pedir qualquer adapter (testes de regressão para os três casos em `tools-pick-account.test.ts`, arquivo novo).
