# F-168 — Navegador aberto pelo agente vira "de outro checkout" depois de trocar de projeto

## F-168 | categoria: funcional | severidade: alta | status: corrigido
- Tela/fluxo: agente do projeto A abre um navegador com `nexus_browser_open` (painel do Coolify) e o opera com `nexus_browser_*`; o operador vai ao projeto B e volta.
- Arquivo:linha: `src/main/orch/pane-registry.ts` (limpeza de `orchMetaByPane` em `syncPanes`; `authzInfoOf` lê o escopo do navegador dessa meta).
- Passos: 1) Agente abre o navegador pelo MCP. 2) Operador troca para outro projeto. 3) Operador volta e o agente chama `nexus_browser_find`/`nexus_browser_read`.
- Esperado: o navegador continua do projeto A e o agente do projeto A continua operando.
- Observado (pane 2 do saasbarbearia, 26/09): de 13:09 a 13:11 todas as chamadas passaram; às 13:26 `nexus_browser_find` e `nexus_browser_read` falharam com "not authorized: pane belongs to another project checkout". O agente acabou pedindo o token ao operador e recorreu à área de transferência.
- Evidencia: transcript `09eb06b2…` do pane 2 (chamadas e erros acima). A meta com o escopo só nasce no `nexus_browser_open`; o `syncPanes` do projeto B apagava a meta de todo pane fora do espelho e, na volta, o pane era registrado sem escopo.
- (resolvedor) Correcao: `syncPanes` só apaga a meta de pane ausente quando ela é do workspace atual do renderer (pane fechado). Pane de outro projeto, que só saiu de cena, mantém a meta. `unregisterOrchRenderer` limpa as metas do dono quando a janela fecha.
- Validação: `pane-registry-main-owned.test.ts` › "keeps an agent-opened browser pane's scope across a workspace round trip" falha no código antigo (escopo `undefined`).
- Evidencia adicional: o mesmo erro às 12:48–12:49 no painel da Hostinger (`browser-muik0oz8-c`), antes do Coolify; o agente citou "o mesmo erro do hPanel" (print do operador, 13:27).
- Navegador aberto à mão pelo operador ("+ Browser"), decisão do operador em 26/09 ("liberal sem bloqueio"): o pane sem meta passa a pertencer ao projeto que a janela mostra (`authzInfoOf`). Os agentes do operador no mesmo projeto usam; workers continuam barrados e orquestrador continua preso à própria missão. O browser-manager segue buscando a vista pelo par (escopo do agente, pane), então outro projeto não alcança a vista. Teste: `pane-registry-main-owned.test.ts` › "gives a browser opened by the operator the project its window shows".
- Limite (resolvido em 26/09, 0.76.106): enquanto o operador estava em OUTRO projeto, o navegador do agente deixava de existir. A troca de workspace destruía a vista (`registerBrowserIpc` → `destroyBrowser`) e o pane saía do espelho, então as ferramentas respondiam "unknown pane" (12:49, 13:08 e 14:10 no mesmo transcript) e, na volta, a página tinha recomeçado.
- (resolvedor) Correcao do limite: trocar de projeto AFASTA o navegador, como os terminais estacionados. O browser-manager esconde a vista em vez de destruí-la (`parkBrowserEntry`) e, na volta, readota a mesma vista sem recarregar a URL salva no layout (a página viva vence, mesmo navegada pelo agente enquanto isso). O registro de panes mantém o navegador afastado endereçável pelo id, com o escopo do projeto de onde saiu (`parkBrowserPanesOfPreviousWorkspace`), então `nexus_browser_*` segue funcionando para o agente do projeto; o número do header não resolve enquanto afastado (a tela nova numera de novo). Fechar o projeto encerra os navegadores dele; tirar o projeto da lista encerra os afastados dele (`forgetRendererWorkspace`); a janela fechada encerra todos. Revisão automática (URL travada) continua encerrando na troca. `nexus_pane_close` num navegador afastado encerra a vista na hora e o pane sai do layout quando o projeto volta (sem recarregar a página).
- Captura com a vista escondida (medido no Electron 26/09, via launchd): navegar, ler o DOM e clicar funcionam; a primeira captura depois de uma página nova carregar escondida falha na hora com `UnknownVizError` e acorda o renderer, e a seguinte (150 ms) sai com a página atual, sem quadro velho. `captureBrowserScreenshot` faz essa segunda tentativa (`captureWithWakeRetry`), o que também cobre painéis escondidos por overlay.
- `nexus_browser_open` com a janela noutro projeto continua recusado (o layout daquele projeto não está montado), agora dizendo ao agente para seguir no navegador que o projeto já tem (`nexus_pane_list` → `nexus_browser_navigate`) ou pedir a volta ao operador.
- Validação do limite: `browser-manager-network.test.ts` (afasta e devolve a página viva; fechar projeto; tirar da lista; fechar afastado; revisão automática), `pane-registry-main-owned.test.ts` (endereçável fora da tela, sem número; projeto fechado; fechar afastado; vista destruída), `screenshot-clip.test.ts` (segunda tentativa). Sem a correção, 5 desses testes falham.
- Mitigação anterior, ajustada: "unknown pane" de navegador explicava que o projeto não estava na janela; agora que o navegador sobrevive à troca, a mensagem diz que o pane foi fechado e aponta `nexus_browser_open`, que exige o projeto na tela (`tools-panes-peer-read.test.ts`).
