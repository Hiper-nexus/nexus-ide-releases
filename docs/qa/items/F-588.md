# F-588 — Reaper de emergência: permissão de estacionamento (park) de workers e panes de operador sob pressão de memória e calibração para máquinas inferiores (8-16 GB)

## F-588 | categoria: runtime-stability | severidade: alta | status: corrigido
- Tela/fluxo: Execução de missões com múltiplos panes / Pressão de Memória no Sistema / Gate de Admissão
- Arquivo:linha: `src/main/orch/pane-non-worker-auto-close.ts:150`, `src/main/orch/pane-non-worker-auto-close.ts:230`, `src/main/orch/pane-non-worker-auto-close.ts:365`, `src/main/orch/pane-admission.ts:72`
- Passos:
  1) O Nexus orquestrava múltiplos panes de agentes (ex.: 4 workers Codex em missões) enquanto uma carga pesada local rodava na mesma máquina (ex.: build de Next.js, compilação ou processos externos).
  2) A memória disponível do sistema caía a níveis críticos (ex.: 148 MB livres) e o load average disparava (ex.: 62), provocando saturação extrema e travamento de swap no macOS/Linux.
  3) O reaper de emergência de `pane-non-worker-auto-close` executava a varredura sob `isUnderMemoryPressure()`, mas consultava `paneIsClosable()`, cujo predicado `isGuardianEligiblePane()` rejeitava sumariamente qualquer worker com missão vinculada (`missionId !== undefined`) e qualquer pane aberto pelo usuário no renderer (`operatorParentSessionId === undefined`).
  4) Como resultado, 0 panes eram considerados elegíveis. Os 4 panes ociosos continuavam retendo ~1 GB de RAM cada (CLI Node/Python + servidores MCP filhos), mantendo o computador congelado.
- Esperado:
  1) Sob pressão de memória, o guardian deve poder ESTACIONAR (`parkPane`) os panes ociosos mais antigos (inclusive workers de missão e panes de operador), suspendendo o processo PTY e liberando ~1 GB de memória por pane imediatamente, enquanto preserva o buffer/scrollback intacto no grid visual com o botão "Acordar".
  2) Workers de missão que ficarem ociosos por longo período (após o TTL) também devem ser estacionados via `parkPane` quando o fechamento definitivo não for aplicável, evitando acúmulo de processos fantasmas.
  3) Máquinas de menor especificação (<= 8 GB RAM) devem ter o teto seguro de panes simultâneos calibrado para 2 panes (e 12 GB para 3), evitando sobrecarga de RAM no boot e prevenindo travamentos.
- Observado:
  - O reaper de emergência usava o critério de fechamento destrutivo (`isGuardianEligiblePane`) para o estacionamento não-destrutivo (`parkPane`), impedindo a liberação de RAM de workers e helpers de missão ociosos.
- Evidencia:
  - `src/main/orch/pane-non-worker-auto-close.test.ts` (29 testes passando, incluindo estacionamento de workers sob pressão e após TTL).
  - `src/main/orch/pane-admission.test.ts` (27 testes passando).
  - `npm run typecheck` (0 erros).
  - `npm run security:renderer-sinks` (0 sinks).
- (resolvedor) Correcao:
  - `isGuardianParkablePane` e `paneIsParkableUnderPressure`: adicionado predicado que permite estacionar qualquer worker ou pane de operador ocioso sob pressão de memória ou após TTL, blindando apenas o orquestrador ativo.
  - `sweepIdlePanes`: atualizado para usar `paneIsParkableUnderPressure` no reaper de emergência e na varredura pós-TTL.
  - `productionDeps().parkPane`: proteção fail-closed garantindo que adapters sem suporte a resume nunca fechem trabalhadores de missão de forma destrutiva.
  - `limitsForMachine`: teto calibrado com piso de 2 panes para máquinas <= 8 GB e 3 para <= 12 GB.
