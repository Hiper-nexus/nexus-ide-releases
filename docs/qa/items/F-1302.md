# F-1302 — contrato `expect` do pane_spawn estoura o limite de profundidade de argumentos MCP

## F-1302 | categoria: funcional | severidade: alta | status: corrigido
- Tela/fluxo: `nexus_pane_spawn` com `expect: {schema, retries}` (contrato de
  entrega, `src/main/orch/delivery-contract.ts`).
- Arquivo:linha: `src/main/orch/mcp-args-validation.ts:8`
  (`MAX_MCP_ARG_DEPTH`, aplicado por `assertPayloadLimits`).
- Passos: 1) spawnar pane com `expect.schema` realista — objeto `findings` como
  array de objetos com campos tipados (ex.: `severity.enum`). 2) O spawn inteiro
  é recusado antes de existir.
- Esperado: schema dentro do subconjunto JSON Schema documentado
  (type/required/properties/items/enum/const/minItems/pattern/anyOf) passa pela
  validação genérica de payload.
- Observado: `nexus_pane_spawn failed: invalid arguments: tool arguments exceed
  max depth 8`. O caminho
  `expect.schema.properties.findings.items.properties.severity.enum[0]` está na
  profundidade 9; qualquer lista de objetos tipados já estourava.
- Evidencia: `npx vitest run src/main/orch/mcp-args-validation.test.ts` — antes
  do fix, 2 testes novos (schema realista e variação com `anyOf`) falhavam com
  "exceed max depth 8"; após, 30/30 verdes.
- (resolvedor) Correcao: `MAX_MCP_ARG_DEPTH` 8 → 16 em
  `mcp-args-validation.ts`. O limite existe para conter payload patológico
  (recursão/ciclos); a largura já é limitada por `MAX_OBJECT_KEYS` (200) e
  `MAX_ARRAY_ITEMS` (1000), então dobrar a profundidade não abre vetor novo —
  um schema com anyOf encadeado chega a ~11, e o teste prova que payload com
  profundidade 40 continua recusado. Testes de regressão adicionados em
  `mcp-args-validation.test.ts` (describe `F-1302`).
