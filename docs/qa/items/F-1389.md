# F-1389 — writers devin entregam por `mission-shim`: o MCP do Nexus está ligado, mas o Devin o esconde atrás de meta-ferramentas

## F-1389 | categoria: funcional | severidade: baixa | status: precisa-decisao
- Tela/fluxo: worker de missão no adapter `devin` → handoff final.
- Arquivo:linha: `src/main/orch/cli-mcp-session-devin.ts` (registro),
  `src/main/orch/mcp-server.ts:1520` (ramo `devin`), `src/main/orch/mcp-server.ts:1145`
  (ENV `NEXUS_MCP_URL/TOKEN`), `src/main/pty/pty-manager.ts:2167` (home de checkout).
- Passos (campo, 12/10, app 0.76.239, missão `mission-94d90f5b`): writers
  devin (`swe-2-medium`) de F-1310 (`pty-mv5249jb-23`) e F-1388 entregaram por
  `mcpProvenance.source = "mission-shim"`, nunca `http-mcp`.
- Esperado: saber se o devin recebe o MCP do Nexus ou só o shim.
- Observado / Evidencia:
  1. Config: `~/.config/devin/mcp_config.json` (escopo user, F-698) tem a
     entrada `nexus` → `node ~/.nexus/mcp-bridge/nexus-mcp-bridge.cjs`. O home
     de checkout do devin troca só `XDG_DATA_HOME`. HOME e `~/.config` seguem
     os reais, então a entrada é lida.
  2. Logs do Devin 3000.11.3 (`provider-state/devin/.../cli/logs`, sessões
     06:35 e 08:23): o filho ACP sobe `MCP server 'nexus'` e registra
     "connected successfully".
  3. Herança de ENV, medida no 3000.11.3/macOS: `devin acp` em HOME isolado,
     com servidor marcador no lugar da ponte. O marcador nasceu com
     `NEXUS_MCP_URL` e `NEXUS_MCP_TOKEN` presentes e recebeu `initialize` e
     `notifications/initialized`. Diferente do Muse 1.4.4 (F-1338 causa 2), o
     Devin entrega o ambiente do processo à ponte. O shim funcionou no `exec`
     do mesmo filho ACP: `NEXUS_SHIM_SECRET` (mesmo objeto `env` do
     `NEXUS_MCP_*`) chegou lá.
  4. Causa do `mission-shim`: os transcripts do Devin
     (`cli/transcripts/*.json`) mostram que o MCP chega ao modelo SÓ por
     meta-ferramentas (`mcp_list_servers`, `mcp_list_tools`, `mcp_call_tool`,
     `mcp_read_resource`). O server `nexus` aparece na lista, mas não existe
     ferramenta `nexus_handoff_submit` inline. Nas 3 últimas sessões há 0
     chamadas de `mcp_list_tools`/`mcp_call_tool`. O modelo procurou o comando
     (`command -v nexus_handoff_submit`) e entregou pelo shim do PATH, como o
     brief mandava ("If the MCP tool is unavailable, use the shell
     alias/command").
- Não confirmado: os `tools/list` reais da ponte no pane de campo. Faltam
  credencial e o caminho TUI→ACP, porque o TUI exige login antes de criar o
  filho. O `initialize` da ponte idle não traz `instructions` e o server
  `nexus` apareceu sem descrição na lista do Devin. Isso é compatível com
  ponte idle, mas não prova nada: o Devin pode só não exibir instructions.
- Decisão pedida ao orquestrador:
  - (a) Política atual, recomendada e sem código: para o devin,
    `mission-shim` é o canal esperado e autenticado do handoff (mesmo
    `dispatchToolCall`, recibo e proveniência próprios). Não tratar como MCP
    quebrado.
  - (b) Se o objetivo for o devin usar o MCP inteiro (`route_task`,
    `memory_recall`…), dar uma dica por adapter no prompt do worker devin:
    "as ferramentas do Nexus estão em `mcp_list_tools({server:"nexus"})` /
    `mcp_call_tool`". Antes, validar ao vivo com credencial que a ponte
    devolve as ferramentas no caminho TUI→ACP.
- (resolvedor) Correcao: nenhuma. Não há bug de fio reproduzido; a doutrina
  depende da decisão (a)/(b).
