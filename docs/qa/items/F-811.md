# F-811 — O classificador "só sincronização" era largo e virava ops tarefas de escrita

## F-811 | categoria: funcional | severidade: alta | status: corrigido
- Tela/fluxo: `suggestMissionLaneFromGoal` — sugestão de lane do wizard (`MissionSetup.tsx`, caminho Expresso), entrega por texto (`allowsTextDelivery` em `mission-delivery-artifact-gate.ts`) e criação de missão pela mão do operador.
- Arquivo:linha: `src/shared/mission-intent.ts` passo 3.5 de `suggestMissionLaneFromGoal` (introduzido pelo F-785): bastava um verbo de sincronização (`atualiz*`, `pux*`, `pull`, `fetch`) junto de `git`/`github`/`repo`/`repositório`/`origin`/`upstream`, sem os verbos de escrita da lista.
- Passos: 1) Pedir "atualize o README do repositório" (ou qualquer outro caso abaixo). 2) A lane sugerida é `ops`. 3) O done é aceito sem arquivo (`mission-delivery-artifact-gate.ts`, só nota de 40 caracteres) e `maxWorkers` zera.
- Esperado: só pedido de sincronização EXPLÍCITO vira `ops`; tarefa de escrita continua standard e exige arquivo; investigação continua consult.
- Observado (revisão adversarial de `ec8524a8`): viravam `ops` "atualize as dependências do repositório para a versão mais nova", "atualizar o workflow do GitHub Actions", "atualize o README do repositório", "fetch os dados da API do GitHub e mostre no dashboard" e "puxe as issues do github e gere um relatório em docs/"; "investigue por que o git pull falha" (consult na base) também virava `ops`. A lane `consult` deixava de abrir a entrega por texto para missões standard com objetivo de investigação que citasse git/pull/fetch.
- Evidência: com o classificador do commit-base, os 6 casos acima devolviam `ops`; agora cinco devolvem `null` (standard) e o da investigação volta a `consult`. Testes novos em `mission-intent.test.ts` (13 negativos, 12 positivos, merge só com fast-forward, verbo sem objeto, recusa de alterar vence) e em `mission-delivery-artifact-gate.test.ts` (investigação com git mantém entrega textual; tarefas de escrita não fecham só com texto).
- (resolvedor) Correcao: `isExplicitGitSyncGoal` (novo, exportado) substitui as duas regexes do passo 3.5. O texto INTEIRO (≤ 280 caracteres) precisa ser sincronização, com vocabulário fechado (sem acento, em Set): verbos sincronizar/atualizar/puxar/pull/fetch/sync, objetos repositório/repo/branch/origin/upstream/remoto/main/git/github (e `origin/<ref>`), palavras neutras (artigos, preposições, cortesia, "local", "últimas mudanças"). Qualquer palavra fora disso (dependências, pacotes, README, docs, workflow, actions, issues, dados, API, relatório…) desclassifica. Vale se houver comando git literal (`git pull`, `git fetch`), `--ff-only`/`fast-forward`, ou verbo de sync + objeto de repositório; `merge` só junto de `--ff-only`/fast-forward. É o único predicado que `operatorHandMissionContract` aceita (F-810). O wizard (`MissionSetup.tsx`) e `allowsTextDelivery` consomem `suggestMissionLaneFromGoal` e herdam a correção sem mudança de código.
- Regra de custo: errar para o lado conservador só deixa a missão `standard` (o done pede arquivo); errar para o outro deixava tarefa de escrita entregar sem arquivo. Por isso o vocabulário é fechado: pedido de sync com nome próprio ("sincronize o repositório nexus-ide com origin") cai em standard.
- Tempo: sem regex com backtracking sobre o texto do operador (corte em 280 caracteres, Set por token, aparo de pontuação por laço); teste adversarial de 16 KB com teto de 50 ms (padrão "F-764: varredura linear").
