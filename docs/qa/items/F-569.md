# F-569 — Sessão governada Grok/Kimi recebia leitura+escrita no home real do provider inteiro

## F-569 | categoria: seguranca | severidade: alta | status: corrigido

- Tela/fluxo: spawn de pane governado (squad/mission) para Grok e Kimi via
  `mcp-server.ts` → `prepareGrokMcpSession` / `prepareKimiMcpSession`.
- Arquivo:linha (antes da correção): `cli-mcp-session-grok.ts:408`,
  `cli-mcp-session-kimi.ts:257` — consumido em `mcp-server.ts:1233,1238`
  (`advisoryProviderStateHome` → `providerStateReadPaths`/`WritePaths`).
- Passos: 1) spawnar um worker governado em Grok ou Kimi; 2) inspecionar o
  resultado de `prepare*McpSession` (`providerStateHome`); 3) comparar com o
  overlay real (`linkGrokAuthPair`/`linkSelectedEntries`).
- Esperado: o grant de sandbox cobre exatamente os arquivos que o overlay
  simlinka de volta para o home real (o par `auth.json`/`auth.json.lock` no
  Grok; `credentials/` e `oauth/` no Kimi) — nunca o resto do diretório.
- Observado: `providerStateHome: providerHome` publicava leitura+escrita no
  `~/.grok`/`~/.kimi-code` **inteiro** — incluindo `config.toml`, `device_id`,
  `workspace-trust`, `workspaces.json` e qualquer outro arquivo que já esteja
  ou venha a estar naquele diretório — para um worker governado cuja política
  (`policy.governed`) existe justamente para restringir o que ele enxerga.
- Correção: `linkGrokAuthPair` passou a devolver os caminhos reais que
  efetivamente linkou (só os que existem) e esses caminhos — nunca mais
  `providerHome` — alimentam os novos campos `providerStateReadPaths`/
  `providerStateWritePaths` em `CliMcpSessionResult`
  (`cli-mcp-session-types.ts`). Kimi ganhou o equivalente
  `kimiAuthGrantPaths` (`credentials/`, `oauth/`, só os que existirem — o
  mesmo par que `managed-credentials.ts` já reconhece como superfície de auth
  do Kimi via `authCandidates`/`skipLinkNames`). `providerStateHome` deixa de
  ser publicado para as duas sessões governadas.
- Pendência de integração (não aplicada nesta rodada): `mcp-server.ts` ainda
  só consome o campo singular `providerStateHome` (`[advisoryProviderStateHome]`
  em dois pontos). Outro pane está ativo nesse arquivo agora; a inserção
  exata necessária para os novos campos surtirem efeito no grant real está
  descrita no handoff do terminal desta sessão (variáveis
  `advisoryProviderStateReadPaths`/`WritePaths`, atribuídas nos 3 branches
  grok/kimi/opencode, espalhadas nos dois arrays do `decoration`). Até essa
  inserção landar, o comportamento de runtime não mudou — a correção fica
  pronta e testada do lado da preparação da sessão, aguardando o gancho.
- Evidência: testes novos em `cli-mcp-session-grok.test.ts` ("F-569 governed
  sandbox grant") e `cli-mcp-session-kimi.test.ts` (idem) plantam um segredo
  irrelevante (`config.toml`/`device_id`) ao lado do material de auth e
  verificam que o grant nunca contém `providerHome` nem esse arquivo. Os três
  testes pré-existentes em `cli-mcp-session-config.test.ts` (describe
  `advisory provider-state home grant`) que antes fixavam
  `providerStateHome === providerHome` foram atualizados para a nova forma.
- Validação: `npx vitest run src/main/orch/cli-mcp-session-grok
  src/main/orch/cli-mcp-session-kimi src/main/orch/cli-mcp-session-config` →
  3 arquivos / 38 testes, 0 falhas.
