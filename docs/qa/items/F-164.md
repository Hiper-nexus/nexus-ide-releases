# F-164 — Pane do operador não consegue abrir helpers após outra janela

## F-164 | categoria: funcional | severidade: alta | status: corrigido
- Tela/fluxo: operador abre qualquer CLI pelo + Pane e pede `nexus_pane_spawn`; relacionado ao navegador aberto por MCP.
- Arquivo:linha: `src/main/orch/pane-registry.ts:585` (`rendererForMission`).
- Passos: 1) Abrir o grid no projeto A. 2) Registrar uma janela auxiliar sem workspace ou uma janela do projeto B. 3) Pedir ao agente do projeto A que abra um helper. Fechar a última janela também reproduz.
- Esperado: o helper abre na janela do pane pai, com o mesmo workspace; a CLI escolhida não altera a autoridade de destino.
- Observado: `orchRenderer` guardava apenas a última janela registrada. `rendererForMission` recusava o spawn com `no renderer window available`, mesmo com a janela e o pane do operador vivos. Com duas janelas do mesmo projeto, o helper era enviado ao grid errado.
- Evidencia: erro reproduzido via MCP nesta sessão em 26/09; cinco regressões falharam antes da correção (janela sem vínculo, outro projeto, última janela fechada, browser pane, duas janelas do mesmo projeto).
- (resolvedor) Correcao: o resolvedor prioriza o proprietário vivo da sessão pai, recebido exclusivamente pelo Main, e revalida o escopo. Sem pai, reaproveita os proprietários dos grids já espelhados, inclusive vazios, sem depender exclusivamente da última janela. Pane pai ausente, crashado ou que mudou de projeto não é redirecionado a outro grid. `parentPaneId` continua sendo o único vínculo enviado ao renderer.
- Validação: Node 22.23.2 executou 106 testes aprovados em 5 arquivos (registry, main-owned, spawn do operador e autoridade de workspace); `npm run typecheck`, `npm run security:renderer-sinks` (0 sinks) e `git diff --check` passaram.
- Limite: o Main do aplicativo já aberto continua com o código da build anterior. A prova de spawn visível deve ser feita na build atualizada, antes de marcar `verificado`.
