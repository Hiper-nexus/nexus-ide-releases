# F-1338 — workers glm/muse nasciam sem o MCP do Nexus (duas causas)

## F-1338 | categoria: funcional | severidade: alta | status: corrigido (glm residual fora do repo, ver lacuna)
- Tela/fluxo: `nexus_pane_spawn` de worker de missão nos adapters Claude-compatíveis
  de terceiros e no Muse Code → ferramentas MCP do Nexus no pane.
- Passos (ao vivo, 12/10, app 0.76.239, missão `mission-94d90f5b`): a sonda C
  (`claude --model glm-5.3 --mcp-config ~/.nexus/ephemeral/<id>/nexus-mcp.json
  --strict-mcp-config`, pane `pane-mv52znio-2i`, 58 min viva) e a sonda B
  (`muse --model muse-spark-1.3`, pane `pane-mv52tnjk-2c`) relataram pane sem
  ferramentas MCP do Nexus — só shims de handoff. As sondas em claude (Opus),
  codex, grok, minimax e kimi tinham as ferramentas.
- Esperado: cada adapter usado como worker de missão enxerga o MCP do Nexus.

## Causa 1 (provada no fio, corrigida): `ENABLE_TOOL_SEARCH=true` no `muse-claude`
- Arquivo:linha (antes): `src/adapters/builtin/muse-claude.json:50`,
  `src/main/adapters/launcher-provider-manager.ts:228`.
- Evidencia (Claude Code 2.1.296 real contra API stub + MCP stub locais,
  mesmo ENV do spawn; `glm-probe.mjs` em /tmp, fora do repo):
  - `ENABLE_TOOL_SEARCH=true` + modelo desconhecido (`muse-spark-1.3`):
    request SEM nenhuma ferramenta `mcp__*`, COM ferramenta `ToolSearch`
    e SEM o beta `tool-search-tool-2025-10-19` — adiamento ligado num host
    que não negocia tool-reference: MCP invisível e inalcançável.
  - ausente (padrão Nexus) + `muse-spark-1.3` ou `glm-5.3`:
    `mcp__nexus__nexus_handoff_submit` inline, sem ToolSearch — inclusive
    com 45 ferramentas MCP (escala do Nexus real) e nos modos `-p` e
    interativo. `false` comporta-se como ausente.
- Correcao: removido o `ENABLE_TOOL_SEARCH` dos dois lugares + comentário
  anti-regressão; teste `muse-claude-surfaces.test.ts` afirma ausência e
  varre TODOS os adapters/upstreams (`offenders == []`).
- RED: com a linha reposta, o teste de varredura falha com
  `expected [ 'muse-claude (adapter)' ] to deeply equal []`.
- Nota: `glm`/`glm-flash`/`deepseek`/`longcat` nunca definiram a variável —
  o padrão já entrega inline; nenhum fix neles.

## Causa 2 (provada no fio, corrigida): Muse Code não recebe a sessão por ENV
- Arquivo:linha (antes): `src/main/orch/cli-mcp-session-muse.ts`
  (`ensureMuseNexusMcpRegistration` registrava `{command, args}` sem sessão;
  o spawn passava URL/sessão só no ENV do pane).
- Evidencia (Muse Code 1.4.4 real, macOS, 12/10):
  - ponte instrumentada: nasce com `NEXUS_MCP_URL/TOKEN` AUSENTES mesmo com
    o ENV presente no processo do Muse → `connected=false` → `tools/list`
    responde `{"tools":[]}` sem tocar o HTTP — pane sem MCP. A premissa do
    F-696 ("herda o próprio ambiente", medida no 1.4.1/Windows) não vale
    no 1.4.4/macOS.
  - entrada com `env` (servidor marcador): o CLI ENTREGA o `env` da entrada
    ao servidor (`MARKER_VAR` chegou; ambiente do processo, não).
  - ponta a ponta (entrada com `env` + stub Nexus MCP): stub recebe
    `initialize`, `notifications/initialized`, `tools/list`; a ponte devolve
    `nexus_handoff_submit`; TUI e `exec` carregam o servidor.
- Correcao: a entrada `nexus` leva `env: {NEXUS_MCP_URL, NEXUS_MCP_TOKEN}`
  da sessão do pane; sem sessão nada é registrado (antes registrava entrada
  inútil); `schema_version: 1` por padrão ao criar (o 1.4.4 recusa o arquivo
  inteiro sem ele); `settings.json` travado em 0600 com fail-closed (sem o
  0600 a escrita é desfeita e o pane segue sem MCP).
- Segurança: sessão por pane, revogada no teardown (`releaseSessionByToken`
  apaga o contexto → Bearer desconhecido → 401); cada spawn regenera a
  entrada com a sessão viva; conteúdo velho no arquivo é sessão morta.
  Concorrência: cada processo Muse captura o `env` no seu próprio spawn —
  sem conversa cruzada; releitura tardia reaproveitaria a última sessão
  (não observada; sem GC por enquanto).
- Riscos restantes: operadores com `settings.json` 0644 passam a 0600 no
  primeiro spawn (só restringe; documentado em AGENTS.md/F-696).
