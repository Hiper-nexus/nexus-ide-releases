# F-1275 — Fila de merge ilegível ao lado de worktree válida travava todo `forScope` do escopo

## F-1275 | categoria: funcional | severidade: media | status: corrigido
- Tela/fluxo: abertura do escopo (`WorktreeRuntimeRegistry.forScope`). Tudo depende dela: spawn de pane, aba, missão e merge.
- Arquivo:linha (antes):
  - `src/main/runtime/sqlite-workflow-state-stores.ts:280-285`: `recoverInvalidState` só olhava `worktree_state` e devolvia `{action:'none'}` assim que a worktree lia.
  - `SqliteMergeQueueStateStore.read` (`:564-570`) lançava `ScopedStoreCorruptionError`.
  - `merge-queue-recovery.ts:120` propagava o erro.
  - `worktree-runtime-registry.ts:185` chamava `queue.reconcile` sem try/catch.
- Mesma família do F-1253 e do F-1257 (estado durável sem saída). Achado da revisão de persistência.
- Passos:
  1. Uma versão mais nova grava em `merge_queue_state` um evento de tipo que esta versão não conhece. O validador antigo recusa em `merge-queue-state.ts:227` (`EVENT_TYPES`).
  2. A `worktree_state` do mesmo escopo continua válida.
  3. O app (esta versão) abre o escopo.
- Esperado:
  - Sem registro `queued` dependendo da fila, a linha ilegível vai para `worktree_state_quarantine` e a fila volta vazia.
  - Se não der para provar isso, o escopo abre mesmo assim e só as operações de merge falham.
- Observado: a recuperação dizia `none`, o `reconcile` lançava `MergeQueuePersistenceError` e todo `forScope` do escopo falhava para sempre. Isso derrubava spawn de pane, aba e missão.
- Evidencia (RED, fontes anteriores restauradas com `git show HEAD:` em `sqlite-workflow-state-stores.ts` e `worktree-runtime-registry.ts`):
  - `sqlite-workflow-state-stores.test.ts` › "F-1275: archives an unreadable merge queue row next to a valid worktree projection" falha com `expected { action: 'none' } to match object { action: 'quarantined', recordCount: 0 }`.
  - Mesmo arquivo, "F-1275: keeps an unreadable merge queue fail-closed while a worktree is queued" falha com `expected { action: 'none' } to deeply equal { action: 'blocked', reason: 'unproven-invalid-state' }`.
  - `worktree-runtime-registry.test.ts` › "F-1275: opens the scope while a queued worktree pins an unreadable merge queue" falha com `MergeQueuePersistenceError: merge queue persistence read failed: project runtime contains an invalid merge queue state record` (causa: `invalid merge queue event`).
  - Resumo: `Tests  3 failed | 38 skipped (41)`.
  - Com só o store corrigido e o registry ainda antigo, o teste do registry continua falhando. As duas partes são necessárias.
- (resolvedor) Correcao:
  - Causa: a recuperação de estado inválido só olhava a projeção de worktrees. Uma fila de merge ilegível não tinha saída, e o `reconcile` de abertura derrubava o escopo inteiro.
  - `sqlite-workflow-state-stores.ts`:
    - A leitura validada da fila vira a função `readMergeQueueState`, que `SqliteMergeQueueStateStore.read` passa a usar (mesma validação, sem cópia).
    - Com a worktree válida, `recoverInvalidState` testa a fila também.
    - Se a fila é ilegível e nenhum registro está `queued`, a linha bruta da fila e a da worktree vão para `worktree_state_quarantine`. A fila é zerada pelo mesmo caminho e com o mesmo CAS de antes.
    - A worktree mantém os registros byte a byte e só a revisão sobe, sob o mesmo CAS. O resultado volta `quarantined` com `recordCount: 0`.
    - Com registro `queued`, a resposta é `blocked/unproven-invalid-state` e nada muda.
    - Sem linha de worktree também fica `blocked`. Não acontece no fluxo normal, porque o enqueue sempre grava a worktree antes.
  - Razão gravada: a coluna `reason` tem `CHECK IN ('relocated-runtime-binding','terminal-legacy-state')`, e criar um valor novo exigiria reconstruir a tabela numa migração. A recuperação só da fila grava `terminal-legacy-state`: nenhum registro `queued` tem autoridade sobre a fila. Ela se distingue por `recordCount: 0` e por `source_records_json` ser a projeção válida.
  - `worktree-runtime-registry.ts`:
    - `queue.reconcile` da abertura fica em try/catch com `console.warn("[worktree-runtime] merge queue reconcile skipped", error)`. O escopo abre e só o merge continua falhando: `claim` recusa enquanto o estado durável não se resolve, e `reconcileMergeIfIdle`/`IfStalled` podem tentar de novo.
    - Os avisos de `quarantined` e de `blocked` (F-1276) passam a falar em "worktree/merge state".
  - Nada no Git é tocado.
  - Testes:
    - worktree vazia válida mais fila com `events:[{type:'future-type',…}]` dá `quarantined`. A fila lê o snapshot vazio na revisão 4, a worktree fica `[]` na revisão 2, a quarentena guarda o `state_json` bruto, e a segunda chamada devolve `none`;
    - com registro `queued`, a resposta é `blocked` e a fila e a quarentena ficam intactas;
    - no registry, o `forScope` abre com o registro `queued` preservado e o aviso emitido.
