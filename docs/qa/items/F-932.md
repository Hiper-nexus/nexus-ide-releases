## F-932 | categoria: dados | severidade: alta | status: corrigido
- Tela/fluxo: Ajustes › Chaves de API › Modelos de decisão (Clef), no Windows e no Mac.
- Arquivo:linha: `src/main/persistence/settings-store.ts` (`SETTINGS_FILE`); gatilhos em `src/main/orch/agent-keyring-persistence.test.ts:69` e `src/main/orch/operator-workspace-memory.test.ts:121`.

- Observado (05/10, 0.76.194): o modo volta para "Somente Jev" e o Account ID some; o token continua (fica no cofre, não no arquivo). Medido com hash do arquivo: os dois testes regravam `~/.nexus/settings.json`; os outros cinco candidatos não.
- Causa: os dois testes chamam `replaceOrchSettings` de verdade. O teste não passa por `load()`, então a memória está nos padrões e `persist(snapshot())` grava os PADRÕES de todo o arquivo (terminal, áudio, orch…) por cima do arquivo real, mais o patch do teste — um deles deixava `agentAttestationGate: required`. Sessões de agentes rodam a suíte o dia todo nas duas máquinas, por isso "não segura". O caminho do app (orchSet → persist → load) está correto: o arquivo real passa no schema e o Account ID sobrevive à releitura.
- (resolvedor) Correcao: `resolveSettingsFile` — sob `VITEST` o arquivo fica em `os.tmpdir()/nexus-vitest-settings-<pid>/settings.json`, nunca no HOME (mesma convenção de `squad-store`/`agy-windows-keyring`). `settings-store.test.ts` novo: prova o caminho e que uma gravação real de teste não muda o arquivo do operador. Repetido com o arquivo real sob vigia: 6 arquivos de teste, hash igual.
