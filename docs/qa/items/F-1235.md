# F-1235 — A lane heavy declarada pelo agente aceitava raiz não registrada e não deixava rastro

## F-1235 | categoria: seguranca | severidade: baixa | status: corrigido
- Tela/fluxo: admissão de comando pesado (`request.cjs` → `/hook/heavy-command` → `NativeHeavyCommands` → `HeavyCommandPermitPool`), lane por raiz Git do job (F-1229).
- Arquivo:linha (antes):
  - `src/main/orch/native-heavy-command.ts:83-87` — `#executionScope` usa a raiz que o `cwd` do pedido indicar;
  - `src/main/orch/nested-worktree-execution.ts:75-91` — `sameRepositoryExecutionRoot` só exige `--git-common-dir` igual ao da raiz do token;
  - `resources/heavy-command/request.cjs` — o `cwd` (ou a dica `NEXUS_HEAVY_CWD`) é declarado pelo processo que pede.
- Relacionado a F-1229 (origem da lane por cwd), F-983 e F-997.
- Passos:
  1. num checkout, crie uma pasta com um arquivo `.git` contendo `gitdir: <checkout>/.git`, sem `git worktree add`;
  2. peça admissão pesada com `cwd` nessa pasta, ou com `cwd` numa worktree ligada enquanto o job roda no checkout.
- Esperado: só o checkout ou uma worktree registrada do projeto viram lane própria. Uma lane escolhida pelo pedido, diferente da do token, fica registrada no trace do Main.
- Observado:
  - A checagem do F-1229 (mesmo `git-common-dir`) não garante registro. `git rev-parse --show-toplevel` na pasta do passo 1 devolve a própria pasta, e o common-dir é o do repositório. Cada pasta assim virava uma lane nova, sem teto além do da máquina. O mesmo vale para um `.git` arquivo apontando para `.git/worktrees/<nome>`.
  - Nenhum registro dizia que a lane veio do pedido e não do token.
  - Os limites de máquina continuavam valendo (`maxActive = cpus/2` e reserva de RAM): o pedido só escolhe a serialização por raiz.
- Evidencia: `src/main/orch/heavy-command-lane.test.ts`, bloco "F-1235". Com a fonte anterior:
  - `sameRepositoryExecutionRoot(<checkout>, <pasta com .git arquivo>)` devolve um escopo (`expected { version: 1, …(7) } to be undefined`);
  - nenhum evento `heavy-command-lane` no trace (`expected [] to deeply equal [ Array(1) ]`).
- (resolvedor) Correcao:
  - (a) `sameRepositoryExecutionRoot` também exige que o toplevel do `cwd` (realpath) esteja em `git worktree list --porcelain`, rodado na raiz do token, com cada caminho passado por realpath. O common-dir igual continua exigido, para o caso de uma pasta registrada trocada por outro repositório. Se o `git worktree list` falhar, a lista fica vazia e o job vai para a lane do token. Um caminho que o git escreve entre aspas (bytes incomuns) também não casa e vai para a lane do token.
  - (b) `#executionScope` recebe o `pid`. Quando a lane escolhida difere da raiz do token, emite no trace do Main (`trace` de `observability/main-trace`, o mesmo do `heavy-command-denied`) o evento `{kind:'heavy-command-lane', sessionId, pid, root, paneRoot}`. Lane igual à do token não gera evento.
  - Agora uma lane própria só existe por worktree registrada. O máximo de jobs paralelos num mesmo checkout passa a ser o número de worktrees registradas, e criar uma exige `git worktree add`, que fica no repositório.
- Validacao (launchd): `heavy-command-lane.test.ts` + `native-heavy-command.test.ts` + `nested-worktree-execution.test.ts`: 29/29. Antes do fix, os 2 testes novos falham. Os testes do F-1229 (worktrees reais rodam juntas; outro repo, pasta sem Git, inexistente ou relativa cai na lane do token) seguem passando.
- Limites (item c, não feito):
  - Conferir se o `cwd` declarado é igual ou ancestral do cwd real do processo que pediu não é barato no macOS. Exige `lsof -p <pid> -d cwd` por pedido, que também é o caminho caro de `runtime/process-cwds.ts`, ou um helper nativo novo com `proc_pidinfo`.
  - No caminho darwin-job, o pid é o supervisor e o cwd dele é o do pane, de antes do `cd <worktree>` da linha. A checagem recusaria justamente o caso legítimo do F-1229.
  - Por isso um agente no checkout ainda pode declarar uma worktree registrada e rodar um segundo job pesado no checkout em paralelo, um por worktree registrada. Isso fica visível no trace (`heavy-command-lane`, com raiz e pid), e os limites de máquina continuam valendo.
