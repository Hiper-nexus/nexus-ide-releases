# F-138 — Regras do scanner usam linhas commitadas para revisar arquivos atuais

## F-138 | categoria: funcional | severidade: alta | status: corrigido
- Tela/fluxo: análise de qualidade de candidato com alterações sem commit.
- Arquivo:linha: `src/main/context/candidate-quality-scanner.ts:181`; `src/main/context/candidate-working-tree-snapshot.ts:147`.
- Passos: 1) Manter HEAD e editar uma nova linha do produto no working tree. 2) Introduzir nela um defeito coberto por regra que depende de lineWasAdded. 3) Executar análise civil.
- Esperado: fontes, mapa de linhas alteradas e recibo correspondem ao mesmo candidato, incluindo mudanças sem commit.
- Observado: scanner monta addedLines por diff baseSha→headSha, mas lê os arquivos atuais. Regras em `candidate-quality-analysis.ts:160,247,431` filtram por esse mapa. Ausência de achados bloqueantes pode aprovar mesmo quando a análise declara complete=false.
- Evidencia: RED em `candidate-quality-scanner.test.ts`: três repositórios Git temporários reais, com instrução inalcançável adicionada na linha 3 em arquivo dirty, staged ou untracked, retornavam zero findings. GREEN: os três casos agora retornam finding high na linha correta, sem alterar HEAD nem bytes do index. A suíte também cobre adições commitadas, rename/delete, diretório sem Git, mudança de HEAD/arquivos durante o scanner, limites e alteração de hash com mesmos caminhos/tamanho.
- (resolvedor) Correcao: opção explícita `candidateSource: 'working-tree'` compara base com o disco atual e inclui arquivos untracked; o modo default continua usando o diff commitado. `captureWorkingTreeCandidate` reutiliza o runner Git protegido e leitura com descriptor de workspace, não faz stage/commit nem escreve objetos/index. Sem Git (ou comparação Git insegura), o snapshot usa inventário limitado do diretório. Metadados de runtime, build/vendor e nomes de segredo seguem o escopo excluído do indexador existente. O scanner compara snapshots antes/depois, revalida os bytes lidos e vincula seus hashes ao recibo; mudança observada, leitura insegura ou truncamento produz `complete: false` com motivo. O caller civil ativa a opção em F-139; este finding não altera políticas de aprovação, não exige Git/documentos novos e não cria espera ou confirmação para o operador.
- Validacao: `npx vitest run src/main/context/candidate-quality-scanner.test.ts src/main/context/candidate-working-tree-snapshot.test.ts src/main/context/candidate-quality-analysis.test.ts` passou 24/24 (13 scanner, 6 snapshot, 5 regras). `npm run typecheck` passou e `git diff --check` passou. Revisão independente de `/root/competitors` não encontrou bloqueador no escopo. Sem apps iniciados, credenciais acessadas ou commit nesta tarefa.
- Limite: snapshot e análise são limitados e detectam alterações observadas; não são um snapshot imutável do filesystem nem prova de execução da aplicação. Diretórios sem Git são examinados como candidato de arquivos, sem alegar quais linhas foram introduzidas pela missão. Os testes usam Git/arquivos reais temporários, mas não uma missão end-to-end com CLI/LLM.
- Relacionado: F-132, F-134.
