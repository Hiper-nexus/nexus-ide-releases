# F-1422 — "active worktree writers disagree on checkout root or integration ref" bloqueia writers isolados

## F-1422 | categoria: funcional | severidade: alta | status: corrigido
- Fluxo: `nexus_pane_spawn({ isolatedWriter: true })` com outro writer isolado
  ativo. A reserva da worktree falhava com
  `WorktreeStateConflictError: active worktree writers disagree on checkout root or integration ref`,
  e o worker não nascia.
- Esperado: writers isolados do mesmo checkout nascem em paralelo, mesmo com
  bases diferentes e mesmo depois de a integração avançar ou trocar de branch.
  Só uma raiz de checkout diferente é recusada, e a mensagem diz qual valor
  diverge e de quem.

### Causa raiz
- `src/main/runtime/worktree-state.ts:233-235` (base `d4e939586a^`):
  `validateWorktreeStateSnapshot` exigia um único `integrationRef` entre
  **todos** os registros ativos (`reserved`/`ready`/`queued`).
- O `integrationRef` de cada registro é o HEAD simbólico do checkout de
  coordenação no instante da reserva. Quando o operador (ou outro agente)
  troca o branch desse checkout, o snapshot passa a ter dois refs. A partir
  daí, todo writer novo é recusado enquanto houver um ativo do branch
  anterior, mesmo com `baseRef` explícito.
- Bases diferentes (`baseSha`) no mesmo ref sempre foram aceitas. O teste
  "A na base X, integ avança, B na base Y" passa antes e depois da correção,
  então o avanço da integ não é a causa.
- A mensagem não dizia qual campo divergia nem de quem.

### Evidência (somente leitura)
- `runtime.sqlite3`, tabela `worktree_state`, rev 272: havia writers `ready`
  com `integrationRef` `refs/heads/feat/orc-outbox…` ao lado de reservas
  novas em outro ref.
- Reflog do checkout principal: troca para `t3`/`t31`/`t32` entre 18:41 e
  18:45 (hora local), com writers ainda ativos.

### Correção (`d4e939586a`)
- Removida a unicidade do `integrationRef` entre ativos. Cada registro integra
  só no próprio ref, e a fila de merge já confere na hora que o checkout está
  nele (`inspectIntegration` → "integration branch changed"). A retomada da
  mesma task continua exigindo raiz e ref iguais (`worktree-manager.ts`).
- A raiz (`rootRealPath`) continua única entre ativos. A mensagem agora é
  `active worktree writers disagree on checkout root: writer <worker> (mission
  <m>, task <t>, <status>) has <root>, writer <worker2> (...) has <root2>`
  (`describeWriter`, `worktree-state.ts:35`, verificação em `:242-251`).
- Desvio do pedido: o pedido era recusar também "outro branch de integração".
  Isso foi deixado de fora de propósito. Recusar no snapshot é exatamente o
  bloqueio de produção, e a proteção certa já existe por registro, no merge.

### Testes (`c8572a9167`, `src/main/runtime/worktree-manager.test.ts:417`)
1. Writer A ativo na base X, a integ avança, writer B nasce na base Y.
2. O checkout de coordenação troca de branch com A ativo, e B ainda nasce (o
   caso de produção).
3. Uma raiz divergente continua recusada, e a mensagem diz o valor e de quem.
- Esse teste substitui o antigo F-1253 "dois ativos com refs diferentes são
  recusados", que codificava o bloqueio.
