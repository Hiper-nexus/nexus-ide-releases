# F-1429 — Writer em worktree aninhada sem recibo de worktree e sem retomada no rework

## F-1429 | categoria: orquestração / via-rápida | severidade: alta | status: corrigido
- Tela/fluxo: `nexus_pane_spawn` com `cwd` em raiz de git worktree aninhada no workspace, recibo de execução e `nexus_handoff_ack` com `verdict: "rework"`.
- Arquivo:linha:
  - `src/main/orch/tools-panes.ts`
  - `src/main/orch/isolated-writer-worktree.ts`
  - `src/main/runtime/worktree-manager.ts`
  - `src/main/runtime/worktree-runtime-registry.ts`
  - `src/main/runtime/worktree-state.ts`
  - `src/main/orch/tools-panes-isolated-writer.test.ts`
- Passos para reproduzir:
  1) Orquestrador abre um writer com `nexus_pane_spawn({ cwd: "<repo>/.harvest/s243-<fix>", ... })`, onde `cwd` é a raiz de outra git worktree do mesmo repositório aninhada no workspace;
  2) Inspecionar o recibo retornado por `nexus_pane_spawn`;
  3) O worker entrega com sucesso e o pane auto-fecha;
  4) O orquestrador envia `nexus_handoff_ack({ handoffId, verdict: "rework", note: "..." })`.
- Esperado:
  1) O recibo do spawn deve retornar `executionMode: "isolated_worktree"` com o bloco `isolatedWorktree` (`branch`, `worktreePath`, `baseSha`);
  2) O registro durável do worker é persistido no registry de worktrees associado ao `paneId`/`sessionId`;
  3) No `nexus_handoff_ack({ verdict: "rework" })`, o writer fechado é reaberto via `resume` nessa mesma worktree com a nota como prompt (`reworkDelivered: true, reworkVia: "resume"`);
  4) Quando `cwd` aponta para o checkout principal, o comportamento permanece intacto (`executionMode: "same_checkout"`).
- Observado:
  1) O recibo retornava `executionMode: "same_checkout"` e `isolatedWorktree: undefined`;
  2) Nenhum registro durável de worktree era criado para o worker;
  3) Ao pedir rework no `nexus_handoff_ack`, o sistema respondia: `reworkDelivered: false, reworkReason: "writer encerrado sem worktree própria (rodou no checkout compartilhado): abra um writer novo com a nota"`.

## Causa Raiz
1. Em `nexus_pane_spawn` (`tools-panes.ts`), a resolução do escopo (`prepareExecutionScope`) reconhecia que `cwd` era a raiz de uma worktree aninhada e isolava o escopo de execução (`nested`), mas não tratava o writer como um `isolatedWriter` alocado;
2. `WorktreeManager` e `WorktreeRuntimeRegistry` suportavam apenas a criação/materialização de novas worktrees (`allocateMissionTaskWorktree` / `allocatePaneWriter`), não possuindo um método para registrar uma worktree Git aninhada preexistente;
3. O validador de registros `validateRecord` em `worktree-state.ts` aplicava regras estritas destinadas apenas a worktrees gerenciadas pelo Nexus (`acceptedWorktreePaths` e `worktreeBranchRef`), rejeitando registros com caminhos reais de worktrees aninhadas e branches existentes (`refs/heads/...`);
4. Sem o registro no `WorktreeRuntimeRegistry` vinculado ao `sessionId` do worker, `isolatedWriterPaneOfSession` não localizava o pane e o `nexus_handoff_ack` tratava o worker encerrado como pertencente ao checkout compartilhado, recusando a reabertura via `resume`.

## Correção Implementada
1. **Validação de estado (`src/main/runtime/worktree-state.ts`):**
   - Atualizado `validateRecord`: para registros `ownerKind === 'pane'`, são aceitos caminhos de worktree contidos em `rootRealPath` com caminho absoluto resolvido (distintos da raiz de coordenação), e branches que sejam referências válidas de integração/heads.
2. **Registro de worktree aninhada (`src/main/runtime/worktree-manager.ts` & `worktree-runtime-registry.ts`):**
   - Implementado `registerExistingPaneWriter`: verifica que `worktreePath` está contido no repositório, valida via `rev-parse --show-toplevel` que é um top-level válido do Git, e grava um `WorktreeRecord` com `ownerKind: "pane"`, `status: "ready"`, `branchRef`, `baseSha` e `taskId`.
   - Exposto o método através de `WorktreeRuntimeRegistry.registerExistingPaneWriter`.
3. **Adoção do writer (`src/main/orch/isolated-writer-worktree.ts`):**
   - Criada a função `adoptNestedWorktreeWriter(scope, missionId, nested, claim, git)`: extrai a branch e baseSha da worktree aninhada via Git, cadastra o registro no runtime registry e rastreia a alocação (`trackAllocation`).
4. **Integração no spawn (`src/main/orch/tools-panes.ts`):**
   - Quando `nested && nested.cwd === nested.scope.rootRealPath` (tanto para `operatorHand` quanto para worker de missão), adota a worktree via `adoptNestedWorktreeWriter`.
   - Isso preenche `isolatedWriter`, gerando o recibo com `executionMode: "isolated_worktree"` e registrando os bindings de sessão/pane.
   - No `isolatedReceipt`, evitou a marcação indevida de `cwdDiscarded` quando o `cwd` requisitado coincide com a própria worktree adotada.
