# F-1434 — Windows: todo comando pesado do Bash de um pane Claude era recusado como "CPU/RAM indisponível"

## F-1434 | categoria: funcional | severidade: alta | status: corrigido
- Tela/fluxo: pane Claude Code no Windows (o Bash da CLI é o Git Bash) → `node`, `npm`, `npx`, `tsc`, `vitest`, build → guard de admissão do `BASH_ENV` (`resources/heavy-command/shell.bash`) → `request.cjs` → `POST /hook/heavy-command` do Main.
- Arquivo:linha:
  - `resources/heavy-command/shell.bash:48` (antes) — mandava `${BASHPID:-$$}`; `shell.zsh:29` mandava `$$`.
  - `src/main/pty/owned-command-process.ts:34` — o Main só admite PID que está na árvore real do PTY do pane.
  - `resources/heavy-command/dispatch.cjs:17`, `shell.bash:48`, `shell.zsh:29`, `preload.cjs:89` — a última linha sempre culpava CPU/RAM.
  - `resources/heavy-command/request.cjs` — recusa sem mensagem do Main (e Main fora do ar) saía muda com 78.
  - `src/main/orch/native-heavy-command.ts` — só a espera na fila tinha `message`; as outras cinco recusas não diziam nada.
- Passos: 1) No Windows, abrir um pane Claude Code pelo "+ Pane". 2) Pedir `npx vitest run x.test.ts` (ou qualquer `node -e` com `require`). 3) Sai na hora com exit 78.
- Esperado: o comando é admitido (há 47 GB livres de 63 GB); quando o Nexus recusar, a mensagem diz o motivo verdadeiro.
- Observado (13/10, 0.76.245): `[Nexus] Heavy command not started: physical CPU/RAM admission unavailable.` em ~0,4 s, com a máquina ociosa. O trace do Main (`%APPDATA%\NexusIDE\logs\main.trace.ndjson`) registra `heavy_command_process_ownership_unproved` em cada tentativa (elapsedMs 300–510).
- Causa raiz: no Git Bash (MSYS2/Cygwin), `$$` e `BASHPID` são PIDs do runtime POSIX, não do Windows. Medido no pane: `$$=9613`, `BASHPID=9613`, `/proc/$$/winpid=18232`. O Main procura o 9613 entre os descendentes Win32 do `claude.exe` do pane, não acha e recusa. Pelo PowerShell o mesmo comando passava, porque o `preload.cjs` usa `process.pid` (PID real). No Windows o hook PreToolUse (`tool-hook.cjs`) nem é instalado (`hook-status-config.ts:149`), então o guard do `BASH_ENV` é o único caminho do Bash. Workers de squad que são Claude Code não conseguiam rodar teste, typecheck, build nem `npm install`.
- Correcao:
  - `shell.bash`/`shell.zsh`: quando `/proc/<pid>/winpid` existe (MSYS2/Cygwin), o guard envia esse PID; em macOS/Linux nada muda (`/proc/<pid>/winpid` não existe).
  - `request.cjs`: toda saída 78 escreve `nexus-heavy: <motivo>` no stderr (endereço inválido, pedido inválido, proxy não local, recusa do Main com o `reason`, HTTP ≠ 200, resposta ilegível, Main que não responde com o código do erro, canal com integridade quebrada). Nunca imprime token, corpo ou endereço remoto.
  - Main (`native-heavy-command.ts`): cada recusa traz `message` própria — pedido malformado, terminal sem autoridade, PID fora da árvore do pane (com o PID), lease herdado não provado, processo que mudou durante a admissão, e as recusas do pool (Nexus encerrando, pedido cancelado, fila cheia, autoridade perdida na espera).
  - Fila (`heavy-command-permit.ts`): a espera que estoura diz a causa real — vaga da raiz ocupada, limite de jobs paralelos da máquina, swap acima do limite, ou RAM livre abaixo da reserva (com os GB). RAM só é citada quando faltou RAM.
  - Última linha do shell/preload/dispatch: `[Nexus] Heavy command not started: Nexus did not admit it (reason above).` O prefixo que `pane-boot-diagnosis.ts` reconhece continua igual. As recusas de configuração dos hooks do Claude, AGY e Muse deixaram de citar CPU/RAM.
  - Não afrouxa nada: a fila por raiz, o limite de jobs da máquina e a reserva de RAM continuam os mesmos.
- Evidencia:
  - RED (código antigo): `heavy-shell-admission-pid.test.ts` 3/3 falham — `expected { pid: 11524 } to match { pid: 21808 }` (PID MSYS × PID do `bash.exe`), a recusa casa `/CPU\/RAM/`, e Main fora do ar sai sem motivo. `native-heavy-command.test.ts` "F-1434: toda recusa…" falha com `expected undefined to be 'nexus-heavy: could not prove that pid…'`.
  - GREEN: os 4 testes passam no Windows (Git Bash real em `Git\usr\bin\bash.exe`).
  - Sem regressão: `npx vitest run src/main/orch/native-heavy src/main/orch/heavy-command src/main/orch/heavy-shell src/main/pty/owned-command-process` → 23 falhas antes e as MESMAS 23 depois (ambiente Windows: caminhos POSIX, `/bin/bash`, `make`, Perl), 392 → 396 passando.
  - `tsc --noEmit` limpo; `oxlint` sem achados nos arquivos tocados.
