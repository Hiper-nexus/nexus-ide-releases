# F-1334 — recusa anterior a todo efeito ainda dizia `effectMayHaveCommitted: true`

## F-1334 | categoria: funcional | severidade: baixa | status: corrigido
- Tela/fluxo: despacho MCP de ferramenta com efeito → handler lança uma recusa → `mcp-dispatch.ts:1934-1936` só limpa `effectMayHaveCommitted` para `PreEffectRefusalError` (F-1013).
- Arquivo:linha (antes):
  - `src/main/orch/tools-context.ts:652`: `nexus_sensor_run` chamava `assertOrchestratorMission`, que lança `Error` comum, antes de resolver o serviço de workflow e de rodar o sensor.
  - `src/main/orch/tools-panes.ts:1320`: no `nexus_pane_spawn` com `agentName`, a recusa "squad agent spawn requires a mission bound to a squad" também era `Error` comum.
  - `src/main/orch/tool-util.ts:1688`: recusa da admissão de panes por teto (ver abaixo).
- Passos (sonda A2 e orquestrador, ao vivo):
  1. `nexus_sensor_run` chamado por um worker.
  2. `nexus_pane_spawn { agentName }` numa missão sem squad.
  3. `nexus_pane_spawn` com o teto de panes cheio.
- Esperado: uma recusa determinística anterior a toda escrita volta sem `effectMayHaveCommitted`.
- Observado: `{ error:'only the mission orchestrator is authorized', effectMayHaveCommitted:true }`, e o mesmo nas duas recusas de spawn.
- Evidencia (RED, fonte anterior, Node 22):
  - `mcp-dispatch-security.test.ts` › "F-1334: sensor_run refused to a worker…": `expected true to be undefined`.
  - `tools-panes-worker-spawn.test.ts` › "agentName sem squad (F-1334)": `expected Error: squad agent spawn requires a missi… to be an instance of PreEffectRefusalError`.
- (resolvedor) Correcao:
  - Causa raiz: as duas recusas usavam `Error` comum em pontos que precedem toda mutação. O dispatcher não tem como distinguir uma recusa de uma falha no meio do efeito.
  - `nexus_sensor_run`: `refuseBeforeEffect(() => assertOrchestratorMission(…))`, o mesmo padrão do `mission_set_status` (`tools-domain.ts:805`). O teste confirma que o serviço de workflow nem chega a ser resolvido.
  - Recusa `agentName` sem squad: virou `PreEffectRefusalError`.
    - O que roda antes dela não grava nada: licença, papel, `expect`, `childMissionId` e leituras do store e do roster. A missão da aba só nasce para `role: user`, que esta recusa exclui.
    - Exceção: um `resume` dentro de missão reserva a continuação do worker (`captureMissionPaneResume`). O `finally` (`tools-panes.ts:2639`) desfaz essa reserva, mas a compensação pode falhar. Nesse caso a recusa continua `Error` comum.
  - **Recusa por teto de panes: NÃO é pré-efeito, e ficou como estava.** No `nexus_pane_spawn`, o handler já fez estes efeitos antes de chegar à admissão (`spawnPaneAndMaybePrompt`, `tools-panes.ts:2442` → `tool-util.ts:1688`):
    - consumiu a RouteReservation durável de uso único (`consumeReservedRoute`, `tools-panes.ts:2115`). O `finally` não a devolve;
    - gravou o `route_log` do modo livre (`:1898`);
    - reservou a vaga de `maxWorkers` (`:1977`);
    - pode ter alocado uma worktree isolada (`:2076`).

    `effectMayHaveCommitted: true` é verdadeiro ali: a reserva de rota foi gasta e o orquestrador precisa rotear de novo. Para tornar essa recusa pré-efeito, a admissão teria de rodar antes do consumo da reserva. Isso é uma mudança de desenho e fica fora deste fix.
  - Validação (Node 22): `npx vitest run src/main/orch/tools-panes-worker-spawn.test.ts src/main/orch/mcp-dispatch-security.test.ts` deu 124/124. Typecheck limpo.
