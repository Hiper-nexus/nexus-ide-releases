# F-1040 — Outbox transacional de efeitos, recibo de comando e reconcile de boot (ORC-01/04/06)

## F-1040 | categoria: confiabilidade | severidade: alta | status: reaberto
- Tela/fluxo: motor de missão › efeitos com efeito (spawn, checkpoint, refresh) › crash/restart do Main no meio de um efeito › retry de `nexus_*` após timeout.
- Arquivo:linha (antes): `src/main/orch/handoff-delivery-outbox.ts` (só handoff, sem lease nem classe); `src/main/orch/mcp-dispatch.ts` (`effectMayHaveCommitted` booleano, sem recibo durável); `src/main/orch/pane-start-watchdog.ts` (vigia início, não morte do Main no meio do turno); `src/main/runtime/project-runtime-schema.ts` (sem `effect_outbox`/`command_receipts`).
- Passos: 1) Worker de missão dispara um efeito (spawn de pane, checkpoint.capture). 2) O Main morre entre o claim e o settle. 3) No boot, o efeito ou re-executa (pane duplicado) ou some (missão que não termina). 4) O agente retenta o `nexus_*` e cai em `effectMayHaveCommitted` sem saber se o efeito valeu.

- Observado (estudo T3 Code @ 26285ab, `docs/analysis/t3code-crosswalk-26285ab.md`, linhas ORC-01/02/04/06): o T3 separa efeitos em `PROCESS_BOUND` (turno/pedido amarrado ao processo) e `REPLAY_SAFE` (idempotente), assenta sob lease e reconcilia no boot. O Nexus só tinha o outbox de handoff.

- (resolvedor) Correção (porte da POLÍTICA T3; casca reescrita em better-sqlite — Effect-TS não encaixa no Main; nenhum arquivo do T3 foi copiado byte a byte):
  1. **ORC-01** — `src/main/orch/effect-outbox.ts` + migration `048-effect-outbox-command-receipts`:
     - Tabela `effect_outbox` (mesmo vocabulário do T3: `pending|running|succeeded|failed|cancelled`, `lease_owner`/`lease_expires_at`, `attempt_count`, `available_at`, `completed_at`, `last_error`).
     - Classe deriva do TIPO do efeito (não de campo livre): `PROCESS_BOUND_EFFECT_TYPES` = `turn.start|turn.interrupt|turn.steer|turn.restart|runtime-request.respond`; `REPLAY_SAFE_EFFECT_TYPES` = `runtime.continue|session.detach|thread.rollback|checkpoint.capture|terminal.cleanup|attachment.cleanup|thread-title.generate|delegated-tasks.stop`.
     - `enqueue` ignora id determinístico já existente (política T3). `claimNext` é por lease, em ordem por thread, sem pular efeito anterior pendente do mesmo thread; título tem faixa própria.
     - Só o dono do lease assenta `succeed`/`retry`/`fail`.
  2. **ORC-04** — `src/main/orch/command-receipts.ts`:
     - Tabela `command_receipts` com `resultSequence`, status `accepted|rejected`, aggregate `thread|project`.
     - `insertIfAbsent` = primeiro aceite (segunda chamada com o mesmo `commandId` não sobrescreve); `upsert` assenta sequence/erro. Recibo com sequence 0 = não assentado (marca honesta, como o T3).
  3. **ORC-06** — `src/main/orch/provider-runtime-recovery.ts` + `reconcileAfterProcessLoss`:
     - PROCESS_BOUND em `pending` OU `running` → `cancelled` ("Cancelled because the server process ended before the effect completed.") — não reexecuta, evita pane duplicado.
     - REPLAY_SAFE em `running` → `pending` ("Requeued after the previous server process ended.") — reentra.
     - REPLAY_SAFE em `pending` já é reexecutável e fica. `succeeded`/`failed` intocados.
     - `pruneSettled` poda `succeeded|cancelled` (7d, política T3); `failed` fica.
  4. **Worker** — `src/main/orch/effect-outbox-worker.ts`: um passe drena sob lease; handler que lança assenta pela classe (process_bound falha; replay_safe retenta com backoff). Um passe não reivindica de novo o que já tentou.
