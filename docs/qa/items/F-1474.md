# F-1474 — Windows: hook do Nexus estoura o tempo do Claude e despeja o comando em base64 na tela

## F-1474 | categoria: funcional | severidade: média | status: corrigido
- Tela/fluxo: pane Claude Code no Windows → operador envia um prompt → hook `UserPromptSubmit` do Nexus (`/hook/delegate`, conselho do Jev) roda por `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -EncodedCommand <base64>`.
- Arquivo:linha:
  - `src/main/orch/hook-status-config.ts` (antes ~113) — `UserPromptSubmit` com `timeout: 5`, enquanto o script (`src/main/orch/hook-delegate-command.ts:26`) espera até `-TimeoutSec 4`.
  - Mesmo aperto em `PostToolUse` (fila de entregas, `-TimeoutSec 3`, antes ~102) e `PreToolUse` `Agent|Task` (aviso de subagente, `-TimeoutSec 2`, antes ~144).
- Passos: 1) No Windows, com vários panes e comandos pesados rodando, enviar prompts num pane Claude do Nexus. 2) De vez em quando o prompt sai com o bloco vermelho.
- Esperado: o hook entrega o contexto ou sai em silêncio; nada de erro na tela.
- Observado (13/10, print do operador): `UserPromptSubmit hook [powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -EncodedCommand JABlAG4A…]` em vermelho, terminando em `hook's "timeout" to allow more time.`, a cada prompt com a máquina carregada.
- Causa raiz: no Windows o `powershell.exe` (5.1) leva de 1 a 3 s só para abrir, mais com a máquina carregada. Com o teto de 5 s do Claude e o script esperando até 4 s pelo Main, sobrava cerca de 1 s para a abertura. Quando a abertura passava disso, o Claude matava o hook antes do `catch { exit 0 }` do script e mostrava o comando inteiro como erro. No macOS e no Linux o `curl` abre na hora, então 5 s basta.
- Correcao:
  - `shortHookTimeoutSeconds(platform)`: 20 s no Windows, 5 s nos demais. Os três hooks curtos dos settings do Claude (delegação, fila de entregas, aviso de subagente) passam a usá-lo.
  - Os scripts continuam limitando a própria espera (`-TimeoutSec 4/3/2`) e saem 0 em silêncio quando o Main não responde: o teto maior só deixa o PowerShell terminar de abrir.
  - `withPowerShellStartupMargin(seconds)`: os hooks longos do Claude (triagem 15 s × `-TimeoutSec 8`, integração, permissão e regressão, que tinham só 5–10 s de folga) ganham +10 s no Windows; nos demais sistemas o teto não muda. Achado da revisão independente (Kimi).
  - Codex e Kimi não mudam (o Codex usa o padrão de 600 s; o schema do Kimi não tem timeout).
- Evidencia:
  - RED (código antigo, teste novo): `npx vitest run src/main/orch/hook-status-config.test.ts -t "F-1474"` → 2 falham (`shortHookTimeoutSeconds is not a function`; os três hooks com teto 5).
  - GREEN: os 3 testes F-1474 passam (teto curto, uso nos três hooks, folga dos hooks longos).
  - Sem regressão: o arquivo inteiro no `main` dá 13 falhas e 5 passando (13 testes assumem comando POSIX em texto puro; no Windows o comando vai em base64 — falha de plataforma pré-existente); com a correção, as MESMAS 13 falhas e 8 passando.
  - Revisão independente (Kimi, somente leitura): RESSALVAS — folga apertada dos hooks longos, corrigida acima; teto de 20 s só atrasa o prompt se o powershell.exe travar por completo (a espera real segue limitada pelo `-TimeoutSec` do script).
