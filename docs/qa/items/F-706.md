# F-706 — Worker Muse no Windows abre e fica horas sem receber a tarefa

## F-706 | categoria: funcional | severidade: alta | status: corrigido
- Tela/fluxo: worker Muse Code 1.4.1 aberto pela missão no Windows.
- Arquivo:linha: `src/main/pty/pty-manager.ts` (resolução do executável no win32), `src/main/adapters/muse-windows-launcher.ts` (novo).
- Passos: 1) A rota manda uma tarefa ao Muse. 2) O pane abre.
- Esperado: o Muse começa a tarefa e entrega o handoff.
- Observado (30/09): print do operador com o Muse ("Muse Code 1.4.1 … muse-spark-1.3 · medium · YOLO") parado com o composer vazio. Queixa: "muse não chegando nada para ele". No trace, os workers Muse viveram 39 min, 15 min e 2h56 até o fechamento, e nenhum deles tem handoff no `runtime.sqlite3`.
- Evidencia: no Windows o Muse é `muse.cmd` → `.muse-launcher.ps1` → `muse-bin-<versão>.exe`. Como `.cmd`, o brief sai do argv (F-670) e vai para a colagem depois do boot (`deliverAgentPrompt`), que no Muse não pegava; a falha só ia para o console do Main. O binário aceita o prompt posicional (`muse [OPTIONS] [PROMPT]`): aberto direto por PTY com um brief de duas linhas, ele começou o turno sozinho.
- Causa: o Nexus sabia abrir direto os atalhos npm (F-668), mas o Muse usa um launcher PowerShell próprio.
- (resolvedor) Correcao: `windowsMuseLauncherSpawn` faz o que o launcher faz na hora de rodar. Confere que o `muse.cmd` é o launcher oficial (referencia `.muse-launcher.ps1`, que existe ao lado), lê `.muse-version` no mesmo formato do launcher, abre `muse-bin-<versão>.exe` e repassa `MUSE_RELEASE_INFO` quando a versão confere. Com um `.exe`, o brief fica no argv. Fora desse formato, segue o caminho antigo. Teste: `muse-windows-launcher.test.ts`.
