# F-789 — MiniMax Code encerra antes do primeiro turno do writer

## F-789 | categoria: funcional | severidade: alta | status: corrigido
- Tela/fluxo: spawn de `minimax-code` (`mcode`, npm) como writer de missão, e qualquer pane MiniMax aberto pelo Nexus.
- Arquivo:linha: `src/main/pty/pty-manager.ts:2409` (spawn do MiniMax); `src/main/adapters/minimax-node-runtime.ts:192`; `src/main/persistence/provider-config-store.ts:194` (permit da CLI).
- Passos: 1) Delegar uma tarefa ao adapter `minimax-code`, modelo `minimax/MiniMax-M3`, com o Nexus rodando com o Node 22 à frente do Node 26 no PATH. 2) Aguardar o primeiro turno.
- Esperado: a TUI fica viva, carrega a sessão e recebe a tarefa.
- Observado: o processo termina com código 1 depois de ~9 a 10 s, em "Loading session"; a tarefa recebe `pane-not-started` (`boot-exit`). Missão "Terminais", 03/10: `pane-mushkg92-1t` (`uptimeMs: 10085`, reroteado para o DeepSeek) e `pane-mushp3iq-28` (`uptimeMs: 8686`, não reroteado). A saída que explicaria a falha não era guardada.
- Evidencia: saída capturada no PTY com o spawn spec real do Nexus (smoke, abaixo, sem segredo):
  - `MCode could not load its native SQLite dependency.`
  - `Original error: … better_sqlite3.node' was compiled against a different Node.js version using NODE_MODULE_VERSION 147. This version of Node.js requires NODE_MODULE_VERSION 127.`
  - O pacote é o `@minimax-ai/code` 0.5.5 (`engines: node >=22.19 <23 || >=24 <27`). O `process.dlopen` do addon falha no `/opt/homebrew/opt/node@22` (ABI 127) e funciona no `/opt/homebrew/bin/node` 26.9.0 (ABI 147).
- Causa: o `mcode` do npm abre com `#!/usr/bin/env node`, isto é, pelo primeiro Node do PATH. O SQLite nativo dele (better-sqlite3) foi compilado para o Node 26 na instalação. Quando o Nexus roda com o Node 22 à frente no PATH, a TUI sobe e morre ao abrir o banco. `mcode --version` não carrega o SQLite, por isso a detecção de CLI não via nada.
- (resolvedor) Correcao:
  - `src/main/adapters/minimax-node-runtime.ts` (novo): decide qual Node roda o `mcode`.
    - Valida que o lançador é o `cli.js` do pacote `@minimax-ai/code` (`package.json`, `bin`) e acha o addon do better-sqlite3 como o `require` do pacote acharia.
    - Lista os `node` do PATH do spawn como o `env` do shebang faria: na ordem, pulando link quebrado e arquivo sem permissão, sem repetir o mesmo realpath.
    - Sonda com `node -e "process.dlopen(…)"` em **subprocesso assíncrono** (`execFile`, timeout de 5 s, env vazio: sem HOME, token, JS do pacote ou banco aberto).
    - O resultado fica em cache por realpath+mtime+tamanho do addon e de cada Node; timeout não entra no cache.
    - Só troca o Node com prova de que o do shebang **não** carrega o addon e outro carrega. Nesse caso o spawn vira `<node que carrega> <cli.js real> …`. Se nenhum carrega (`incompatible`), segue pelo shebang com aviso no log; a CLI morre com a própria mensagem, que agora fica na cauda do `pane-not-started`.
    - Nunca recompila nem reinstala o pacote.
  - `src/main/persistence/provider-config-store.ts`: `acquireCliSpawnPermit('minimax-code')` prepara a decisão depois de travar o lançador e antes do spawn síncrono, para o binário ativo (`activeProviderBinary`) e o PATH do processo. O permit é o portão assíncrono por onde passam os spawns do renderer (`pty-ipc`) e os do Main (`main-owned-pane-runtime`). Erro na decisão nunca segura o permit.
  - `src/main/pty/pty-manager.ts`: o spawn (síncrono) só consulta a decisão pronta para o mesmo lançador e o mesmo PATH. Sem decisão (warm pool, que não passa pelo permit), segue pelo shebang e dispara a preparação para o próximo spawn. Uma preparação mais antiga nunca sobrescreve a decisão de uma mais nova. O lançamento é aplicado com argv final, antes do sandbox e do tmux.
  - O que mudou em relação ao começo salvo do worker: a sondagem era `execFileSync` (até 2,5 s por Node) **no Main, a cada spawn**. Passou a ser assíncrona, em cache e fora do caminho síncrono do spawn.
  - Cauda sanitizada do PTY no `pane-not-started`: ver F-788 (mesmo commit, `f23cf27e`).
- Validação:
  - `src/main/adapters/minimax-node-runtime.test.ts`: 8 testes.
    - Node do shebang com ABI errado: fixa o Node que carrega, com o entrypoint real; o spawn só lê a decisão do mesmo lançador e PATH.
    - Node do shebang que carrega: nada muda, uma sonda só.
    - Nenhum carrega: `incompatible`, addon intocado.
    - Timeout: mantém o shebang e não entra no cache.
    - Cache por mtime: o spawn seguinte não sonda; addon reinstalado sonda de novo.
    - Symlink repetido conta uma vez e link quebrado no PATH é pulado.
    - Outro pacote ou instalação sem addon: nenhuma sonda.
    - Sonda real: addon inválido dá `fails`, Node inexistente dá `unknown`.
  - `src/main/pty/pty-manager.test.ts` ("F-789: MiniMax abre pelo Node que carrega…"): sem decisão, o spawn é o shebang de sempre; com a decisão do permit, é `<node26> <cli.js> --model …`. Com o `pty-manager.ts` anterior falha.
  - `src/main/persistence/provider-config-spawn.test.ts` (2 testes novos): o permit do `minimax-code` só libera depois da decisão, para `/usr/local/bin/mcode`; o de outra CLI não sonda; erro na decisão não segura o permit. Com o `provider-config-store.ts` anterior falha.

Roda o `mcode` 0.5.5 instalado por 20 s, sem prompt (nenhuma chamada de modelo), com o PATH do teste começando pelo Node 22, como no incidente. O login é o do perfil nativo, só lido pela CLI.

  - Vizinhos: 12 arquivos, 439 testes passaram e 8 foram pulados (lista no F-788). `npm run typecheck` limpo.

Um teste em `provider-config-deepseek.test.ts` trava o comportamento: o inventário não bloqueante dá o DeepSeek pronto (`authState: ok`, modelos prontos) pelo índice cifrado, sem decifrar a chave.
- Riscos:
  - A primeira preparação sonda até um processo `node` por candidato, normalmente 1 ou 2, de 0,25 a 0,3 s cada nesta máquina carregada, sem bloquear o Main; as seguintes só fazem `realpath`/`stat` assíncronos. Isso adiciona essa latência ao permit do primeiro pane MiniMax.
  - Spawn pelo warm pool, que não passa pelo permit, usa a última decisão ou o shebang. Se o operador reinstalar o `mcode` com outro Node entre dois spawns desse tipo, o primeiro pode usar a decisão velha. Se falhar, a cauda do `pane-not-started` mostra o motivo, e o spawn seguinte já decide de novo.
  - Só o `node` do PATH é candidato. Um Node compatível fora do PATH (nvm, Cellar de outra versão) não é procurado; nesse caso o resultado é `incompatible`, e a correção é reinstalar o `mcode` com o Node em uso.
  - O `mcode` tem auto-update próprio (0.6.2 publicado), que não foi desligado no smoke por morar no config do operador. A instalação foi conferida e não mudou.
- Fora do escopo: Windows (o helper devolve `default`); reinstalar ou recompilar o pacote do operador; o `mcode` fixar o próprio Node.
