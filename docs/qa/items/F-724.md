# F-724 — DeepSeek sem escolha de provedor: a chave do Token Plan ia para api.deepseek.com

## F-724 | categoria: seguranca | severidade: alta | status: corrigido
- Tela/fluxo: Configurações › Contas de IA › DeepSeek; pane DeepSeek (CLI do Claude) aberto pelo "+ Pane", pela rota da missão ou pelo `nexus_pane_spawn`; pane Qwen Code com o DeepSeek.
- Arquivo:linha: `src/main/persistence/provider-config-store.ts` (`resolveDeepseekProviderKey` :638, `anthropicHostForProvider` :570, rota do DeepSeek no spawn :1160, recusa de conta fixada no plano :1263, setConfig :2916, `deepseekProviderChoiceInfo` :1936), `src/main/adapters/deepseek-provider.ts`, `src/main/adapters/launcher-provider-manager.ts` (rota `deepseek-token-plan` :205, `loadLauncherProviderBaseUrl` :435), `src/main/pty/pty-manager.ts` (`providerServedModel` :1334), `src/main/orch/task-router.ts` (`providerServedModel` :613), `src/main/adapters/qwen-settings.ts` (`settingsUseTokenPlan` :51), `src/renderer/components/settings/ProvidersPanel.tsx` (`ProviderChoiceField` :236, `KeyField` :89).
- Passos: 1) Ter a chave do Alibaba Model Studio Token Plan (`sk-sp-…`) no launcher (`deepseek=` com `deepseek-base-url` no endpoint da Alibaba, `dashscope=`), como na máquina do operador. 2) Abrir um pane DeepSeek ou deixar a rota escolher o DeepSeek. 3) Pedir o DeepSeek pelo Qwen Code.
- Esperado (pedido do operador, 02/10): "no DeepSeek me dá opção de usar direto pela DeepSeek ou pelo plano Alibaba, onde eu já tenho key também"; "fica operacional pelo plano tanto DeepSeek no Claude como DeepSeek pelo Qwen Code, e o Qwen 3.8 fica apenas pelo Qwen Code mesmo".
- Observado:
  - Não havia escolha de provedor: o adapter `deepseek` sempre apontava para `api.deepseek.com/anthropic`.
  - O `loadLauncherProviderKey('deepseek')` devolvia a chave `sk-sp-` do Token Plan, que o Nexus injetava como `ANTHROPIC_AUTH_TOKEN` contra api.deepseek.com. O pane falhava em 401 e a chave da Alibaba saía para um terceiro. O intent router (`api.deepseek.com/chat/completions`) recebia a mesma chave.
  - O `deepseek-flash` da rota trivial/easy não existe no plano (403).
  - O catálogo do Qwen Code descartava todo `deepseek-*`, então o DeepSeek não aparecia no Qwen Code.
- Evidencia:
  - `providers.conf` do operador (só nomes e igualdade, sem valores): `deepseek` == `dashscope`, prefixo `sk-sp-`, `deepseek-base-url` no host `token-plan.ap-southeast-1.maas.aliyuncs.com` (`/apps/anthropic`).
  - Sondas de 02/10 nos dois endpoints do Token Plan: `deepseek-v4-pro` 200, `qwen3.8-max` 200, `deepseek-v4-flash` 403.
  - 26 testes novos reprovam o código antigo, entre eles "nunca manda para api.deepseek.com a chave do Token Plan que o launcher amarra à Alibaba".
- Causa: o DeepSeek tinha uma origem só e lia a chave do slot `deepseek` sem conferir para qual host o launcher a amarrava.
- (resolvedor) Correcao:
  - Seletor "Provedor do DeepSeek" com "DeepSeek (API direta)" (padrão, comportamento antigo) e "Alibaba Token Plan". A escolha é gravada como `upstream` do adapter, e o setConfig recusa outros valores para o DeepSeek.
  - Rota `deepseek-token-plan`: `ANTHROPIC_BASE_URL` = `https://token-plan.ap-southeast-1.maas.aliyuncs.com/apps/anthropic`, `ANTHROPIC_AUTH_TOKEN` = chave do Token Plan e `ANTHROPIC_DEFAULT_HAIKU/SONNET/OPUS_MODEL` = `deepseek-v4-pro`. O `DEEPSEEK_API_KEY` é retirado do processo. A rota tem `scopedTo: 'deepseek'`: fica fora do seletor genérico e nenhuma outra CLI a escolhe.
  - Chaves disjuntas. A API direta usa o cofre `deepseek`, o `deepseek=` do launcher (só sem `deepseek-base-url` de outro host), `DEEPSEEK_API_KEY` e `ANTHROPIC_AUTH_TOKEN` com BASE_URL em api.deepseek.com. Chave `sk-sp-` nunca vai para a DeepSeek. O plano usa a chave do Qwen Code: cofre `qwen`, `qwen`/`dashscope`/`bailian` do launcher (com base URL no Token Plan, quando declarada), `BAILIAN_TOKEN_PLAN_API_KEY`/`DASHSCOPE_API_KEY` e `ANTHROPIC_AUTH_TOKEN` só com BASE_URL no host do Token Plan. O `~/.qwen/settings.json` não é copiado (F-238). `resolveRuntimeApiKey('deepseek')` (intent router) devolve só a chave da API direta.
  - No plano, `deepseek-flash`/`deepseek-v4-flash` viram `deepseek-v4-pro` na rota (`modelAliases`, motivo "servido pelo provedor escolhido"), no `--model` do spawn e no modelo padrão salvo. O catálogo do provider no plano só mostra o v4-pro.
  - Contas DeepSeek (chaves da API direta) não entram no plano: o pane sem conta usa a chave do plano e o pane com conta fixada é recusado. Na API direta, conta com chave `sk-sp-` ou rota para a Alibaba é recusada.
  - O bloco de chave do card mostra a vaga do provedor escolhido: "Chave da DeepSeek" ou "Chave do Token Plan (a mesma do Qwen Code)". Neste segundo caso, salvar e testar usam a vaga `qwen`.
  - Qwen Code: com a auth OpenAI-compatible no Token Plan, o catálogo vivo ganha o `deepseek-v4-pro` (só ele). Outros `deepseek-*` continuam fora. O Qwen 3.8 não entra no DeepSeek do Claude nem nas linhas de rota dele.
  - Verificação ao vivo (02/10, chave lida só dentro do processo): `qwen --model deepseek-v4-pro -p "responda só: ok"` saiu 0 com "ok" (controle: `deepseek-v4-flash` saiu 1 com 403). O `claude.exe` 2.1.287 com o env da rota `deepseek-token-plan` e `--model deepseek-v4-pro` saiu 0 com "ok". Com `--model deepseek-flash` saiu 1, por isso existe o alias.
  - Testes: `provider-config-deepseek.test.ts` (novo, ponta a ponta com launcher e manifestos reais), `deepseek-provider.test.ts`, `launcher-provider-manager.test.ts`, `qwen-settings.test.ts`, `cli-model-discovery.test.ts`, `task-router.test.ts`, `pty-manager.test.ts`, `ProvidersPanel.test.tsx`.
- Reabertura (02/10, depois da 0.76.168): o operador viu de novo `401 Authentication Fails, Your api key: ****WSah is invalid` num pane DeepSeek, até "Please run /login". A 0.76.168 ainda não tinha o F-724. A chave `…WSah` é a do Token Plan: está nas vagas `deepseek` e `qwen` do cofre e no `deepseek=` do launcher (conferido só por prefixo, tamanho e igualdade, decifrada em memória). O operador nunca salvou o card do DeepSeek (não há `~/.nexus/providers.json`). Com o F-724 como estava, o padrão "API direta" recusaria a chave e o DeepSeek ficaria sem credencial até alguém trocar o seletor.
- (resolvedor) Correção da reabertura: sem escolha salva, o provedor segue o slot `deepseek` do launcher (`defaultDeepseekProviderChoice`, em `defaultConfigFor`). Com `deepseek-base-url` no host do Token Plan, ou com chave `sk-sp-` sem base-url, vale o Alibaba Token Plan; nos outros casos, a API direta. A escolha salva no card continua valendo. O seletor mostra o provedor efetivo e, ao salvar o card, é ele que fica gravado. Testes: `deepseek-provider.test.ts` ("sem escolha salva, segue o slot `deepseek` do launcher") e `provider-config-deepseek.test.ts` (store novo, sem providers.json, com a forma do PC do operador). O teste de ponta a ponta reprova o código anterior.
