# F-146 — Modal de confirmação a cada pane tool da mão do operador sem missão

## F-146 | categoria: usabilidade | severidade: media | status: corrigido
- Tela/fluxo: pane aberto pelo operador sem missão (modal mostra "Missão:
  bootstrap") → agente chama `nexus_pane_close` / `nexus_pane_write` /
  `nexus_pane_ask` → modal nativo "Permitir ação solicitada pelo agente?".
- Arquivo:linha: `src/main/orch/mcp-dispatch.ts:871`,
  `src/main/orch/mcp-consent-policy.ts:71`.
- Passos: 1) abrir um pane direto (sem missão); 2) pedir ao agente para fechar
  ou falar com outros panes; 3) observar o modal por chamada/pane.
- Esperado: a mão do operador opera panes sem interromper o fluxo; o modal fica
  só para o que não tem caminho de volta.
- Observado: modal a cada `pane_close`/`pane_write`/`pane_ask`, com o mesmo
  texto genérico; fechar 3 panes = 3 perguntas.
- Evidencia (causa raiz): `requiresHumanConfirmationForTool` devolve true para
  as classes `mission-effect` e `execution-effect`; o auto-approve existente
  exigia contrato de missão aprovado, que não existe em pane direto. Como a
  permissão é de uso único por args (`consumePermission`), cada `paneId` novo
  pergunta de novo. A mão do operador já passava pelo dispatch
  (`OPERATOR_PANE_EFFECT_TOOLS`), mas parava no modal.
- Correcao: o dispatch auto-autoriza `permitsOperatorPaneEffect(ctx, tool)`
  (role `user`, sem missão, apenas pane_spawn/pane_write/pane_write_many/
  pane_ask/pane_close) quando o texto não é destrutivo
  (`isDestructivePaneInput`). Texto destrutivo injetado em PTY
  (`rm -rf`, `git reset --hard`, `sudo`, `git push --force`, …) volta ao modal,
  e shell/arquivo/git/deploy continuam com o piso de consentimento intacto.
- Validacao: `npx vitest run src/main/orch/mcp-dispatch-security.test.ts
  src/main/orch/mcp-consent-policy.test.ts` (98/98); `npm run typecheck` limpo.
