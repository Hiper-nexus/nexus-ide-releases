# F-1617 — No Windows, fechar um pane lento derruba o PTY host e todos os panes caem juntos

## F-1617 | categoria: estabilidade | severidade: critica | status: corrigido

- Tela/fluxo: missão com vários workers no Windows; o Maestro fecha um worker (`nexus_pane_close`, origem `pane-close`). Todos os panes da grade mostram de uma vez `[nexus] processo caiu. Use "Retomar missão" no topo deste painel.`
- Arquivo:linha (antes): `src/main/pty/pty-descendant-termination.ts:628-638` (`killPtyRoot` no win32 chamava `proc.kill()` a cada pedido) e `src/main/pty/pty-host-entry.ts:428-429` (mensagem `kill` sem sinal chamava `target.kill()` cru).
- Passos: 1) No Windows, abrir uma missão com vários panes de agente. 2) Fechar um pane cuja CLI leva mais de 1,5 s para sair depois do fechamento do console (AGY em 20/10). 3) Esperar ~1,7 s.
- Esperado: só o pane fechado termina; os outros seguem vivos.
- Observado (20/10, 0.76.345, 16:06:29): o Maestro fechou o worker AGY às 16:06:27.847; às 16:06:29.525 o utility process `node.mojom.NodeService` (o PTY host) saiu com `exitCode -1073740940` (`0xC0000374`, STATUS_HEAP_CORRUPTION, `crash-reports.json`). Os 7 terminais vivos receberam `agent-pty-terminate origin pty:post-exit-proof` no mesmo milissegundo e saída `-1` (`main.trace.ndjson`, `lifecycle-2026-10-20.ndjson`). RAM física livre 19,8 GB de 64 GB (não era falta de memória).
- Causa raiz: no Windows o `WindowsPtyAgent.kill()` do `@lydell/node-pty` (1.2.0-beta.12) não é idempotente: cada chamada repete o `ClosePseudoConsole` nativo sobre o mesmo HPCON. A escalada de `terminatePtyProcessTree` manda `SIGTERM`, espera a graça (1,5 s no `drivePhysicalTermination`) e, se a raiz não saiu, manda `SIGKILL`; no win32 os dois viravam `proc.kill()`. O 2º fechamento antes do `onExit` libera a mesma memória de novo e o host inteiro morre. CLIs que saem em menos de 1,5 s (Codex, Devin, Muse no mesmo dia) escapam; a que demora (AGY) derruba todos.
- Evidencia:
  - Reprodução isolada com o node-pty real (Node 22, `conpty.node` N-API), filho que ignora o fechamento do console: `kill()` simples ou duplo com a raiz já encerrada → host sobrevive; dois `kill()` antes do `onExit` → host sai com `0xC0000374`, o mesmo código da queda.
  - Mesma reprodução passando pelo `killPtyRoot` corrigido (`SIGTERM`, `SIGKILL` e pedido sem sinal antes do `onExit`), 3 rodadas → host sobrevive, filho encerrado (`onExit code=1`).
- (resolvedor) Correcao:
  - `pty-descendant-termination.ts`: `killPtyRoot` no win32 fecha o pseudoconsole só no 1º pedido por processo (`WeakSet`, marcado ANTES da chamada, para um `kill()` que lança nunca abrir um 2º fechamento); a escalada `SIGKILL` seguinte termina a raiz pelo PID (`process.kill(pid)` = TerminateProcess), sem tocar no HPCON. Fora do Windows nada muda. `signal` ficou opcional.
  - `pty-host-entry.ts`: a mensagem `kill` sem sinal passa por `killPtyRoot` (antes chamava `target.kill()` cru e podia ser o 2º fechamento).
  - `pty-descendant-termination.test.ts`: um fechamento só com pedidos repetidos, `kill()` que lança, escalada com raiz lenta pela `terminatePtyProcessTree` (um único `kill()`, PID terminado) e POSIX inalterado.
  - Validação: `npx vitest run src/main/pty/pty-descendant-termination.test.ts` (30 verdes); `npm run typecheck` (exit 0); `src/main/pty/`, `src/main/usage/` e `renderer-mission-authority-adoption.test.ts` com as mesmas 26 falhas do HEAD limpo no Windows (base conhecida), nenhuma nova.
- Não verificado: a reprodução usou um filho de teste, não o binário do AGY; a mudança do relay conout compartilhado (16/10, `scripts/patch-node-pty-win32.mjs`) não participa do mecanismo reproduzido.
- Relacionado a F-659 (o `kill()` sem sinal no Windows) e F-1618 (a recuperação depois desta queda perdeu a conversa do Maestro).
