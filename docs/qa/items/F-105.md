# F-105 — Leitura síncrona do Keychain congela o main inteiro (missões morrem sem diagnóstico)

## Status
corrigido

## Descrição
Em sessões de dev, qualquer leitura de segredo com cache frio (`getSecret` →
`safeStorage.decryptString`) entra em `SecItemCopyMatching` **síncrono** no main
do Electron. Como o binário de dev (`com.nexuside.dev`) não é a assinatura que o
ACL do cofre confia, o SecurityAgent segura a chamada indefinidamente — e com
ela morrem TOGETHER: timers (delegation-supervisor), gate HTTP de hooks,
IPC, entrega de handoffs, CDP. A missão congela no meio (worker spawned pela
metade, MCP call do orquestrador pendente para sempre) sem nenhum log.

## Evidência (21/08 ~19:37–20:00, missão acf86ff6)
- `sample` do PID do Electron main por 3s: thread principal 100% das amostras em
  `SecItemCopyMatching → SSDbUniqueRecordImpl::get → CSSM_DecryptDataFinal →
  SecurityServer::ClientSession::decrypt` — XPC para o securityd nunca volta.
- Missão parou às 19:37:22 exatamente no spawn do 3º worker ("pane spawn
  materialized" sem "session result"); zero eventos no journal por 22min;
  handoff `[auto]` ficou `queued` sem tentativa de entrega.
- CPU do main: 0% (bloqueio em syscall, não busy-loop).

## Correção
`secrets-store.ts`: em sessão de CLI de dev (`process.defaultApp` definido), o
vault fica DESLIGADO por padrão — leituras falham fechado (`null`) e writes
ficam em memória; os CLIs usam auth nativa. Opt-in: `NEXUS_DEV_VAULT=1`.
Kill-switch adicional `NEXUS_DEV_NO_VAULT=1`. Build empacotada inalterada.
A doutrina já existia (`startClaudeSubscriptionFreshness` só toca segredos com
cache quente); o buraco era o default permissivo em dev.

## Próximos passos (dívida)
1. Watchdog de hang do main com stack sample automático antes de reiniciar.
2. Mover decrypt para utilityProcess ou pre-warm assíncrono pós-boot também no
   empacotado (login travado ainda pode bloquear o primeiro acesso).
