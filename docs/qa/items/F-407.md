# F-407 — `util/atomic-write.ts`, o writer canônico de segredos, não tinha teste co-localizado

## F-407 | categoria: seguranca | severidade: media | status: corrigido
- Tela/fluxo: cobertura de teste da persistência atômica no processo main.
- Arquivo:linha: `src/main/util/atomic-write.ts` (108 linhas, 3 exports:
  `writeJsonAtomic:43`, `writeFileAtomic:52`, `writeTimestampedBackup:93`).
- Passos: 1) `ls src/main/util/ | grep atomic`; 2) comparar com a regra do
  `AGENTS.md`.
- Esperado: `AGENTS.md` › Authoritative Owners: "**Co-located tests**: every
  source file has a `.test.ts` sibling — run it after editing the source."
- Observado: existiam `atomic-write.ts` e **nenhum** `atomic-write.test.ts`. O
  módulo do qual **8 outros dependem** para persistência crash-safe de segredos —
  entre eles `src/main/remote/remote-device-token-store.ts:53` (tokens de
  pareamento remoto) e `src/main/remote/remote-bridge.ts` — não tinha uma linha
  de teste.

  Isso importa mais aqui do que a regra geral sugere, porque **todas** as
  garantias do módulo são sobre modos de falha: atomicidade sob falha de rename,
  ausência de temp residual, modo `0o600`, `O_NOFOLLOW` contra symlink
  pré-plantado, `fsync` do arquivo e do diretório. Ler o código não é evidência
  de que valem — é exatamente o tipo de propriedade que se escreve correta e se
  quebra numa refatoração sem que nada reclame. O cabeçalho do próprio arquivo
  descreve o cenário de ameaça ("a local attacker cannot pre-plant a symlink at
  the temp path to redirect the write") sem que houvesse teste afirmando o
  comportamento correspondente.
- Evidencia: `ls src/main/util/ | grep -E "atomic"` → só `atomic-write.ts`.
  `npx vitest run src/main/util/atomic-write.test.ts` antes da correção →
  "No test files found".
- Correcao: `src/main/util/atomic-write.test.ts` criado, 15 testes, cobrindo o
  que é observável:
  - publica o payload e não deixa temp residual (`readdirSync` do diretório);
  - cria diretório pai ausente;
  - **falha de rename**: destino anterior intacto, temp removido, erro original
    propagado (spy em `fs.renameSync`);
  - payload binário (`Uint8Array`) byte a byte;
  - **symlink no destino é substituído, não seguido** — o alvo do symlink fica
    intacto e o caminho vira arquivo regular. É a propriedade de segurança que o
    cabeçalho descreve;
  - modo `0o600` por default, modo explícito honrado (`0o640`), diretório pai
    criado `0o700`, e **re-aperto** de um destino que tinha sido deixado `0o644`;
  - diretório pai pré-existente tem o modo **preservado** (comportamento real de
    `mkdirSync recursive`, documentado em vez de desejado);
  - `writeJsonAtomic` **não** emite newline final — fixado de propósito porque
    `persistence/atomic-json-file.ts` delega aqui e mantém o próprio newline por
    compatibilidade de bytes (ver F-406);
  - `writeTimestampedBackup` devolve um sibling legível, deixa o original
    intacto, dá nome distinto a cada chamada e cria o backup `0o600`.

  As asserções de modo ficam em `describe.skipIf(process.platform === 'win32')` /
  `it.skipIf(...)`, porque bits de modo não são significativos no Windows.
- Validacao: `npx vitest run src/main/util/atomic-write.test.ts` → **15/15
  verdes na primeira execução**, o que é o resultado relevante: as garantias
  documentadas já valiam, só não eram verificadas.
  `npx vitest run src/main/persistence src/main/util` → 320 testes em 31
  arquivos, verdes. `npm run lint:oxlint:ratchet` → 168, inalterado (o arquivo
  novo soma 0 warnings). `npx tsc --noEmit` sem erro neste arquivo.
- Limites: `fsyncDirectory` é best-effort e silencioso em plataformas que não
  suportam abrir diretório como descritor (Windows); isso não é testado, porque
  testar exigiria simular a falha do `openSync` no diretório e o comportamento
  correto é justamente não lançar. `O_NOFOLLOW` no **temp** não é testável
  diretamente — o nome vem de `randomBytes(8)`, então não há como pré-plantar;
  o teste de symlink cobre o caso atingível, que é o do destino.
