# F-1627 — O dev rouba o `nexus://` do app instalado e o login para de voltar

## F-1627 | categoria: funcional | severidade: alta | status: corrigido

- Tela/fluxo: login com GitHub/Google no app instalado (macOS). O navegador conclui ("Login concluído"), o Nexus fica para sempre em "Consultando seu acesso".
- Arquivo:linha (antes): `src/main/deep-link.ts:257` — `app.setAsDefaultProtocolClient(SCHEME, process.execPath, [script])` dentro do ramo `process.defaultApp` (dev), sem condição de plataforma.
- Passos: 1) Rodar `npm run start` uma vez (qualquer worktree). 2) Fechar o dev. 3) Abrir o app instalado e tentar o login.
- Esperado: o callback `nexus://` volta para o app instalado e a sessão entra.
- Observado: o link é engolido. Nenhum app abre, nenhum erro aparece, nenhum log registra nada.
- Causa: `setAsDefaultProtocolClient` em dev aponta o handler do macOS para `com.nexuside.dev` — o bundle `.dev-electron/dist/Electron.app`, que **não declara `CFBundleURLTypes`**. O sistema passa a entregar `nexus://` a um app que nunca reivindicou o esquema, e descarta a entrega em silêncio. Quem declara corretamente é `/Applications/NexusIDE.app` (`com.nexuside.app`, `CFBundleURLName` + `nexus`). Como o empacotado reivindica de volta sempre que roda, o sintoma parecia aleatório — era o "às vezes não pega no primeiro login" relatado há tempos.
- Evidencia (21/10/2026): com o handler em `com.nexuside.dev`, `open nexus://quota` não abre nem reage em nenhum app. Depois de apontar a preferência (`LSHandlers` em `~/Library/Preferences/com.apple.LaunchServices/com.apple.launchservices.secure.plist`) para `com.nexuside.app`, o mesmo comando navegou o app de "Início" para "Configurações › Uso e cotas". Verificado na tela.
- Lixo associado: 82 apps reivindicavam `nexus://` na máquina do operador, **80 fantasmas** em `/private/var/folders/.../electron-packager/tmp-*/NexusIDE.app` — cada `npm run make` deixa uma cópia registrada e a pasta temporária some depois. Removidos com `lsregister -u <path>` (o `-kill` foi REMOVIDO nesta versão do macOS).
- (resolvedor) Correcao: `shouldClaimDeepLinkScheme({isDev, platform})` em `src/main/deep-link.ts`, função pura. Em dev no `darwin` o app não reivindica o esquema — reivindicar é estritamente pior que não reivindicar, porque o bundle de dev não consegue receber o link de qualquer forma. Empacotado reivindica sempre; dev no `win32`/`linux` segue reivindicando (lá o registro de sistema e a entrada `.desktop` funcionam). Não há saída por variável de ambiente: ela seria uma armadilha, porque reivindicar em dev no macOS é exatamente o que quebra a entrega — o "escape hatch" reproduziria o bug em vez de contorná-lo (achado na revisão do PR #153). Quem precisa que o build de dev receba `nexus://` tem de declarar `CFBundleURLTypes` no bundle de desenvolvimento primeiro. O ramo que não reivindica loga o motivo.
- Evidencia da correcao: `npx vitest run src/main/deep-link.test.ts` (17 testes) — empacotado reivindica nas três plataformas; dev no macOS não; dev no Windows/Linux sim; e não existe variável que force o contrário.
- Relacionado: F-1628 (segunda camada — a troca mentia "login superseded" e escondia o motivo real da falha quando o link CHEGAVA).
- Não verificado: se o Windows e o Linux sofrem o mesmo roubo com outros sintomas; lá o registro de dev funciona de verdade, então o comportamento foi preservado em vez de alterado às cegas.
