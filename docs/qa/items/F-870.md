# F-870 — Cliente OCI encerrado não prova fim físico do comando

## F-870 | categoria: seguranca | severidade: alta | status: aberto
- Tela/fluxo: comandos pesados MCP Main-owned no sandbox OCI do Windows; reserva de execução e limpeza do runtime.
- Arquivo:linha: `src/main/runtime/process-sandbox.ts:968`; implementação de ownership em `src/main/orch/owned-oci-command.ts`.
- Passos: 1) Executar um comando OCI duradouro. 2) Encerrar o cliente `docker run`/attach sem encerrar o contêiner. 3) Observar a reserva que toma fechamento do cliente como saída física.
- Esperado: manter reserva e runtime até o fechamento do cliente exato e a remoção comprovada do contêiner exato; cancelamento encerra apenas esse contêiner.
- Observado: o plano anterior usa `run --rm`, sem identidade Main-owned nem prova independente do estado do engine; o cliente pode morrer antes do trabalho físico.
- Evidencia: ciclo vermelho inicial `owned-oci-command.test.ts`: 17 testes falharam com ownership ausente; fake cliente real em Node 22 mantém estado do kernel `running` após `ChildProcess.close`.
- (resolvedor) Correcao: `prepareOwnedOciCommand` cria sem executar, usa nome e nonce aleatórios somente em memória, captura ID completo e prova ID/nome/label antes de devolver `start --attach`. Mantém os mounts, ambiente, rede, imagem fixada e limites do plano OCI original. Não usa cidfile nem grava ownership nos mounts do agente. `waitForExit` exige `close` do filho registrado e ausência do ID completo; remover esse ID também impede um start atrasado. `stop` prova ownership antes de encerrar/remover. Erros de transporte, resposta malformada e identidade substituída mantêm a espera e repetem a prova. Resposta de criação perdida limpa o contêiner comprovado antes de rejeitar; cliente que comprovadamente não nasceu rejeita sem criar ownership fictício. Mensagens de erro nunca incluem stdout/stderr, comandos, ambiente ou credenciais.
- Integração do chamador: owned-command-launch chama waitForExit imediatamente após spawn; tools-terminal/bg conservam reserva/runtime pela promessa, usam stop no cancelamento e dispose na falha pré-spawn. União de testes/TypeScript validada em F-868. O runtime Docker Windows real continua não verificado; o status deste item conserva essa pendência de aceite.
- Validação local (2026-10-03, Node 22, ABI 127, mutex de validação da sessão): `npx vitest run src/main/orch/owned-oci-command.test.ts --maxWorkers=1` passou 27/27; `npm run typecheck` passou; `git diff --check` passou. A regressão de cliente que não nasceu também foi vista vermelha (`pending` indevido) antes da correção.
- Referência do contrato Docker: [`container create`](https://docs.docker.com/reference/cli/docker/container/create/) cria sem iniciar; [`container inspect`](https://docs.docker.com/reference/cli/docker/container/inspect/) e [`container ls`](https://docs.docker.com/reference/cli/docker/container/ls/) permitem consultas restritas e ID sem truncar.
- Limite: não há runtime Docker Windows disponível neste ambiente. A evidência local é de fake-client/estado de kernel e processos reais Node 22; Windows OCI real permanece não verificado.
