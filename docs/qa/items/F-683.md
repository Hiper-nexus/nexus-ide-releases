# F-683 — Helper roteado para modelo que o provider recusa ("Model access is disabled") e o roteador repetia o erro

## F-683 | categoria: funcional | severidade: alta | status: corrigido
- Tela/fluxo: missão da aba no hipergo (RU-261), helper roteado automaticamente para OpenCode.
- Arquivo:linha: `src/main/orch/limit-detector.ts` (padrões de modelo recusado), `src/main/orch/failover.ts` (ramo `hit.kind === 'model'`), `src/main/orch/task-router.ts` (hidratação dos candidatos).
- Passos: 1) Roteamento escolhe `opencode/deepseek-v4-flash` (OpenCode Zen) para um helper. 2) A conta não tem acesso ao modelo.
- Esperado: o pane troca de modelo (F-520) e o roteador não manda o próximo helper para o mesmo modelo.
- Observado (29/09 14:02–14:03): "[nexus] processo caiu (code 1)" com "Error: Upstream request failed: Model access is disabled". O log do OpenCode no provider-state mostra 5 tentativas em `providerID=opencode modelID=deepseek-v4-flash`, todas com o mesmo erro; o trace F-212 grava `agent-pty-exit` opencode worker exit 1, uptime 83 s, sem origem de término (morte natural).
- Causa: o texto do OpenCode Zen não casava nenhum padrão canônico de "modelo recusado", então o failover não trocava o modelo; e mesmo quando troca, o roteador não sabia da recusa e podia escolher o mesmo modelo para o helper seguinte.
- (resolvedor) Correcao: padrão `upstream request failed: model access is disabled` como `kind: 'model'`; no ramo de modelo recusado do failover, `quarantineRejectedModel` põe o par CLI+modelo em quarentena por 12 h (memória do Main, some no reinício); `routeTask` pula candidatos em quarentena com a nota "recusado pelo provider". Testes: `limit-detector.test.ts` (texto real casa; prosa não), `model-access-quarantine.test.ts`, `task-router.test.ts` (F-683: modelo em quarentena sai da rota).
