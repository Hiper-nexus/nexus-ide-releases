# F-510 — Grok pede device-login em loop no Nexus com sessão válida (sombra stale da conta gerenciada)

## F-510 | categoria: auth-detection | severidade: alta | status: corrigido
- Tela/fluxo: abrir o Grok no Nexus (pane com overlay `GROK_HOME`). O CLI
  ignora a sessão, imprime o device-code, o navegador mostra "Dispositivo
  Autorizado" — e na próxima abertura tudo se repete.
- Arquivo:linha: `src/main/orch/cli-mcp-session-grok.ts` (montagem do
  overlay; `resolveGrokOverlayAuthSource` novo) e
  `src/main/orch/cli-mcp-session-grok.test.ts` (novo, 7 testes).
- Passos: 1) `grok login` no Terminal (sessão válida); 2) conta gerenciada
  grok com captura antiga; 3) abrir o Grok no Nexus → device-login; autorizar;
  4) reabrir → device-login de novo.
- Esperado: o overlay enxerga a sessão viva do operador; sem novo login.
- Observado (verificado nesta máquina, só metadados, sem segredos):
  - `~/.grok/auth.json` VÁLIDO (`expires_at=2026-09-08T18:22:51Z`, mesmo
    e-mail da conta gerenciada, `auth_mode=oidc`);
  - `~/.nexus/managed-accounts/grok/acct-mtlzidwr-1/home/auth.json` é cópia
    capturada em 03/09, **expirada em `2026-09-03T20:43:37Z`** — nada nunca
    recapturou após o re-login no Terminal;
  - overlay fresco (`mcp-clients/grok/99f5df…`, 11:54) **sem `auth.json`**
    (stat falha) embora o set linkado o inclua — a CLI rejeitou a credencial
    expirada e removeu o link durante o login;
  - `GROK_HOME` vazio → `grok -p` responde `Not signed in` (a CLI obedece ao
    overlay, não ao `~/.grok`).
  - Cadeia: conta gerenciada fixada → providerHome = managed home → overlay
    linka a cópia expirada → grok rejeita e limpa o link → device flow →
    token cai no efêmero (rebuild com `rm -rf` perde) → loop.
- Correção aplicada (só link de overlay; **nenhuma mutação no vault**):
  `resolveGrokOverlayAuthSource(providerHome, home)` — managed com QUALQUER
  entrada fresca → providerHome (N contas coexistem, intocado); senão, nativa
  fresca + (managed sem identidades OU e-mail igual = mesma conta com
  credencial rodada) → home nativo; resto (pin de outra conta, nada fresco)
  → providerHome = comportamento de hoje, sem vazar identidade alheia.
  Par `auth.json`/`auth.json.lock` linkado uma única vez da origem resolvida
  (governado e não-governado).
- Validação: `npm run typecheck` limpo; `cli-mcp-session-grok.test.ts` 7/7 +
  `cli-mcp-session-config.test.ts` 25/25; prova ao vivo com os diretórios
  reais (scratch `/tmp/live-grok-overlay.test.ts`, não commitado):
  sombra expirada resolve para `~/.grok` e o overlay linka o `auth.json`
  nativo (2/2).
- Limites: a cópia do vault continua expirada (recaptura é lane do
  multi-conta em andamento — sem conflito: este fix não toca
  `managed-credentials.ts`/`account-store.ts`); `active_sessions.json`
  segue `[]` (a CLI o gerencia); como todo fix de motor, exige rebuild do
  app empacotado para valer.
