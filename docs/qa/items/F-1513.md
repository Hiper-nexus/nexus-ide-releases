# F-1513 — macOS abria o modal «security deseja acessar a chave "ai.meta.dev.credentials"» na tela de Início

## F-1513 | categoria: seguranca | severidade: alta | status: corrigido
- Tela/fluxo: abertura do NexusIDE no macOS (tela de Início) → poll inicial do `QuotaService` (`useQuotaSync`) → `resolveMuseLoginCredential` → `readMusePlatformSecret`.
- Arquivo:linha (antes): `src/main/quota/muse-usage.ts:378-393` (`readMusePlatformSecret` executava `security find-generic-password -s ai.meta.dev.credentials -a <account> -w` no `darwin`).
- Passos:
  1. Ter o Muse Code logado via OAuth no macOS (`~/.config/muse/auth.json` com `storage: "keychain"` e item `ai.meta.dev.credentials` no Chaveiro `login`).
  2. Abrir ou reiniciar o NexusIDE no macOS.
- Esperado: nenhum diálogo de senha do Chaveiro (`security deseja acessar a chave "ai.meta.dev.credentials"`) aparece; a sessão do Muse continua reconhecida sem tocar no segredo (`museLoginSignedIn` / `museKeychainItemExists` sem `-w`, F-616).
- Observado: logo ao abrir a tela de Início («O que você quer criar?»), o macOS exibia o modal `security deseja acessar a chave "ai.meta.dev.credentials" de suas chaves. Para permitir isso, digite a senha das chaves "login"`.
- Evidencia:
  - O item `ai.meta.dev.credentials` no Chaveiro `login.keychain-db` é criado e renovado diretamente pelo binário nativo `muse-bin-*` via `Security.framework` (`SecItemAdd`), cuja ACL autoriza exclusivamente o próprio `muse-bin-*` — nunca `/usr/bin/security`.
  - O F-1447 apenas guardava a negação em um `Map` em memória (`museSecretCache`) com `MUSE_SECRET_DENIED_BACKOFF_MS = Infinity`, mas mantinha a chamada `security find-generic-password -s ai.meta.dev.credentials -a <account> -w`:
    1. A cada abertura/atualização do app, `museSecretCache` nascia vazio e disparava `security … -w` imediatamente no boot;
    2. O `timeout: 5_000` com `SIGKILL` matava o processo `security` enquanto o modal do `SecurityAgent` continuava aberto na tela, descartando qualquer senha digitada após 5 s;
    3. Clicar em «Permitir» reabria o modal a cada 10 min (`MUSE_SECRET_CACHE_TTL_MS`);
    4. Clicar em «Sempre permitir» concedia a ACL ao binário público `/usr/bin/security` (expondo o segredo a qualquer processo do usuário, mesma classe do F-993) até a próxima rotação de token ou atualização do `muse-bin-*`, que recriava a ACL e fazia o modal voltar.
- (resolvedor) Correcao:
  - `src/main/quota/muse-usage.ts` (`readMusePlatformSecret`): no `darwin`, retorna `Promise.resolve(null)` sem invocar `security find-generic-password … -w`. A detecção de sessão conectada segue por `museLoginSignedIn` / `museKeychainItemExists` (atributos sem `-w`, zero modal), e `fetchLiveProviderWindows('muse', …)` reporta `quota-key-required` («conectado, cota sem fonte») quando não há `META_API_KEY` nem `api_key` em arquivo. A leitura assíncrona via `secret-tool` permanece restrita ao Linux.
  - `src/main/quota/muse-usage.test.ts`: teste de regressão garantindo que no `darwin` `readMusePlatformSecret` e `resolveMuseLoginCredential` nunca invocam `security -w`, preservando `museLoginSignedIn === true`.
- Validacao: `npx vitest run src/main/quota/muse-usage.test.ts src/main/quota/provider-live-usage.test.ts src/main/adapters/subscription-auth.muse-keychain.test.ts`, `npm run typecheck`, `npm run lint:main-sync`, `npm run security:renderer-sinks`.
