# F-576 — Pane Claude no Windows abre "Not logged in": `CLAUDE_CONFIG_DIR=""` joga o store de credenciais para o cwd

## F-576 | categoria: funcional | severidade: alta | status: corrigido

- Tela/fluxo: pane do Claude nativo no Windows ("+ Pane", terminal de login,
  operator-choice) — mesmo sintoma do F-575, causa raiz diferente.
- Arquivo:linha: `src/main/orch/mcp-server.ts` (`env.CLAUDE_CONFIG_DIR = ""`,
  F-567/0.76.45); merge em `src/main/pty/pty-manager.ts` (`Object.assign(env,
  decoration.env)`).
- Passos: 1) abrir um pane Claude no Windows; 2) "Not logged in · Run /login"
  mesmo com `claude auth status` → `loggedIn: true` no shell real; 3) /login
  dentro do pane reporta "Login successful"; 4) próximo prompt volta a dizer
  "Not logged in".
- Esperado: o pane enxerga `~/.claude/.credentials.json` linkado no overlay
  (backend de arquivo no Windows) e o login persiste.
- Observado: o `.credentials.json` nativo e o do overlay ficam intactos e
  hardlinkados (LastWriteTime de dias atrás — nada os toca); o login OAuth
  completa em memória (`oauthAccount.profileFetchedAt` do `.claude.json` do
  overlay atualiza na hora) mas a credencial nunca é relida.
- Causa (reproduzida nesta máquina, 17/09): `env.CLAUDE_CONFIG_DIR = ""`
  pretendia neutralizar um path herdado para as sessões reais, mas string
  vazia **não é unset** — a var continua no env block como
  `CLAUDE_CONFIG_DIR=`. O resolver de config dir do binário
  (`(env.CLAUDE_CONFIG_DIR ?? join(homedir(),'.claude'))`) usa `??`: `""`
  passa literal, o config dir vira `""` e todo o state file-backed
  (`.credentials.json`, `projects`, `sessions`) resolve **relativo ao cwd do
  pane**. Prova controlada com spawn Node e env literal do pane:
  - `CLAUDE_CONFIG_DIR=""` + cwd contendo `.credentials.json` →
    `claude auth status` → `loggedIn: true`, `configDirectory: ""`,
    `projectsDirectory: "projects"`;
  - `CLAUDE_CONFIG_DIR=""` + cwd vazio → `loggedIn: false`.
  - Sem a var (removida do env) + HOME=<overlay> → `loggedIn: true`,
    `configDirectory: <overlay>\.claude`.
  - O `.claude.json` seguia funcionando porque seu resolver usa `||`
    (falsy → homedir) — inconsistência `??` vs `||` dentro do próprio binário,
    exatamente o que mascarou o bug: oauthAccount/profile update ok,
    credencial nunca lida. macOS não quebrava porque lá o store é Keychain
    (F-575); no Windows o store é o arquivo.
- Correção (`pty-manager.ts` + `mcp-server.ts`): `AgentSpawnDecoration` ganha
  `envRemove?: readonly string[]` — remoção real da chave no merge
  (`delete env[key]`), espelhando o contrato de `overrides.suppressEnv`. O
  branch de HOME efêmero Claude-family empurra `CLAUDE_CONFIG_DIR` para
  `envRemove` em vez de atribuir `""`: sem a var, o resolver cai no
  `join(homedir(), '.claude')` → `<overlay>/.claude` → credencial linkada.
  A garantia original do F-567 (não herdar path custom — ex.: passthrough
  declarado por adapter de usuário com bin `claude`) fica preservada pela
  remoção pós-merge.
- Evidência RED→GREEN: assertion `envRemove: ['CLAUDE_CONFIG_DIR']` +
  `env.CLAUDE_CONFIG_DIR === undefined` no teste de HOME efêmero claude/glm
  em `mcp-server-governed-profile.test.ts` falhava antes (env trazia `""`);
  teste novo `deletes decoration envRemove keys from the spawned child env`
  em `pty-manager.test.ts` prova a chave ausente do spec enviado ao PTY.
  Reprodução manual do resolver documentada acima.
