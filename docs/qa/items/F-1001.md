# F-1001 — Badge de RAM sumia no Linux depois de ajuste do relógio

## F-1001 | categoria: funcional | severidade: media | status: corrigido
- Tela/fluxo: badge de RAM do pane (PaneToolbar, `usePaneFootprintFeed`) ← push `perf:paneFootprints` ← `footprint-probe` do PTY host (`captureFootprints`).
- Arquivo:linha: `src/main/pty/pane-footprint.ts:42,110` (identidade do root = PID + início com tolerância de 2 s); `src/main/pty/pty-host-entry.ts:77-105` (`ps -axo pid=,ppid=,rss=,lstart=`). Relacionado a F-572 e QLT-11 (122cf2ec8).
- Passos: 1) Linux (alvo de release), pane de agente aberto com o badge de RAM visível. 2) Suspender e retomar a máquina (ou o NTP dar um passo de alguns segundos no relógio). 3) Esperar a próxima amostra.
- Esperado: o badge continua mostrando a RAM da árvore do pane.
- Observado: no Linux o `lstart` é btime + starttime/HZ, e o btime segue o relógio de parede. Um passo de +3 s desloca o início de todos os processos; |lstart − spawnedAtMs| > 2.000 ms → o root vira "PID reciclado" → `rssBytes: null` em toda amostra até o pane morrer; o badge some. Antes do QLT-11 o root seguia só pelo PID e isso não acontecia.
- Evidencia: revisão sênior (Fable) da QLT-11; reprodução determinística no teste novo (tabela com o mesmo root deslocado +3 s, +300 s e −90 s → `rssBytes: null` no código anterior). Lacuna de teste apontada junto: nada executava o `ps` real nem provava o `LANG/LC_ALL=C` — nesta máquina, em pt-BR, `ps -o lstart=` imprime `qui  8 out 00:14:49 2026` e o parse lê 0 de 630 linhas.
- (resolvedor) Correcao: `attributeSessionFootprints(table, roots, host)` aceita o root também quando ele é filho direto do PTY host (`rootRow.ppid === host.pid`) — o processo raiz da sessão é criado pelo node-pty no próprio host. A proteção contra PID reciclado continua: um processo com outro pai e outro início vira null; o `ps` da própria amostra (`transientPids`, o único filho que o host cria nesse instante) não conta; e quando duas sessões reivindicam o mesmo PID (a nova herdou o número antes de a velha sair do mapa) só vale a regra de PID + início. Sem `host`, a regra é a de antes. O host passa `{ pid: process.pid, transientPids: [pid do ps] }`. O comando e o env do `ps` saíram para `FOOTPRINT_PS_ARGS` e `footprintPsEnv` (força `LANG`, `LC_ALL` e `LC_TIME` = C sobre o env do operador), usados pelo host e pelos testes. Arquivos: `src/main/pty/pane-footprint.ts`, `src/main/pty/pty-host-entry.ts`, teste `src/main/pty/pane-footprint.test.ts`. Commit: ver `git log --grep F-1001`.
- Validacao: vitest por launchd (fora do pane, Node 22). `pane-footprint.test.ts`: relógio deslocado +3 s/+300 s/−90 s com root filho do host → atribuído (vermelho antes); PID reciclado com outro pai, o `ps` do host e dois roots com o mesmo PID → null; sem host → regra antiga. `ps` real da máquina (macOS aqui; pulado se não houver `ps`): com `footprintPsEnv` sobre um env pt-BR, todas as linhas parseiam, o próprio processo do teste aparece com o ppid certo e início a < 5 s, e a atribuição dá RSS > 0; sem forçar C, com o locale pt_BR instalado, o parse da saída localizada é vazio (pulado com motivo se o locale não existir). Mutações: tirar `LC_ALL` do `footprintPsEnv` → o teste do `ps` real fica vermelho; tirar a regra do filho do host → o teste do relógio fica vermelho. Junto: `pane-footprint-broadcast`, `pane-footprint-store`, `PaneToolbar*`, `npm run typecheck`, `npm run lint`.
- Limite: não rodou num Linux real (a máquina de validação é macOS); o deslocamento do btime foi reproduzido pela tabela do `ps`, não por um suspend de verdade.
