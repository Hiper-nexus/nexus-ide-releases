# F-1323 — LSP ignorava `extends` do tsconfig e acusava erro falso de módulo

## F-1323 | categoria: corretude | severidade: media | status: corrigido
- Tela/fluxo: tools `nexus_lsp_*` (diagnostics/definition/references/symbols via worker `src/main/orch/lsp-worker-source.ts`) — varredura s240, sonda A1.
- Arquivo:linha (antes, base cb3191f3f): `src/main/orch/lsp-worker-source.ts:389-417` (`safeProjectConfig` usava `parseConfigFileTextToJson` + `convertCompilerOptionsFromJson` só do `compilerOptions` do filho — `extends` nunca era lido e include/exclude/files da base não eram herdados).
- Passos: 1) Projeto com `tsconfig.json` `{ "extends": "./tsconfig.base.json" }` e base com `paths` `{ "@local/*": ["src/*"] }`. 2) `nexus_lsp_diagnostics` em `src/use.ts` com `import { greet } from '@local/lib'` devolve TS2307 "Cannot find module '@local/lib'". 3) Copiando as MESMAS opções para o `tsconfig.json` (sem extends), `items=[]`.
- Esperado: a cadeia de `extends` local é resolvida (caminhos relativos ao arquivo que declara), `paths`/`baseUrl` da base valem, e diagnostics não acusam TS2307 falso; definition de `greet` aponta para `src/lib.ts`.
- Observado: qualquer opção herdada por `extends` sumia — alias de módulo, strict, jsx — e o LSP respondia com erros falsos ou sem as regras do projeto.
- Evidencia: testes novos em `src/main/orch/lsp-sidecar.test.ts` escritos ANTES da correção — vermelho com TS2307 no caso base+extends; depois da correção, `diagnostics.items` vazio, definition em `src/lib.ts` e `budget.degraded=false`.
- (resolvedor) Correcao:
  - Causa raiz: o parse lia só o JSON do filho; a semântica de herança do tsconfig (extends em cadeia, lista, include/exclude herdados, caminhos relativos à base) nunca era aplicada.
  - `safeProjectConfig` agora usa `ts.parseJsonConfigFileContent` com um host restrito: `readFile`/`fileExists` são o próprio `safeRead`/`safeFileExists` (arquivo real sem link, `inside(root)`, tetos de bytes/arquivos, prazo) e `readDirectory` delega ao `ts.matchFiles` com o `matchFileSystemEntries` guardado (teto de diretórios/entradas, IGNORED_DIRS, prazo). O parse resolve a cadeia de `extends` (inclusive lista, TS 5.x), mescla compilerOptions com o basePath correto por arquivo e expande include/exclude/files herdados.
  - Base ilegível, ausente ou cadeia circular = erro de parse: com `extends` presente e `parsed.errors.length > 0`, o worker segue com o que resolveu e marca `budget.degraded=true` (resultado sai `truncated`) — degradação explícita, nunca silenciosa. Erros de config SEM extends (ex.: opção desconhecida) mantêm o comportamento anterior, sem degradação nova.
  - `scriptsFromParsedConfig` filtra `parsed.fileNames` por `safeRealFile` (workspace, sem `.git`/`.nexus`, realpath preso à raiz) + extensão suportada e o mesmo teto `maxProjectFiles`. Guards pós-merge inalterados (`baseUrl`/`outDir`/`rootDir` fora da raiz removidos, `rootDirs`/`typeRoots`/`types` filtrados/capados, `noEmit`, `plugins` e `configFilePath` zerados).
  - Arquivos: `src/main/orch/lsp-worker-source.ts`, `src/main/orch/lsp-sidecar.test.ts`. Commit: ver `git log --grep F-1323`.
- Validacao: `npx vitest run src/main/orch/lsp-sidecar.test.ts` — verde (inclui os testes pré-existentes: escopo externo nunca resolve, teto de arquivos do projeto, tsconfig.lsp.json dedicado, includes ancorados na raiz, repo real ≤ 2000 diretórios, F-1252 degraded, F-1183 asar).
- Riscos: `extends` de pacote (`@tsconfig/…`) resolve via node_modules somente se legível pelas guardas (arquivo real, dentro da raiz, sob o teto de bytes) — caso contrário degrada explicitamente. `parsed.errors` com extends marca degraded mesmo para erro benigno na base (conservador, visível no resultado).
