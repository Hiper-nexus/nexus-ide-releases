# F-1506 — Windows: `%TEMP%` em 8.3 derruba o sandbox de processo

## F-1506 | categoria: funcional | severidade: alta | status: corrigido
- Renumerado na integração com a origin (0.76.252): este achado era o F-1452 da frente de squads (nunca publicado) e virou F-1506 para não colidir com a numeração que a origin publicou (F-1436..F-1451).
- Tela/fluxo: comando confinado no Windows → `createScopedSandboxHome` + `buildScopedExecPlan`/`buildScopedShellPlan` (`src/main/runtime/process-sandbox.ts`). Usado por `nexus_terminal_run`, `nexus_bg_run`, verificações de conclusão de missão (`orch/completion-check-executors.ts`), portão de regressão (`regression-gate/regression-gate.ts`) e sensores (`context/sensor-broker.ts`).
- Arquivo:linha: `src/main/runtime/process-sandbox.ts:549` (antes) — a pasta do runtime era resolvida com `fs.realpathSync`; HOME/temp privados com `fs.realpathSync.native` (`:254`, `:588-589`).
- Passos: 1) Windows com usuário de mais de 8 letras (`%TEMP%` = `C:\Users\ADMINI~1\AppData\Local\Temp`). 2) Rodar qualquer comando confinado (terminal do agente, verificação de conclusão, portão de regressão).
- Esperado: o plano do sandbox é montado (com OCI configurado) ou falha pela razão real (`secure process sandbox provider is unavailable on win32; configure …`).
- Observado: `sandbox private HOME or temp resolves outside its runtime directory`. Medido aqui: `realpathSync(os.tmpdir())` = `C:\Users\ADMINI~1\…`, `realpathSync.native` = `C:\Users\Administrador\…`. Com o runtime OCI configurado o sandbox nunca funcionava; sem ele a mensagem escondia o que fazer. As verificações de conclusão viravam `code_checks_unavailable` com o texto errado.
- Causa raiz: os dois lados da checagem "está dentro" vinham de resoluções diferentes. `fs.realpathSync` (JS) mantém o nome curto; `fs.realpathSync.native` devolve o longo. Nenhum HOME longo "cabia" no runtime curto. A mesma mistura deixava a disjunção runtime × checkout cega quando só o checkout vinha em 8.3 (runtime dentro do checkout passava).
- Correcao: `normalizeExecPlan` resolve a pasta do runtime com `fs.realpathSync.native`, a mesma forma do HOME/temp, e compara a disjunção runtime × checkout (e o `processHome` × checkout) com a raiz também em forma canônica (`rootCanonical`). Nenhuma checagem foi removida ou afrouxada: a disjunção ficou mais estrita. No macOS/Linux a pasta criada por `mkdtemp` resolve igual nas duas formas. Commit: ver `git log --grep F-1506`.
- Evidencia:
  - RED (código antigo): `npx vitest run src/main/runtime/process-sandbox.test.ts -t F-1506` → `Error: sandbox private HOME or temp resolves outside its runtime directory` em `normalizeExecPlan` (`process-sandbox.ts:582`), com o runtime passado em 8.3 (`windowsShortPath`, via `for %I in (...) do @echo %~sI`). O `vitest.setup.ts` canoniza o TEMP, por isso as suítes existentes não pegavam.
  - GREEN: o mesmo teste passa (plano OCI monta `src=<nome longo>`; shell sem OCI falha com `sandbox provider is unavailable`; runtime dentro do checkout escrito em 8.3 é recusado com `disjoint from the project checkout`). Arquivo inteiro: 16 passaram, 21 pulados (só macOS/Linux) e 2 falhas de ambiente do Windows que já falhavam na base (bits de modo `0o077` e `/bin/sh` inexistente).
